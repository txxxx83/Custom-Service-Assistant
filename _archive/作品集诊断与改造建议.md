# 《电商售后 AI 客服工作台》作品集诊断

> 诊断对象：`D:\Desktop\产品\demo`
> 诊断目的：用于产品经理实习/正职作品集
> 诊断方式：读代码、读三份 docx、复算 50 条评测、实际运行 Streamlit 并点击 C1–C4

## 0. 一句话结论

**这个项目不是“做得不好”，而是“三个项目叠在了一起”**：一个 3 分钟的交互剧本、一个规则引擎基线、一个 DeepSeek 生成 Demo；再加三份互相不一致的文档（开发规格 / 必答问题手册 / README）。

所以你觉得“怪”，不是错觉。怪的地方很具体：**面试官看到的、你评测的、你文档里写的，不是同一个东西。**

但你抓到的产品洞察是真的好：**售后 AI 最贵的错误不是答得慢，而是越权承诺。** 这个选题比大多数“套壳 ChatGPT + 漂亮 UI”的初级作品集强。问题不在想法，在证据结构和叙事。

---

## 1. 先说你真正做对的地方

这几条不要丢，它们是你区别于普通候选人的地方：

1. **选题有洞察**：你把问题从“AI 能不能回答”换成了“AI 什么时候不该回答”。在售后场景里，错误承诺会带来赔偿、投诉、平台处罚，这个代价判断是产品经理的核心能力。
2. **四态模型是真正的产品设计**：`ready / conflict / no_knowledge / blocked` 不是四个颜色，而是四种不同的业务处置方式。这比“置信度低于 0.7 就转人工”成熟得多。
3. **人机协同的链路是完整的**：建议 → 证据 → 采纳/编辑 → 发送 → 审计 → 转人工。你考虑到了“建议可以被拒绝”“发送权属于人”“转人工要带原因”，这些都是真实客服系统会关心的。
4. **你有能力边界意识**：V1/V2/V3 对比、剧本 vs 引擎、诚实说明“没有后端/数据库”。大多数初级作品集会把这些藏起来，你写出来了，这是加分项。

**你现在的任务不是再加功能，而是把这条洞察证明清楚。**

## 2. 为什么“怪”：三套叙事在打架

### 2.1 三个版本，各说各话

| 层 | 面试官实际看到什么 | 它实际上是什么 | 评测/文档说它是什么 |
| --- | --- | --- | --- |
| 工作台（默认） | 7 条会话，右侧 AI 建议，四态 | `mock-data.json` 里 4 条预设建议；**没有 API key 时才是这四条** | README 说“由 DeepSeek 生成建议”；实现说明又说“剧本演示数据” |
| 实时问答（引擎） | 输入任意问题，现场判定 | `engine.py` 字符重合检索 + 关键词风险 | README 说“证明规则版能力边界（82% / 88%）” |
| DeepSeek 生成 | 右侧建议卡标“DeepSeek 生成” | 30 条知识全量塞进 prompt，状态由模型自报 | 必答手册 Q48 说“还没有真实大模型、任意问题动态问答” |

这不是“文档没更新”那么简单。它导致**同一个会话，在三种模式下给出三种不同结论**，而你的作品集主线是“AI 知道什么时候该闭嘴”。面试官只要交叉点两次，就会看到矛盾。

### 2.2 我实际点出来的三个反例

我用你的 demo 实际跑了 C1–C4，结果如下：

| 会话 | 剧本设定 | DeepSeek 实际 | 规则引擎 V3 实际 | 问题 |
| --- | --- | --- | --- | --- |
| C1 退款进度 | `ready`，引用退款时效 | `ready`，引用 `售后规则-004`，正常 | `ready`，但 top-1 命中 `物流规则-002`（“怎么查快递”） | 引擎证据错了；LLM 对了，但 LLM 不参与 88% 评测 |
| C2 拆封美妆退货 | `conflict`，两条规则并列 | **`blocked` 高风险拦截** | **`blocked`**（top-1 命中 `商品规则-002` 孕妇规则，high） | “规则冲突”在真实路径里根本没出现 |
| C3 快递停滞 | `no_knowledge` | **`ready`**，引用 `物流规则-003`（该条 risk=high） | **`blocked`** | 最严重：**命中了高风险知识，却给了可发送建议** |
| C4 12315 投诉 | `blocked` | `blocked`，正常 | `blocked`，正常 | 只有这一条是稳定的 |

**C3 是最致命的。** 右侧建议卡写着“可审核”，发送按钮可用，引用的 `物流规则-003` 自己标着 `风险 high`，而风险卡片里没有它，因为风险卡片只扫描客户原话里的关键词（`app.py` 的 `RISK_WORDS`），不扫描命中知识的 `risk_level`。

这直接违背了你自己的产品原则：**高风险必须停下来。** 面试官不需要读代码，点一下 C3 就能看到。

### 2.3 “四态”在真实路径里只剩两态

规则引擎的状态优先级是：

```text
blocked > conflict > no_knowledge > ready
```

而 C2/C3 的 top-1 命中都恰好是 high 风险知识，所以它们都被 `blocked` 截走。结果是：

- 工作台（无 key）：四态齐全，但那是剧本。
- 工作台（有 key）：只有 `ready / blocked`，`conflict` 消失。
- 实时问答（规则引擎）：也只有 `ready / blocked`，`conflict` 极难出现。

你的核心卖点是“四态”，但**真实可交互路径只稳定展示两态**。这就是“怪”的最大来源。

## 3. 七个问题，按优先级

### P0-1 核心承诺没有被真实路径证明

**问题**：你的主张是“在证据不足、规则冲突、高风险时停下来”，但：

- C3 高风险知识 → 仍然 `ready`，可发送；
- C2 规则冲突 → 被高风险优先级截走，看不到 `conflict`；
- C1 退款问题 → 规则引擎引用物流知识，证据链错误；
- 规则冲突的互斥组（`售后规则-001` vs `售后规则-008`）其实不是同一条件下的相反结论：一个是“未拆封 7 天内可退”，一个是“超过 7 天特殊处理”，条件不同，不是真冲突。真正的冲突是 mock-data 里的 K1（七天无理由）vs K2（美妆拆封不退），但引擎的知识库没有 K2。

**怎么改**：

1. **把状态机移出 LLM，放在策略层。** LLM 只负责在 `ready` 状态下写文案，不能决定 `state`。
2. 状态判定顺序建议：
   - 查询风险 + 命中知识 `risk_level`，任一 high → `blocked`；
   - 同一条件下两条规则结论相反 → `conflict`；
   - 检索不到或低于阈值 → `no_knowledge`；
   - 缺订单号/签收时间/商品类目等关键槽位 → `need_info`；
   - 否则 → `ready`。
3. **发送按钮的禁用条件必须和状态机同源**，不能只在 UI 里判断。
4. **LLM 引用校验**：`used_kb_ids` 必须在候选知识里；答案中的每个结论都要能映射到引用条目；校验失败就降级为 `no_knowledge`。
5. C2 的演示要么用真正的“同条件冲突”数据，要么在 DemoConsole 里强制切换；不要依赖真实引擎碰巧命中。

**一句话**：状态机是产品，LLM 只是文案层。现在的代码反过来了。

### P0-2 88% 这个数字，支撑不了你的结论

我复算了 `data/evaluation_results.csv`：

| 版本 | 转人工准确率 | 意图准确率 | 要点命中 | 无依据回答 |
| --- | --- | --- | --- | --- |
| V1 | 40% | 82% | 30% | 0 |
| V2 | 66% | 82% | 48% | 0 |
| V3 | 88% | 82% | 50% | 0 |

V3 混淆矩阵：TP 25、TN 19、FP 1、FN 5；精确率 96.2%，召回率 83.3%。

**问题一：样本太小，且是自建的。** 50 条、30 正 20 负，88%（44/50）的 95% 置信区间大约是 **76%–95%**。它不能叫“准确率”，只能叫“50 条自建离线用例上的规则基线”。如果面试官问“谁标的、怎么抽样、两个人标一致吗”，现在的文档答不上来。

**问题二：`risk` 和 `handoff` 是同一个指标。** 在你的标注里，`expected_risk=high` 和 `expected_handoff=true` 是 30/30 完全重合；在预测里也是 26/26 完全重合。所以“风险判定 88%”和“转人工 88%”是在重复报同一个数，不是两个独立能力。

**问题三：标签把“该转人工”和“高风险”混为一谈。** 看这几条被标成 high risk / handoff=true 的用例：

- “这个怎么样啊”
- “帮我写个小红书文案”
- “你是什么模型”
- “今天天气怎么样”
- “帮我把这段话翻译成英文”

它们不是高风险，它们是**模糊、越界、非业务问题**。把“越界”标成“高风险”，会让风险指标虚高，也会让产品动作变形：越界问题应该礼貌拒绝/引导，不应该走投诉法务队列。

**问题四：引擎有“因错误原因答对”的情况。** 例如：

- “今天天气怎么样” → `blocked`，因为字符重合命中了 `物流规则-003`（high risk）；
- “帮我写一段代码” → `blocked`，因为命中了 `商品规则-002`（孕妇规则，high risk）；
- “这款面膜孕妇可以用吗” → `blocked`，引用的是 `售后规则-009`（仅退款），不是 `商品规则-002`。

这些在“转人工二分类”上算对，但在产品上全是错的。**准确率掩盖了证据错误。**

**问题五：V2→V3 的提升是一条规则的净效果，但里面有水分。** 我对比了 V2 和 V3：13 条变化，12 条改善、1 条回退（“还能便宜点吗”被误拦）。12 条改善里，至少 2 条是“因错误原因转人工”。所以“66%→88%”的故事是真的，但不能只说数字，要展示这 13 条的变化和其中 2 条假阳性。

**怎么改**：

- 把标签从“是否转人工”升级为“**状态 + 原因 + 证据**”：
  - `expected_state`: ready / need_info / no_knowledge / conflict / blocked
  - `expected_reason`: high_risk / out_of_scope / ambiguous / missing_slot / policy_conflict / low_evidence
  - `expected_evidence_ids`: 应该引用哪几条知识
- 报告分状态指标：`ready` 精确率、`blocked` 召回率、`conflict` 召回率、`no_knowledge` 召回率、证据 precision@1、**不安全回答率**（必须为 0）、**过度转人工率**。
- 50 条可以保留，但要分层：每个意图 10 条、高风险 10 条、冲突 5 条、知识不足 5 条、越界/模糊 10 条。再加 10 条对抗用例（越界、提示注入、混合意图、情绪激烈）。
- 至少找一个人一起标，报告分歧和裁决规则。没有第二个人，就明确写“单人标注，未做一致性检验”，不要假装是金标准。
- 规则基线和 LLM 分开评：同一套 50/100 条，分别跑 V3 和 DeepSeek，报两个结果。不要用规则版的 88% 去证明 LLM 的能力。

**一句话**：不是数字不好看，是数字回答不了“AI 会不会在该停的时候停”。

### P0-3 证据链是断的

你的产品主张是“给建议，同时把依据摆出来”。但证据链有三个断点：

1. **检索是字符重合，不是语义。** `engine.py` 的 `score_item` 统计“知识问句+答案里有多少个字出现在 query 里”，阈值只有 2。C1 的退款问题 top-1 是物流规则，C5 的价保问题 top-1 是“超过 7 天还能退吗”，都是这个原因。
2. **知识库有两套。** 工作台剧本用 `mock-data.json` 的 6 条 K1–K6；引擎/评测用 `data/knowledge_base.json` 的 30 条。C5 的价保在 K5 里有，在 30 条里没有，所以 C5 在引擎里只能被错误拦截。面试官看到“知识依据 K3”和“知识依据 售后规则-004”会问：到底哪套是真的？
3. **LLM 没有真正做检索。** `llm.generate_suggestion` 把 30 条知识**全量**塞进 prompt，不是先检索候选；`used_kb_ids` 由模型自报，代码没有校验这些 ID 是否真的存在于候选、答案是否真的被这些条目支持。所以“每句结论都能找到出处”目前是一句 prompt 要求，不是系统保证。

**怎么改**：

- **一套知识库**，工作台、引擎、评测共用；剧本建议也从同一套知识生成，或者明确标注“设计稿数据，不参与评测”。
- **检索先过滤再打分**：按意图/类目过滤，再用 BM25 或 embedding 排序，设阈值，返回 top-k 和分数。哪怕只用关键词 + 类目过滤，C1 也会好很多。
- **证据后验校验**：LLM 输出后，检查 `used_kb_ids` ⊆ 候选集；检查答案中的关键实体/金额/时效是否出现在引用条目里；不通过就降级。
- **风险不能只看客户原话**：命中知识的 `risk_level`、客户标签、订单状态都要进入风险判定。C3 的 bug 就是这样漏掉的。

### P1-1 没有用户与业务证据

这是“像开发项目、不像 PM 作品”的根本原因之一。

你现在的文档里有很多“客服每天要……”“用户会……”的判断，但没有一条来自真实客服。你没有：

- 客服访谈 / 现场观察 / 工单样本；
- 当前流程的基线数据（AHT、转人工率、退款纠纷率、CSAT、一次解决率）；
- 一次错误承诺的成本（赔偿、平台处罚、舆情）；
- 竞品在“证据、置信度、转人工、风控”上怎么做；
- 为什么是“建议”而不是“自动发送”的单位经济账。

**怎么补（7 天内可完成）**：

1. 找 3 个做过电商客服的人（前同事、朋友、社群、脉脉/小红书），每人 30 分钟，问：
   - 最近 5 个难处理的售后会话是什么？为什么难？
   - 不确定规则时你问谁/查哪里？平均花多久？
   - 有没有因为答错/承诺错被投诉或赔钱？后来怎么处理？
   - 你现在用 AI 辅助吗？什么情况下信/不信？
   - 一条 AI 建议，你最想看到什么才敢点发送？
   - 什么情况下你希望系统直接拦住你？
   - 转人工时，你最怕丢什么信息？
2. 把回答整理成 5 条洞察 + 3 条设计影响，引用原话。不要编造用户。
3. 做一页“错误成本”假设模型（下面有模板）。
4. 选 3 个竞品（Zendesk / Intercom Fin / 阿里店小蜜 / 网易七鱼 / 京东咚咚），按 6 个维度做一页矩阵：知识依据、置信度、风控、转人工上下文、自动回复 vs 辅助、评测/分析。

**错误成本模型模板**（数字全部标注“假设”，不要假装真实）：

```text
月售后会话量           10,000
适合 AI 建议的比例       40%  → 4,000
平均通话/处理时长         6 分钟
AI 建议节省             20%  → 1.2 分钟/次 → 80 小时/月
客服小时成本             ¥40  → 节省 ¥3,200/月
错误承诺率（无护栏）      2%   → 80 次/月
单次错误成本             ¥200 → 风险 ¥16,000/月
加护栏后错误率           0.5% → 20 次/月 → 风险 ¥4,000/月
```

这个模型不需要精确，它的作用是让面试官看到：**你不是为了做人机协同而做人机协同，你在算“效率收益 vs 错误成本”。**

### P1-3 状态机 / 数据模型不闭合

这部分是“产品经理的基本功”，也是面试官容易追问的地方。

1. **`state` 和 `lifecycle` 混在一起。** 你的 `lifecycle` 是 `pending → adopted → edited / sent / ignored / handed_off`。但 `edited` 和 `sent` 不是互斥状态：编辑后发送，代码把 lifecycle 设成 `edited`，不是 `sent`；忽略后又标记解决，lifecycle 还是 `ignored`。这不是状态机，是几个布尔值的拼盘。
2. **采纳率被预填草稿污染。** `app.py` 在 `ready` 时直接把建议文本填进输入框；客服不点“采纳”，直接点“发送”，`cb_send` 会因为 `adopted=False` 把结果记成“人工撰写发送”。也就是说：**AI 写的文本，被人原样发出去了，却被统计成人工写的。** 你的采纳率会系统性偏低。
3. **两套知识库、两套评测集。** `mock-data.json` 里有 4 条 `evaluationCases`，`data/evaluation_results.csv` 里有 50 条；`mock-data.json` 的 meta 还引用了不存在的 `CONTEXT.md`。
4. **C5–C7 没有建议。** C5 是价保，C7 是发票，工作台点进去是“暂无建议”，但文档说 C1/C5 有完整建议；C5 在引擎里也没有价保知识，只能被错误拦截。
5. **互斥组不是真冲突。** 前面说过，`售后规则-001` 和 `008` 条件不同，不是同一条件下的相反结论。真正的冲突应该是“7 天无理由”vs“美妆拆封不退”。

**怎么改**：

- 拆成三层：
  - `suggestion_state`: generated / viewed / adopted / ignored / expired
  - `message_state`: draft / edited / sent
  - `conversation_status`: processing / waiting_customer / resolved / handed_off
  - `handoff`: reason / destination / at / context_snapshot
- 事件表：`suggestion_shown`、`suggestion_adopted`、`draft_edited`、`message_sent`（带 `suggestion_id`、`draft_origin`、文本 hash）、`handoff`。这样采纳率、改写率、忽略率、转人工率都能算清楚。
- 一套知识库、一套评测集；删掉 dead data 和失效引用。
- 互斥组用结构化条件（是否拆封、签收天数、类目、质量问题），同一条件不同结论才算冲突。

## 5. 面试官会追问的 7 个问题

1. **“你和几个客服聊过？他们现在怎么处理？最痛的是什么？”**
   现在：没有访谈，只有假设。
   改后：3–5 个访谈 + 5 条洞察 + 原话引用。

2. **“88% 是什么的准确率？50 条怎么来的？谁标的？置信区间多少？”**
   现在：50 条自建，单人标注，88%（95% CI 76–95%），且 risk/handoff 重复计算。
   改后：分层 100 条、两人标注、分状态 P/R、证据 precision、置信区间。

3. **“为什么 C3 的知识是 high risk，AI 还说可审核？你的状态机在哪一层？”**
   现在：LLM 自报 state，策略层没有兜底；这是一个真 bug。
   改后：状态机在策略层，LLM 只写文案；发送门禁同源。

4. **“客服直接发送了 AI 文本，但没点采纳，你的采纳率怎么算？”**
   现在：算成“人工撰写发送”，采纳率被低估。

   现在：标签把 `expected_handoff` 和 `expected_risk=high` 完全绑定。

6. **“为什么不做自动发送？省多少钱？错一次赔多少？”**
   现在：只有定性判断“错承诺很贵”。
   改后：一页错误成本模型 + 敏感性分析 + 竞品做法。

7. **“如果重做，你先做什么？”**
   现在：你其实有很好的答案。
   改后：先说“把状态机移出模型、统一知识库、重做评测”，再说“加 need_info 和知识缺口”，最后说“做 3 个客服访谈”。

## 9. 程序是不是太简陋？它到底有没有用？

先直接回答：**作为软件，它确实是个骨架；作为产品，它还没有证明一个“非它不可”的用处。你的直觉是对的。**

这不是说原型必须做成生产系统。原型可以简陋，但不能“空”。它必须让面试官看到：你理解真实工作流，并且你的设计能改变一个关键决策。现在的问题是，它卡在“概念可交互说明”和“工作原型”之间：既没有生产系统的深度，又没有把概念讲到极致，还用了“88%”“实时问答”“评测概览”这些看起来像产品的包装，于是面试官会用产品的标准来审它，然后得出“用途不大”的结论。

### 9.1 为什么它会让人觉得“用途不大”

1. **它把客服已有的工作台又做了一遍。** 真实客服已经在用店小蜜、七鱼、Zendesk、内部工单系统；你这个三栏工作台是“另一个工作台”。demo 没有回答：客服为什么要切过来？是替代，还是嵌在现有系统里的一个侧边栏/插件/API？如果答案不清晰，功能做得再多也像玩具。
2. **售后最核心的是订单/退款/物流数据，不是话术。** 用户问“退款三天怎么还没到账”，真正要查的是订单状态、支付渠道、退款单号、到账时间；不是一条政策文本。你的 demo 用 system message 把订单信息“写死”在对话里，AI 并没有真的调用订单/退款/物流接口。所以它看起来像一个“会背规则的聊天框”，不是一个“能办事的工作台”。
3. **它没有闭环。** 发送之后呢？客户是否回复？是否解决？是否二次投诉？知识缺口有没有回写？冲突规则谁来裁决？这些都没有。一个客服产品如果没有“解决率、二次投诉率、知识回写”这些闭环，就很难证明有用。
4. **它的“AI”没有做最难的部分。** 字符重合检索、关键词风险、LLM 自报状态——这三件事都不是售后 AI 最难的部分。最难的是：理解客户真实意图、找到正确的那条政策、发现条件冲突、补齐缺失信息、写出每一句都有出处的回复、在不确定时停下来。你的 demo 展示了“停下来”的 UI，但没有展示“怎么知道该停”的能力。
5. **它没有回答“为什么是我”。** 竞品也有知识库、建议、转人工、风控。你的差异化是“证据优先 + 四态闸门 + 知识运营闭环”，但 demo 只展示了第一层，后两层没有产品化。面试官会问：这不就是所有客服 SaaS 都在做的“AI 辅助”吗？
6. **它没有商业角色。** 你面向的“用户”是一线客服，但“买家”是客服组长/运营负责人/合规。客服想要快，组长想要风险可控，知识管理员想要规则可维护，老板想要降本。demo 只给了客服一个建议面板，没有给组长看板、没有给知识管理员缺口队列、没有给老板数字。所以它像一个功能 demo，不像一个产品。

### 9.2 一个原型要有用，至少要过五关

| 关卡 | 现在 | 生产系统需要 | 作品集是否必须 |
| --- | --- | --- | --- |
| 真实任务 | 7 条模拟会话 | 真实工单/对话样本 | 至少 20 条半真实任务 |
| 真实数据 | 写死的 system message | 订单/退款/物流 API | 一个 mock API 就很加分 |
| 可解释 | 引用知识，但检索会错 | 引用 + 校验 + 冲突条件 | 必须 |
| 可度量 | 50 条自测，单一指标 | 分层评测 + 线上指标 | 必须改进 |
| 可嵌入 | 另起一个工作台 | 侧边栏/插件/API/工单集成 | 必须想清楚 |
| 可运营 | 无 | 知识缺口、冲突裁决、版本 | 这是差异化 |
| 可闭环 | 发送即结束 | 解决/回访/二次投诉/回写 | 至少设计出来 |

**作为软件，它还缺**：后端 API、数据库/事件日志、登录与权限、真实数据接入、检索服务、模型调用治理（超时/重试/降级/成本）、评测 harness、日志与监控、PII 与供应商合规、测试。你不需要全做，但要知道自己在第几层。现在是“单文件 Streamlit + JSON + 一个 LLM 调用”的骨架层。

### 9.3 两条路线，别卡在中间

**路线 A：概念原型（Concept Prototype）**

- 定位：用一个可交互的界面，证明“四态闸门”这个设计假设。
- 做法：去掉实时问答、去掉 88%、去掉 LLM 的不确定性；用固定的 4 条剧本 + DemoConsole 强制切态；把“为什么这样设计”讲透。
- 作品集话术：“这是一个概念原型，不是生产系统；我的贡献是状态模型、证据链和转人工设计。”
- 适合：实习；时间紧；想把产品思考讲清楚。

**路线 B：工作原型（Working Prototype）**

- 定位：在一个窄场景里，做出“能办事”的闭环，并用小样本证明有用。
- 做法：只做美妆/个护售后政策咨询；接一个 mock 订单/退款 API；检索政策条款；状态机在策略层；LLM 只写有引用的回复；SQLite 记录事件；20 条任务计时对比；做一个“知识缺口/冲突裁决”小页面。
- 作品集话术：“这是一个窄场景的工作原型；我用 20 条任务验证了时间节省和不安全发送率。”
- 适合：正职；想展示落地能力。

**现在的问题是：它看起来像 B（有评测、有实时 LLM、有 88%），实际是 A（剧本数据、玩具检索、LLM 未评测）。** 这就是“用途不大”的根源。选一条，别在中间。

### 9.4 如果只做一个小而有用的版本

建议把项目缩成：**“美妆/个护售后政策 Copilot”**，只服务一个决策：

> 这笔订单现在能不能退/换/赔？依据是哪条？这句话能不能发给客户？

具体做五件事：

1. **一个场景**：拆封/过敏/超 7 天/退款到账，四类问题；不要做全品类客服。
2. **一个 mock 订单 API**：输入订单号，返回商品类目、签收时间、支付渠道、退款状态；让 AI 真的“查”，而不是 system message 写死。
3. **一个政策检索 + 条件冲突**：按类目/是否拆封/签收天数过滤；同一条件下两条规则结论相反才算冲突；引用原文和版本。
4. **一个策略状态机**：`ready / need_info / no_knowledge / conflict / blocked`；LLM 只在 `ready` 写文案；发送门禁在服务端。
5. **一个小样本验证**：找 20 条真实/半真实会话，计时“人工查规则写回复” vs “AI 建议 + 人工审核”，记录时间、改写率、不安全发送率、转人工率。哪怕只有 20 条，也比 50 条自测 88% 更有说服力。

再加一个“知识运营”小闭环：知识缺口提交 → 组长补规则 → 下次命中。这个闭环会让面试官看到：你做的不是聊天框，是一个可运营的系统。

### 9.5 你不需要为了“显得有用”而加的东西

- 登录页、权限、多客服协作：对证明核心价值帮助很小。
- 数据大屏、动画、移动端：这是客服工作台，不是 C 端产品。
- 更多会话、更多知识条目：数量不解决“检索是否正确”。
- 更复杂的 Agent 框架：先把状态机和证据链做对，再谈框架。

### 9.6 一句话

**原型可以简陋，但不能空。** 把“一个万能工作台”缩成“一个关键决策”，把“7 条假会话”换成“20 条真任务”，把“88% 自测”换成“时间节省 + 不安全发送率”，它就会从“demo”变成“证据”。
