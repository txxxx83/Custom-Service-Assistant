# 电商售后 AI 客服 · 判定层原型

一个「只说有依据的话」的售后客服建议系统：在**信息不足、知识不足、高风险、规则冲突**时，它不给话术，而是给出三种可执行的动作——**追问、转人工、禁止发送**，并写清这一步该由谁接手。

产品主张一句话：**把「不确定」变成可执行的动作，并让商家看得见为什么。**

---

```bash
cd demo
python -m streamlit run app.py
```

## 3. 判定只有一条线

所有判断都在 `policy.py` 的 `decide()` 里，返回一个 `Verdict`。建议卡、发送按钮、转人工原因、审计日志**只读这个对象**，UI 不再自己算——所以不会出现「卡片说不可发、按钮却能点」。

顺序本身就是主张：

```
① 风险词（只看对话：投诉 / 法律 / 舆情 / 人身安全）→ blocked
② 规则冲突（同组两条规则结论相反）              → conflict
③ 查订单（查无此单 / 没有单号）                  → need_info
④ 缺字段（只缺「这次真要用到」的字段）            → need_info
⑤ 知识匹配（有无可引用规则）                      → no_knowledge
⑥ 规则风险（命中 risk_level=high）                → blocked
⑦ 全通过                                        → ready
```

第 1、2 步不依赖订单，所以放在查单之前。否则「规则冲突但订单号打错」会先报信息不足，把冲突藏起来——藏起来的冲突就是下一次赔付。第 6 步是第二道闸：即使检索命中，只要规则本身标了 `high`（例如「显示签收但我没收到」），也不自动作答。

两种「不可发」要分开：`blocked` 是**内容不能发**（风险或高风险规则），`need_info` 是**现在还不能发**（缺字段/缺单号）。前者换个人也不能直接发，后者补齐事实后可以继续。

五种状态与动作：

| 状态 | 系统做什么 | 谁接手 |
| --- | --- | --- |
| ready 可发建议 | 给出带出处的建议 | 客服 |
| need_info 信息不足 | 不给结论，列出「该问客户什么」 | 客服 |
| blocked 高风险拦截 | 禁止生成可发送内容 | 客服组长 |
| no_knowledge 知识不足 | 不说「大概是这样」，登记知识缺口 | 知识库管理员 |
| conflict 规则冲突 | 并列两条原文，勾选确认后才可发 | 客服，升级组长 |

`can_send` / `requires_ack` / `handoff_reason` 都是 `Verdict` 的派生属性，只有一处定义。

## 5. 这个原型证明了什么 / 没证明什么

**证明了**

- 判定可以只有一条线：7 个会话实测，卡片「不可发」与按钮禁用 0 例外；15 条用例全过。
- 「不知道」可以是一个具体动作：C1 输出的是「缺退款单号，需核对是否落库或引导重新提交」，而不是「正在为您查询」。
- 同一个诉求下，选错退货原因的钱是会算出来的：¥0 / ¥12 / ¥24，且只有一种计品退率。
- 最值钱的一条不是「AI 会答」，是「AI 拦住了人已经说出口的承诺」：C6 的客服说了「在仓库处理中」，但换货单没落库；C5 的客服说了「可以补」，但这单没有活动标记。系统在这两句发出去之前把它们变成 `need_info`。

**没证明**

- 没有真实订单接口，也没有真实客服用过它；没有数据证明它降低了赔付。
- 5 人可理解性走查、真实访谈都没做（我没有可访谈的客服/商家）。
- 规则冲突是「演示态」：两条互斥规则由我手工构造，真实样本 0 条。
- 只锁美妆个护一个类目，生鲜（无花果）、百货（保温杯）的证据只用于归纳共性问题。
- 转人工只做了一半：带了原因和上下文，没做交接之后的回传。

评测口径（`data/evaluation_results.csv`，50 条用例 × 3 版本，规则基线离线跑，非估算）：

| 版本 | 意图识别 | 转人工判定 | 风险判定 | 要点命中 | 无依据回答 |
| --- | --- | --- | --- | --- | --- |
| V1 | 41/50 = 82% | 20/50 = 40% | 20/50 = 40% | 15/50 = 30% | 50/50 = 100% |
| V2 | 41/50 = 82% | 33/50 = 66% | 33/50 = 66% | 24/50 = 48% | 0/50 = 0% |
| V3 | 41/50 = 82% | 44/50 = 88% | 44/50 = 88% | 25/50 = 50% | 0/50 = 0% |

**82% 是意图识别，88% 是 V3 的转人工判定**，都不是「AI 准确率」，也都不是五态判定层的成绩——跑的是 `engine.py`，与 `policy.py` 不是同一个系统，不要混着讲。

这张表最有说服力的一点：**意图识别三版都是 82%，一行没改**，而无依据回答从 100% 降到 0。说明收益来自依据要求与发送门禁，不是来自更强的识别或生成。

## 6. DeepSeek key（可选）

不配 key 也能跑：判定层与话术模板都是本地的，key 只影响「ready 状态下的措辞是否由模型改写」。

- 本地：`demo/.streamlit/secrets.toml`

  ```toml
  [deepseek]
  api_key = "sk-..."
  model = "deepseek-chat"
  ```

  该文件在 `.gitignore` 里，不会进 Git；仓库只留 `secrets.toml.example`。
- 也可以设环境变量 `DEEPSEEK_API_KEY`（优先级更高）。
- 部署到 Streamlit Cloud：App settings → Secrets，粘贴同样两行。
- **模型不参与工作台的判定**：`get_suggestion()` 只在 `ready` 时请它改写措辞，`state` 仍以 `policy.decide()` 为准。`?dev=1` 的「实时问答」页是另一条对照线——那里直接展示模型自报的 state，用来和规则引擎比，不代表工作台的门禁。

## 8. 90 秒演示脚本

1. **工作台 → C1**：右侧写「信息不足 · 缺退款单号」，发送禁用。「它没答，是因为查了字段发现退款单根本没生成。」
2. **C3**：同样一套卡片，这次给建议且可发——回答用订单里的运单尾号 **8873** 和停留天数，最后问「需要我现在提交催件登记吗」，不假装已经登记完。**这里有个值得多讲十秒的细节**：客户说「五天没动」，话术写的是 **4 天**——天数由「会话末条消息时间 − `lastNodeAt`」算出，不抄客户原话；判定步骤里专门有一条「核对客户口径」写明两个数字的差异。「会停」不是无能，**连客户自己说的数字都要核对**才是这套东西的立身之本。
3. **C4**：高风险，按钮禁用，归属客服组长。
4. **C6**：客服上一句已经说了「在仓库处理中」，系统仍判信息不足——因为换货单没落库。这一屏讲的是「拦住人已经说出口的承诺」，不是「AI 不会答」。
5. **C5**：客服已经说了「可以补」，系统要求先核对活动标记（秒杀/券叠加不适用）。同样是拦承诺。
6. **退货原因**：三个原因并排，品质退货点不动，`¥0 / ¥12 / ¥24` 一句话说完。
7. （可选 `?dev=1`）实时问答输入「你们能开发票吗」→ 知识不足，不是硬答。
