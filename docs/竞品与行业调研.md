# 竞品与行业调研 · 电商售后 AI 客服「判定层」原型

> 调研时间：2026-11 ｜ 调研人：产品经理初学者（一人项目，无团队）
> 配套阅读：`README.md`、`docs/产品经理带教手册.md` 第 1、8、13 章
> 纪律：本项目所有数字只来自 `docs/FACTS-事实基线.md`（2026-11-12 核对版）；每条外部事实标注 [编号]，来源清单见第 10 节；查不到的写"公开资料未披露"；没有来源的判断标"作者推测/作者判断"。

## 1. 调研目的与靶心问题

先说清楚这份调研**不是**什么：不是"AI 客服行业全景报告"，不是给投资人看的市场规模分析，更不是抄一份竞品功能列表。它只服务一个决策——

> **验证"事前判定门禁"是不是一个真空位，从而决定这个作品集项目的差异化叙事怎么讲。**

本项目的核心主张（FACTS.md 第二节）：售后客服真正的成本不在"答得慢"，而在"答得没依据"。原型不做"更快地生成回答"，做的是**在回答发出前判定这句话能不能发**——该追问就追问（need_info），该说不知道就说不知道（no_knowledge），该转人工就转人工（blocked/conflict）。最值钱的洞察是 C6：客服已经说出口"换货在仓库处理中"，但换货单没落库，判定层把这句必然失信的承诺拦成 need_info。

所以整份调研围绕一个靶心问题展开：

> **这些真实存在的电商客服 AI 产品，在"回答发出之前"有没有判定门禁？还是只做"生成 + 事后质检"？**

围绕靶心，每个竞品拆五个子问题：
1. 它自动发送回复吗，还是只给人工坐席提建议？
2. 发送前有没有验证/拦截/置信度门槛？官方文档写没写？
3. 回答的知识来源是什么？给不给出处？
4. 转人工在什么条件下触发？高风险场景（投诉、退款、人身安全）怎么处理？
5. 公开效果数据是什么口径？谁测的？

初学者常犯的错：调研前没有问题，调研后只有功能清单。功能清单谁都能抄，**带着一个可以被证伪的问题去查，查完敢修正自己的假设**，这才是调研。本次调研确实修正了假设——见第 7 节，"真空位"这个说法不成立，成立的是一个更窄、更诚实的空位。

**本次调研的三个关键发现（先给结论，证据在后文）**：
1. "发送前门禁"不是无人区：Fin 与 Sierra 的官方文档明确写了事前验证/确定性护栏 [16][18]。
2. 国内电商平台工具的公开文档以"知识库 + 转人工 + 事后修正/质检"为主流，发送前门禁机制未披露 [7][9][12]。
3. 本项目能讲的差异化是三个更窄的角度（拦人类承诺 / 订单事实判定 / 单一 Verdict 契约），且全部标注为作者判断——详见第 7 节。

## 2. 调研方法与来源可信度分级

**方法**：WebSearch 检索 + WebFetch 抓取原文，优先官方文档/官网/政府法规文本，媒体报道只作补充与交叉验证。调研时间 2026-11，检索时刻意使用当前年份。**未实测任何竞品**（无账号、无试用），所有功能描述均来自公开资料。

**来源分级**（每条来源在清单中标注级别）：

| 级别 | 定义 | 本次例子 | 使用纪律 |
| --- | --- | --- | --- |
| A | 官方文档、官网产品页、政府网站法规文本 | 飞鸽机器人操作白皮书 [9]、Fin AI Engine 页 [16]、抖店体验分规则 [27][28]、《七日无理由退货暂行办法》[32] | A 级只代表"官方说了"，**不代表数据真实**——官网上的解决率、"0 风险 case"仍是厂商自报口径 |
| B | 媒体报道、官方渠道转载的厂商稿、云厂商客户案例 | 网经社京小智报道 [8]、AWS 智齿案例 [14]、新浪财经 Gap 事件 [23] | 转述官方发布时可用，但效果数字必须保留"厂商自报/内测"口径 |
| C | 百科、社区讨论、自媒体、投资者笔记 | 百度百科店小蜜词条 [4]、雪球版本分析 [5]、知乎专栏 [34] | 只用于线索与旁证，关键功能不单独依赖 C 级 |

**三个必须交代的访问限制**：
1. 京东帮助中心 [7] 与抖店学习中心 [9][10][11][27][28] 是 JS 渲染页面，直接抓取只返回脚本壳，正文经搜索引擎快照核对（2026-11 访问）。快照可能滞后于页面当前版本，引用时按快照内容表述。
2. 中文互联网上大量"选型指南/榜单"是厂商软文（本次检索中反复出现），一律降为 C 级或不采用；本文不引用任何榜单排名。
3. **AI 摘要工具会编造功能名**。本次调研中，某摘要工具两次声称 Zendesk 七月更新博客 [35] 介绍了名为"VeriDraft/Ticket Done"的功能，逐字核对原文后发现这些名字不存在，相关引文实际属于第三方应用介绍。该证据已整体弃用，Zendesk 部分改用官方产品页 [20]。教训写进第 9 节。

**样本**：国内 5 家（AI 店小蜜、京小智、飞鸽、网易七鱼、智齿科技）+ 海外 3 家（Intercom Fin、Sierra、Zendesk AI），Decagon 作为补充证据出现在趋势与空位判断中。拼多多客服工具、Udesk、美洽未纳入：本次未检索到足够回答靶心问题的公开文档（公开资料未披露，不代表没有）。

**检索策略（可复现）**：本次检索按四组词展开，均带当前年份（2026）：
1. 产品词：`产品名 + 官方文档 / 使用说明 / 白皮书`——先找 A 级原文，如飞鸽白皮书 [9]、京东帮助中心 [7]。
2. 机制词：`产品名 + guardrails / validate / 风控 / 拦截 / 幻觉`——专查靶心问题，Fin Validate [16] 与 Sierra 护栏原文 [18] 都来自这组。
3. 规则词：`平台名 + 品退率 / 品质退货率 / 体验分 / 纠纷率 + 规则`——找平台考核口径 [27][28][29][30][31]。
4. 事故词：`AI 客服 + 乱承诺 / 赔偿 / 越狱 / 判例`——找真实损失证据 [23][24][25][26]。

**记录纪律**：每条被采用的来源记录 URL + 访问日期 + 级别；被弃用的来源（如 [35]）也保留在清单里并注明弃用原因——弃用记录本身就是方法论证据。

## 4. 逐个竞品短评

### 4.1 AI 店小蜜（淘宝/天猫）

- **它解决什么**：2026-05-11 发布，官方定位"电商行业首个具备售前到售后办事能力的客服 Agent"，全链路基于千问大模型，售后能自动办退差价、退定金、改地址、订单排障，打通平台系统与第三方服务商接口 [1][2]。
- **边界在哪**：只服务淘系；公开材料讲的都是转化与效率（转人工率降 45% 等，厂商自报 [2][3]），**发送前如何判定"这句话能不能说"未披露**。
- **证据薄弱处**：百科提到 Critic 模型评估回答质量，但执行时机不明，且百科是 C 级来源 [4]。
- **值得借鉴**："售后从回答规则延伸到办理业务"的方向——本项目 A 场景把"选错退货原因谁付钱"算出来，正是同一问题意识。
- **必须回避**：拿厂商转化数据当行业事实引用；默认"大厂没写 = 大厂没有"。

### 4.2 京小智（京东）

- **它解决什么**：官方免费机器人解决中小商家接待压力，平台预置 219 条通用问答 + 61 个品类知识库，全自动/智能辅助双模式，诊断分析每天自动归纳并调整 top 问题答案 [7]。
- **新动向**：2025-12 上线"电商客服思维链"，快慢思考双模式，把 AI 思考过程可视化，内测转化率 +3.27%、转人工率 -4.39%（厂商内测口径）[8]。
- **边界在哪**：思维链解决的是"让人看见 AI 怎么想"，**不是"在发出前拦住不该说的"**（作者判断）；诊断分析是事后优化。
- **值得借鉴**："可解释"作为信任卖点的思路——本项目 Verdict.steps 渲染真实判定步骤与之同向。
- **必须回避**：把"过程可见"偷换成"发送前门禁"，两者不是一回事，面试被追问会露馅。

### 4.3 飞鸽机器人（抖音电商）

- **它解决什么**：抖店官方 IM 客服，知识库（含美妆知识包）+ 场景解决方案按订单节点配话术，全自动/智能辅助双模式，辅助模式回复计入响应指标 [9][10]。
- **边界在哪（直接证据）**：白皮书原文要求商家"确保学习信息的真实、准确和有效性，**如发现机器人回复的买家信息不准确的，请及时向买家补充回复**"[9]——这是白纸黑字的"事后修正"模型。
- **边界在哪（厂商宣称）**：客服 Agent·飞鸽版（火山引擎）宣称"三层风控体系、0 风险 case"，但三层是什么未披露，无法核验 [11]。
- **值得借鉴**："按订单状态节点组织话术"，与本项目"订单即数据"同构；美妆知识包的存在也说明本项目的类目选择有真实行业对应物。
- **必须回避**：把营销话术当机制证据——"0 风险 case"引用时必须标注口径。

### 4.4 网易七鱼

- **它解决什么**：全渠道客服 SaaS，官网宣称文本机器人"独立解决 80% 常见问题"，有退款/退差价智能体，全量智能质检准确率宣称 95% 以上 [12]。
- **幻觉控制路线**："知识库 + QA 索引 + 知识路由 + 大小模型结合"，从源头减少知识缺失导致的幻觉 [13]。
- **边界在哪**：公开材料中质检是**事后全量**的，发送前判定门禁未披露；幻觉控制主要约束"生成依据"，不是"发送许可"（作者判断）。
- **值得借鉴**："知识缺口要回流知识库"的闭环意识——本项目 no_knowledge 态登记缺口给知识库管理员正是这个动作。
- **必须回避**：把"质检准确率 95%"误读成"回答准确率 95%"，两者口径完全不同，这是初学者最容易踩的数字陷阱。

### 4.5 智齿科技

- **它解决什么**：基于 LLM 的客服 Agent，AWS 客户案例显示其用 RAG 把回复限定在私域知识范围内，支持企业自定义召回阈值，机器人可主动发起转人工且路由可自定义 [14]。
- **边界在哪**：自报第一轮答复准确率超 87%、人工介入降 42%、幻觉概率较上一代降约 90%——注意这是**厂商对比测试**，不是第三方审计 [14]。
- **机制定位**：召回阈值是检索层控制，发生在生成之前，但不是"这句话能不能发"的完整判定（作者判断）。
- **值得借鉴**："阈值交给企业按业务自定义"——本项目 risk_level 与 FIELD_TRIGGERS 也是把控制权交给规则配置者。
- **必须回避**：把"幻觉降 90%"当成"不会乱承诺"的证明，剩下 10% 落在退款承诺上就是真金白银。

### 4.6 Intercom Fin

- **它解决什么**：按结果计费的 AI 客服 Agent，$0.99/结果，"resolution"定义为 Fin 最后一次回答后客户未再求助 [17]；Fin Tasks 能执行付款、退款等操作 [15]。
- **边界在哪（门禁证据）**：**它是本次调研中发送前门禁证据最强的竞品**——官方 Fin AI Engine 页明确流程为 Refine→Retrieve→Rerank→Generate→Validate→Optimize，Validate 在回复前校验准确性与安全性，无法有把握回答时诚实升级人工 [16]。
- **边界在哪（未披露项）**：门禁细节（阈值、规则形态）未披露；官网解决率 76% 为厂商自报 [15]。
- **值得借鉴**："escalates honestly when it can't"——把"承认不知道"做成产品承诺，与本项目 no_knowledge 态完全同向。
- **必须回避**：声称"国外也没人做发送前判定"，Fin 官方文档直接证伪这句话。

### 4.7 Sierra

- **它解决什么**：企业级 Agent 平台，官网主张"设目标引导 Agent、设护栏确保其符合政策"[19]。
- **最接近本项目主张的原文**：官方博客写道，换货政策若规定 30 天窗口，"an agent should never be able to process an exchange if a customer's purchase falls outside that range"——确定性规则在动作前强制执行，另有监督 Agent 审查事实性与滥用 [18]。
- **边界在哪**：2025-12 Gap 官网的 Sierra 机器人被恶意用户越狱，输出成人用品与纳粹相关不当内容，Sierra 致歉并归因"配置错误 + 恶意诱导"[23]——**有护栏不等于护栏不可绕过**。
- **值得借鉴**："确定性规则管动作、模型管理解"的分层，与本项目"判定不交给模型"同构。
- **必须回避**：把 Sierra 的护栏神化，Gap 事件是面试里必须主动提的反例。

### 4.8 Zendesk AI

- **它解决什么**：Resolution Platform 中的 AI agents，自动识别意图并回复邮件等渠道咨询，官方主张"Ground every agent in your business context"、内置控制与测试（"Set policies, review behavior"）、需要时交接人工并智能路由，内置 QA 评估每次交互 [20]。
- **边界在哪**：官方给了"治理/策略/测试"的框架性声明，但**发送前判定的具体流程未披露**；官网客户数据（自动化率 66%/80%、月省 $14k）为客户自报 [20]。
- **证据纪律**：本次调研曾在其七月更新博客的 AI 摘要中读到疑似功能名，核对原文后弃用（见第 9 节），本文不引用该博客作功能证据 [35]。
- **值得借鉴**："QA 与治理作为平台一等公民"的产品化表达。
- **必须回避**：把厂商框架性宣传（govern/control）直接当成"有发送前门禁"的证据——声明与机制之间还差一层文档。

## 5. 行业现状与趋势

每条都带来源；判断性内容标"作者判断"。

1. **从"问答"到"办事"，自动化边界在扩张，错误代价在升级。**
   - AI 店小蜜售后自动办退差价/退定金/改地址 [1][2]；Fin Tasks 处理付款与退款 [15]。
   - Sierra Agent 可执行换货并受 30 天窗口约束 [18]；Decagon 与 Stripe 集成后处理订阅取消与退款工作流 [22]。
   - 作者判断：当 AI 从"说错话"进化到"做错事"，发送前/动作前判定的价值随之上升——这正是本项目主张的行业背景。
2. **AI 乱承诺已有真实损失与判例，企业必须为 AI 的话负责。**
   - 加拿大航空聊天机器人谎称丧亲票价可购票后 90 天内申请退款，2024 年被 BC 省民事解决法庭判赔约 812 加元，"聊天机器人是独立法律实体"的抗辩被驳回（案号 2024 BCCRT 149）[25][26]。
   - 2026-02 快科技报道英国一小型电商的 AI 客服擅自承诺 80% 折扣（订单超 8000 英镑），损失数千英镑、顾客威胁诉讼 [24]。
   - 2025-12 Gap 官网 Sierra 机器人被越狱输出不当内容，Sierra 致歉 [23]。
   - 作者判断：三个案例分别对应"幻觉承诺""越权折扣""护栏被绕过"，正好覆盖本项目 need_info/blocked/conflict 想拦的三类风险。
3. **"可解释/信任"成为明确卖点。**
   - 京小智思维链把思考过程可视化；报道援引行业数据称 AI 客服渗透率已超 75%，但 73% 用户担忧机器人无法准确理解需求、50% 质疑信息准确性与可执行性 [8]。
   - Fin 以专利 AI Engine 的 Validate 阶段作为信任叙事 [16]；Sierra 用监督 Agent 审查主 Agent [18]；Decagon 主打全链路可观测 [21]。
   - 作者判断：行业在补"信任"这一课，但各家补法不同——有的补"看得见"，有的补"拦得住"，本项目属于后者。
4. **质检与护栏已是标配，但重心分"事后"与"事前"两派。**
   - 事后派：飞鸽白皮书要求商家发现错误后补充回复 [9]；京东官方机器人靠每日诊断分析调答案 [7]；七鱼全量智能质检 [12]；Zendesk 内置 QA [20]；Decagon Always-on QA [21]。
   - 事前派：Fin Validate [16]；Sierra 确定性护栏 [18]；智齿召回阈值（生成前检索控制）[14]。
   - 作者判断：国内电商平台的公开文档以"知识库 + 转人工 + 事后修正"为主流，发送前判定门禁未披露；海外头部已把事前验证写进官方架构文档。
5. **平台把"售后原因怎么选"写进了流量考核，且各平台口径不同。**
   - 抖音商品品质退货率取**首次**申请售后原因，"4 看 2 不看"，不看售后结果 [28]。
   - 淘宝真实体验分 2026-03-05 起把宝贝质量指标从"首次品退率 + 商品差评率"改为"商品负反馈率 + 商品好评率"[30]。
   - 微信小店"最终品质退款率"却取**最终**申请原因，用户改为非品质原因则不计入 [31]。
   - 作者判断：原因选择直接关联商家流量与成本，客服有动机替客户"选个省事的原因"，这与本项目 A 场景（品质退货多掏 ¥24 且计品退率，¥12 为假设运费）的问题意识一致；规则因平台而异且会改版，判定层必须引用可溯源的政策原文而非焊死话术。

## 6. 平台规则约束（美妆个护）

### 6.1 七天无理由与拆封规则（法规层面，可核实）

《网络购买商品七日无理由退货暂行办法》（工商总局令第 90 号，政府网站转载全文 [32]）：
- 第六条：四类商品不适用（定作、鲜活易腐、已拆封的数字化商品、交付的报纸期刊）。
- 第七条：三类商品**经消费者购买时确认**可不适用，其（一）即"拆封后易影响人身安全或者生命健康的商品，或者拆封后易导致商品品质发生改变的商品"——美妆个护的拆封争议主要落在这一条。
- 第八条：商品完好标准；**基于查验需要打开包装不影响完好**。
- 第九条：超出查验需要使用导致价值贬损较大视为不完好，其（一）明确"食品（含保健食品）、**化妆品**、医疗器械、计生用品：必要的一次性密封包装被损坏"。
- 中消协 2026-08 消费提示（北京日报转载 [33]）：拆封≠不能退；七日自签收**次日**起算；商家不得擅自扩大排除范围。

条文到本项目字段的映射（实现见 FACTS.md 第八节）：
- 第七条/第九条（拆封与完好性）→ 订单字段 `afterSale.opened / used` → 决定七天无理由是否适用。
- 七日窗口起算（签收次日 [33]）→ 订单字段 `deliveredAt` → 计算是否仍在窗口内。
- 第五条鼓励商家作出更有利于消费者的承诺 → 店铺政策可以严于或宽于法规 → policyHooks 引用 K1–K6 原文，conflict 态检测规则互斥。**判定必须引用店铺自己的政策原文，不能只背法规。**

### 6.2 品退率与纠纷率考核（平台层面，部分可核实）

- **抖音**（官方规则 [27][28]）：商品品质退货率 = 近 30 天物流签收订单中因商品品质原因售后的订单数 / 近 30 天物流签收订单数；**取首次申请售后原因**；考核售后类型含发货后仅退款、退货退款、**换货**、维修、补寄；不论消费者撤销还是商家拒绝/同意，仍计入；不看售后发起人/处理人，不看售后结果。体验分另含"消费者升级求助平台"口径（有售后仲裁，或咨询商家人工后就同一诉求咨询平台/投诉的订单）[27]。
- **淘宝/天猫**（官方商家社区运营手册 [29][30]）：旧口径"首次品退率"同样按买家首次选择的退款原因统计，后续修改/撤销不影响计入，**换货/维修不计入**；2026-03-05 起升级为"商品负反馈率"（近 30 天物流签收订单中发起退款且首次原因为品质相关、或描述相符被评 1-2 星的订单占比）+商品好评率。
- **微信小店**（官方规则 [31]）：最终品质退款率按**最终**申请原因统计，用户修改为非品质原因则不计入——与抖音/淘宝的"首次口径"相反。
- **未核实项**：各平台纠纷率的具体阈值、处罚档位、美妆类目专属细则，本次未找到完整公开文本，标注**未核实**；不编造数字。

三平台口径速查（细节与来源见上方各条）：

| 平台 | 指标 | 取首次还是最终原因 | 换货是否计入 | 备注 | 来源 |
| --- | --- | --- | --- | --- | --- |
| 抖音 | 商品品质退货率 | 首次 | 计入 | 撤销/拒绝仍计入；不看售后结果 | [27][28] |
| 淘宝/天猫 | 首次品退率（旧）→ 商品负反馈率（2026-03-05 起） | 首次 | 旧口径换货/维修不计入 | 新口径含描述相符 1-2 星差评 | [29][30] |
| 微信小店 | 最终品质退款率 | 最终 | 公开文本未明确（未核实） | 改为非品质原因则不计入 | [31] |

作者判断：三个平台对"同一笔品质退货"计不计入的口径都不同（首次 vs 最终、换货计不计），这直接论证了本项目"规则必须可配置、可引用、可检测冲突"的设计——把任何一个平台的口径焊死进话术，换个平台就是乱承诺。

### 6.3 必须分清：K1–K6 不是平台规则

本项目 `mock-data.json` 里的 K1–K6 是**作者自拟的模拟店铺政策**，供订单 policyHooks 引用，不是任何平台的官方规则。A 场景中"品质退货计品退率、无理由退货不计"的**相对关系**与上述公开平台规则方向一致 [28][29]，但具体条文是模拟的，¥12 运费是假设值（ASSUMED_SHIPPING=12），¥0/¥12/¥24 的绝对金额没有真实账单支撑（FACTS.md 第九节）。面试必须主动说这句话，等人问出来就被动了。

## 7. 空位判断（最重要的一节）

### 7.1 直接回答：不是"无人做过"的真空位

靶心问题的答案分两半：
- **海外头部已经做了，而且写在官方文档里。** Fin AI Engine 的 Validate 阶段在回复前校验准确性/安全性 [16]；Sierra 用确定性规则在动作前强制执行企业政策（30 天换货窗口原文）[18]；Zendesk 宣称内置控制与策略治理 [20]；Decagon 的护栏由代码层强制执行 [21]。"事前判定门禁"作为机制**已被验证、已被商品化**。
- **国内电商平台的公开资料里，主流仍是"生成+转人工+事后修正/质检"。** 飞鸽白皮书的"发现不准确请及时补充回复"[9]、京东官方机器人的每日诊断分析 [7]、七鱼的事后全量质检 [12] 都是直接证据。店小蜜的 Critic 模型时机未披露 [4]，飞鸽 Agent 版"三层风控"细节未披露 [11]——**未披露，不能断言没有**。

### 7.2 更精确的空位表述（作者判断，基于本次 8+1 家样本）

本项目真正的差异化不在"发明门禁"，而在三个更窄的角度：
1. **门禁对象**：竞品的门禁管"AI 自己的输出"[16][18]；本项目管"人+AI 的全部待发送内容"，包括拦住客服已经说出口、但订单事实兑现不了的承诺（C6 换货单未落库、C5 无活动标记）。本次样本中未见以"拦人类承诺"为明确目标的公开产品（作者判断，受样本限制）。
2. **判定依据**：竞品的不确定性处理主要靠检索置信度/召回阈值 [14][16]；本项目靠**订单事实字段**——退款单号为 null 就判 need_info，与话术写得多好无关。"不知道"被拆成五种状态、各配动作与归属人（客服/组长/知识库管理员）。
3. **工程契约**：单一 `decide()→Verdict` 驱动建议卡、发送按钮、转人工原因、审计日志，conflict 态必须勾选确认才解锁发送，steps 渲染真实执行路径。公开文档中未见等价的状态机契约披露（未披露≠没有）。

### 7.3 判断的不确定性（面试必须主动讲）

1. **未披露≠不存在**：国内平台内部很可能有风控/拦截层，只是不写进商家文档。本结论只对"公开证据"负责。
2. **官方声明≠实际行为**：Sierra 有确定性护栏仍发生 Gap 越狱 [18][23]；飞鸽 Agent 版"0 风险 case"是无法核验的厂商宣称 [11]。护栏的存在与护栏的有效性是两件事。
3. **访问与样本限制**：JS 页面靠搜索快照、未实测任何产品、样本仅 8+1 家、中文软文噪声大。结论保质期短——店小蜜 2025-09 到 2026-05 两次大升级 [4][1]，投递前建议复查关键页面。
4. **效果数据全是厂商口径**：本文引用的 76%、87%、45% 等数字无一经过独立审计，只能用于"厂商如何叙事"，不能用于"行业实际水平"。

### 7.4 对求职叙事的含义

不要说"我发现了行业空白"（会被 Fin/Sierra 的官方文档当场证伪）。要说：

> **"发送前门禁的价值已被海外头部验证；国内电商售后场景的公开产品仍以事后质检为主。我把这个机制做成可复现、可审计的方法论原型，并补了两个角度：拦住人已经说出口的承诺，以及用订单事实而非检索置信度做判定。"**（作者判断）

### 7.5 投递前复查清单（结论保质期管理）

本次结论基于 2026-11 的公开快照，以下页面变动会直接影响第 7 节结论，投递简历前建议逐一复查：
1. Fin AI Engine 页 [16]：Validate 阶段描述是否变化——它是"海外已做事前门禁"的最强证据。
2. Sierra 博客与官网 [18][19]：护栏叙事是否更新，Gap 事件后是否有新声明。
3. 飞鸽白皮书与 Agent 版介绍 [9][11]："三层风控"是否披露细节——若披露，国内"未披露"结论要改写。
4. AI 店小蜜发布稿与百科 [1][4]：Critic 模型执行时机是否明确——同上。
5. 淘宝体验分规则 [30]：2026-03-05 改版后是否再有调整——第 6 节口径表随之更新。

复查动作本身也是面试素材：它证明你知道"调研结论有保质期"，而不是把一次检索当永久事实。

## 8. 本项目的差异化定位与不做什么

定位一句话：这是一个**方法论原型**，不是竞品替代。它证明"判定可以只有一条线、不确定可以变成可执行动作"，不证明"比店小蜜/Fin 更好"。

数据规模（FACTS.md）：31 条知识规则（售后 14/商品 9/物流 8）、7 张模拟订单、7 条工作台会话、15 条判定用例全过；7 条会话实测 1 可发/3 信息不足/2 高风险拦截/1 知识不足。

**三条差异化**：
1. **拦人不只是拦 AI**：C6 客服已说"在仓库处理中"但换货单没落库、C5 已说"可以补"但订单无活动标记，系统在这两句兑现之前判成 need_info。竞品门禁的公开叙事都围绕 AI 自身输出 [16][18]。
2. **订单事实驱动的五态门禁**：七步判定（识别意图→对话风险词→规则互斥冲突→查订单→本轮缺失字段→知识匹配→规则风险等级），五态 ready/need_info/conflict/no_knowledge/blocked（另有 error 兜底），每态绑定动作与归属人；conflict 需勾选确认才可发。判定依据是字段级事实，不是置信度分数。
3. **可复现、可审计、模型不越权**：建议卡/按钮/转人工/审计只读同一个 Verdict；模型只改写 ready 态措辞，调用失败静默回退本地文案，判定不变。外加 A 场景代价模型（¥0/¥12/¥24，¥12 为假设值）把"选错退货原因谁付钱"算给商家看。

**三条明确不做**：
1. **不做生产系统/竞品替代**：无真实订单接口、无持久化（审计刷新即丢）、无登录权限、无多坐席并发；不接平台 API 自动回复。
2. **不做跨类目与"真实规则库"宣称**：只锁美妆个护，跨类目未验证；31 条规则是人工整理的，不是真实工单聚类；规则冲突是手工构造的演示样本，真实样本 0 条。
3. **不做准确率/ROI 营销**：评测页 88% 是**规则引擎（无模型）的历史基线口径**，与当前五态判定不是同一系统，绝不能说成"AI 准确率 88%"或"上线后提升 88%"；15 条用例全过是验收通过率不是准确率；无真实用户、无赔付下降数据；度量体系（北极星"无依据发送率"等）是建议口径，尚未上线验证。

## 9. 对初学者的方法论小结

竞品调研怎么做才不是抄功能列表？五条可迁移方法，每条配一个能照做的动作。

1. **先写一个能被证伪的靶心问题，再设计表格列。** 本次的靶心是"发送前有没有门禁"，所以矩阵里"发送前门禁"是独立一列，而不是塞进"功能特色"。动作：调研前用一句话写下你要服务的决策，然后问自己"查到什么结果会让我改变结论"——本次查到 Fin Validate [16] 就推翻了"真空位"假设，这是调研成功的标志，不是失败。
2. **每条功能区分"官方写了的"和"我推测的"，查不到就写未披露。** 动作：给每个竞品建三栏笔记——原文引句（带 URL）/ 我的推断 / 未披露项。本文矩阵里"未披露"出现十余次，这些空格本身就是结论：国内平台不公开门禁机制，与海外形成对照。
3. **怎么查一个产品有没有某个功能（具体查法）**：
   - 读官方文档的**设置章节**：飞鸽白皮书的"接待模式/机器人大脑/应急关键词/转人工"[9]、京东帮助中心的"启用设置/问答管理/诊断分析"[7]——门禁若存在，最可能写在"机器人设置"或"转人工"附近。
   - 看**更新日志/发布节点**：京小智 5.0→思维链的时间线靠媒体报道官方发布还原 [8]；Zendesk 按月发更新博客 [35]。新功能（如护栏、验证）通常首发于 changelog 而非产品主页。
   - 看**定价页的功能分层**：Fin 定价页把"resolution"定义写进计费口径 [17]，店小蜜分标准版/高阶版 [5]——厂商把什么能力放进高价档，什么能力就是它真正的卖点；门禁若值钱，会出现在分层里。
   - 看**开发者文档的 API 字段**：搜 send/reply 接口的请求参数里有没有 confidence、approved、review 之类字段，字段是比宣传页更硬的证据。本次未逐一核验各家 API（诚实标注），这是下一步可做的动作；本项目 Verdict 的 can_send/requires_ack/handoff_reason 就是这类契约字段。
4. **主动找反例，警惕确认偏误。** 动作：对每个竞品额外搜一轮"产品名 + guardrails/validate/风控/拦截"。本次正是这轮搜索找到了 Fin Validate 与 Sierra 30 天窗口原文，避免了把作品集建立在"别人都没做"的幻觉上。同时给厂商宣称降权：Sierra 有护栏仍出 Gap 事件 [23]，"0 风险 case"无法核验 [11]。找到的反例要写进文档（如第 7.3 节），不要藏起来——藏反例的调研经不起追问。
5. **用 AI 工具读网页时，引文必须回溯原文，功能名必须逐字核对。** 本次真实事故：摘要工具两次给出 Zendesk 博客的功能名"VeriDraft/Ticket Done"，逐字核对后发现原文根本没有这些名字，引文属于第三方应用介绍 [35]，证据整体弃用。动作：凡要写进文档的功能名/数字，至少用两种独立方式确认（原文抓取+搜索快照，或两个不同来源）；确认不了就只引原句、不写功能名，或干脆不用。另外，JS 渲染页面（京东帮助中心、抖店学习中心）抓不到正文时，用搜索引擎快照交叉核对，并在文档里注明访问方式与时间。

五条方法的共同点：**调研的产出不是"我知道了什么"，而是"我敢在面试里说什么、不敢说什么"**。本文所有"未披露/未核实/作者判断"标注，就是这条纪律的执行记录。
