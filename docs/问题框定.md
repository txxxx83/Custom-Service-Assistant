# 问题框定 · 电商售后 AI 客服「判定层」原型

> 版本：2026-11-12 ｜ 独立完成（产品、开发、测试三个角色都是我，无研发/测试/运营团队）
> 事实基线：`docs/FACTS-事实基线.md`（核对时间 2026-11-12）。本文所有数字、规则 ID、状态名均来自 FACTS.md、`data/*.json`、`mock-data.json` 或现场跑代码复算，出处见附录 A。
> 项目性质：**个人作品集 / 学习项目。未上线、无真实用户、无真实业务指标、数据全部模拟。**
> 这份文档要证明的不是方案多完整，而是**问题多具体、证据多诚实、边界多清楚**——我不是先想到"做个 AI 客服"，而是先想清楚"谁在为什么付代价"。

**证据标签约定**（全文通用，请先记住）

| 标签 | 含义 | 能支撑什么 |
| --- | --- | --- |
| 【实测】 | 现场跑 `python test_policy.py` / 读 JSON / 复算 `policy.decide()` | 机制成立、可复现 |
| 【原话】 | 我记录的商家或客户原话转述（截图/评论），未核验、无样本量 | 机制存在，不能推频率 |
| 【二手】 | 跨类目公开材料归纳（生鲜/百货/美妆） | 共性问题，不能推单类目结论 |
| 【构造】 | 我为演示写的设计假设（7 条 counterfactual、互斥规则样本） | 设计意图，不是观测事实 |
| 【假设】 | 数值假设（如 `ASSUMED_SHIPPING = 12`） | 相对关系，不是绝对金额 |
| 【未验证】 | 目前没有任何证据 | 只能写成待验证假设 |

提醒：最容易犯的错是把【构造】和【假设】写成【实测】。被追问时，对方只要问一句“这数据哪来的”，就答不下去了。**标签不是减分项，是退路。**

## 1. 一句话问题陈述

> **美妆个护店铺的一线客服，在客户追问退款/换货进度、或要求把"拍错色号"按品质退货处理时，因为查不到（或不去查）退款单/换货单是否真的落库、知识库是否覆盖这个问题，会用一句听起来确定的话把不确定盖过去；这句话发出去之后，代价不由说话的人承担——商家多掏来回运费并被记一次商责退货，客户在承诺时限（换货 48 小时、微信退款 1–3 个工作日）过后等不到兑现，再回来投诉。**

四个成分都必须能指到具体的东西：

| 成分 | 本项目里的具体所指 | 出处 |
| --- | --- | --- |
| 谁 | 一线客服（坐席王倩 A1）说话；商家/店主付钱；客户（周女士、吴先生等）承担失信 | `mock-data.json` agents / conversations |
| 什么场景 | ① 进度追问（退款到账、换货出库）② 退货原因归类 ③ 知识库没覆盖的问题（发票） | C1 / C6 / C8 / C7 |
| 因为什么 | 单据未落库（`refund.refundNo = null`、`missingFields` 含"换货单号"）；知识无覆盖；客服省事动机 | `data/orders.json`、`data/knowledge_base.json` |
| 付出什么代价 | 商家：来回运费（假设 ¥24）+ `counts_return_rate=True` + `affects_score=True`；客户：时限过后仍无结果 | `policy.return_reasons()`、K4 / K3 原文 |

**最省事的写法是“客服效率低、回复慢、准确率不够”，但一被追问就露馅**：效率低是谁的效率？慢多少？准确率的分母是什么？这三句话没指向任何字段、任何政策、任何付钱的人。

**可反驳版本**——不能被推翻的问题陈述不是问题陈述，是口号：如果真实工单里"承诺兑现不了"的占比极低，且商家并不真的为品退率与平台处罚付费，那么这个问题不值得做，我应该回去做效率工具。这两个前提我都没有数据【未验证】，所以我把它写成"值得验证的问题"，不是"已经证实的痛点"。

同一件事两个受害者，讲的时候要分开：客服视角是"我不知道退款单生成没有，但客户在催，我得说点什么"；商家视角是"客服说的每一句可以退/可以补/在处理中，最后都可能变成我的运费、我的品退率、我的投诉工单"。

## 2. 问题的来源与证据分级

### 2.1 一手证据：我看到的商家原话与截图

| 编号 | 内容 | 出处 | 强度与局限 |
| --- | --- | --- | --- |
| P1 | "引导成'品质退货'对客服最省事，但会推高品退率、触发平台处罚——这正是截图里商家的原话" | `orders.json` → C8 订单 `whyThisOrder` | 【原话】证明**动机与代价的因果链**存在；无样本量、无店铺名、无处罚截图 |
| P2 | 商家评论"这月帮我品退大几十单" | `evidence/02-过度承诺.jpg` 评论区转述 | 【原话】"大几十"是口语量级，**不是统计数字**，本文不当频率证据用 |
| P3 | 截图 01：商家设"20 个/斤"，AI 答"单果 1–2g、250–500 个" | `orders.json` → C9 订单 `whyThisOrder` | 【原话】+【二手】"参数缺失时硬报数字"的具体失败样本，但属**生鲜类目** |

提醒：一手证据 ≠ 可量化证据。P1 能证明"客服最省事的路径恰好是商家最贵的路径"这个**机制**，不能证明它**多久发生一次**。说"商家普遍这么干"就是拿 n=1 推总体。正确说法：**"我看到一个商家明确这么说，据此设计了一个能拦住它的机制；发生率我没有数据。"**

### 2.2 二手证据：跨类目材料，以及"锁单一类目"的取舍

`orders.json` → `meta.categoryDecision` 原文："证据跨类目（无花果=生鲜、保温杯=百货、评论=美妆），产品锁单一类目=美妆个护。跨类目证据仅用于归纳共性问题，未做跨类目验证。"

从三个类目归纳出的**共性问题**（这是二手证据唯一的合法用途）：① 参数没登记时倾向于编一个看起来合理的数字（无花果个数、保温杯容量、美妆开封后使用期限）；② 客户问"能不能办"，回答给"政策是什么"——**政策背诵不等于事实核对**；③ 归类错误不会让成本消失，只会**把成本转移给商家**。

为什么锁死美妆个护而不是"支持多类目"：

| 理由 | 具体说明 |
| --- | --- |
| 类目规则是硬差异 | K2：美妆个护一经拆封不支持七天无理由，过敏需医院证明或质检报告。生鲜的"个数/斤"换算在美妆里不存在 |
| 单人无跨类目验证能力 | 31 条规则人工整理，非工单聚类【实测：售后 14 / 商品 9 / 物流 8】 |
| 可辩护性 | "锁一个类目、机制可迁移但未验证"比"支持多类目"安全一万倍 |

**取舍的代价要主动说**：P3 那条生鲜截图在本项目里被"翻译"成 C9 订单——`spec.开封后使用期限 = null`、`missingFields = ["开封后使用期限"]`，系统不报数字，改为追问/登记缺口。这是**结构同构的移植，不是同类目的验证**。

两条诚实声明：① 一份 9 条的二手证据清单（E-01～E-09，含消协投诉结构、国标生效时间）**不在 demo 工作区，我无法核对原文，因此本文不引用其中任何数字**——引用链断了的数字一律不用，现场打不开它，它就等于不存在。② `mock-data.json` 里 7 条会话各有一句 `counterfactual`（"如果没有这道判定"），它们是**我写的反事实设计说明【构造】，不是真实历史工单**；价值在于逼我说清"不做会怎样"，局限在于旧做法的发生率与后果都无观测数据。第 4 节使用它们时，我会把"政策条文推导"与"我的推断"分开标。

### 2.3 第三类证据：项目内可复算的验证（别混成业务成果）

| 项 | 数字 | 口径 | 出处 |
| --- | --- | --- | --- |
| 判定验收用例 | 15 通过 / 0 失败 | **验收通过率**，不是准确率 | 现场跑 `python test_policy.py`【实测】 |
| 工作台 7 条会话 | 1 可发 / 3 信息不足 / 2 高风险拦截 / 1 知识不足 | 用 `app.py` 同一调用路径复算，与 FACTS 第七节逐条一致 | `policy.decide()`【实测】 |
| 知识规则 | 31 条：20 low / 2 medium / 9 high；**23 条没有 `triggers` 字段** | 召回主要靠字符重叠，同义说法覆盖有限 | 现场统计 `knowledge_base.json`【实测】 |
| 旧引擎离线评测 | 150 行 = 50 用例 × 3 版本 | **上一代四态规则引擎**，与现在五态不是同一系统 | `data/evaluation_results.csv`【实测】 |
| 意图识别准确率 | 41/50 = **82%**，V1/V2/V3 三版完全持平 | 关键词法已到上限，继续加词不会提升 | 按 `pred_intent == expected_intent` 统计 |
| 转人工判断准确率 | V1 20/50=40% → V2 33/50=66% → V3 44/50=**88%** | FACTS 里"88%"的准确口径是 **V3 的转人工判断**，不是整体准确率 | 同上 |
| V3 的 6 条错误结构 | **5 条漏转 + 1 条多转** | 5 条漏转的 `pred_intent` 全部已是"转人工"，却仍生成了一句商品答案 | 同上 |

**最后一行是整个项目最硬的一条证据**：旧引擎的失败不是“听不懂”，而是“听懂了也照样答”。（例：“你是什么模型”“帮我写个小红书文案”，意图已判成转人工，但出口只看风险词与检索命中，于是照样返回商品答疑。）

禁止讲法：把 88% 说成"AI 准确率 88%"或"上线后提升 88%"。正确讲法："在 50 条离线用例上，旧规则引擎 V3 的转人工判断准确率是 88%，意图识别停在 82%；我没有上线数据。"

### 2.4 没有的证据：缺什么、影响什么、怎么补

| 缺口 | 现在只能说什么 | 对结论可信度的影响 | 最便宜的补法 |
| --- | --- | --- | --- |
| 真实工单量与分布 | "我构造了 7 条会话"【构造】 | 无法判断 need_info 类占比，也就估不出价值上限 | 要 1 个商家 1 天的售后会话导出，人工标 50 条 |
| AHT 基线 | 从未测量【未验证】 | 无法回答"门禁会不会拖慢客服"，只能列为反向指标 | 试点期记录接入/解决时间戳，取中位数 |
| 投诉率 / 二次咨询率基线 | 从未测量【未验证】 | 无法证明减少无依据承诺真的减少了下游成本 | 先拿一个店的现状数字 |
| 品退率触发处罚的阈值 | 只有商家原话"会触发平台处罚"【原话】 | ¥24 之外"更贵的代价"无法量化 | 查平台公开的商责退货率考核规则原文 |
| 真实运费账单 | `ASSUMED_SHIPPING = 12` 是假设【假设】 | 绝对金额不可信，相对关系可信 | 一张快递月结账单或运费险保单 |
| 真实客服/商家访谈 | 0 人，5 人可理解性走查也未执行【未验证】 | "客服会不会用"完全没答案，最大落地风险 | 5 个非同行 × 3 分钟走查，只记原话不解释 |
| 规则冲突真实样本 | 0 条，售后规则-001 / 008 两条互斥规则手工构造【构造】 | conflict 态只能证明机制，不能证明需求 | 从真实店铺政策里找两条结论相反的条文 |
| 规则库来源 | 31 条人工整理，非工单聚类【实测】 | 覆盖率未知，23 条无触发词 | 用真实会话跑召回，统计 no_knowledge 占比 |
| 持久化埋点 | 审计只在 `st.session_state`，刷新即丢【实测】 | 连原型内行为数据都留不住，任何指标都算不出 | 先把 `log_action()` 落到本地 CSV |

**结论可信度分级（本文最重要的自我评估）**：机制存在且可被拦截＝**中等偏上**（一手原话 P1 + 可复算判定链路）；发生频率与业务收益＝**无证据**；客服愿不愿意用＝**无证据**。一句话：**我能证明这个失败机制存在、且能被一道事前门禁拦住；我不能证明它多久发生一次、拦下来值多少钱。**

## 3. 问题的边界：In scope / Out of scope

### 3.1 做什么

| 范围 | 具体到字段/代码 |
| --- | --- |
| 单一类目：美妆个护 | `orders.json` → `meta.lockedCategory`；7 张订单 `category` 全为美妆个护 |
| 三类意图：售后 / 物流 / 商品咨询 | `engine.INTENT_KEYWORDS`；识别不出时归"转人工" |
| **发送前**判定，五态出口 | `policy.decide()` → `Verdict`：ready / need_info / conflict / no_knowledge / blocked（另有 error 兜底） |
| 订单是可查询数据，不是旁白 | `refund.refundNo`、`afterSale.opened/used/type`、`deliveredAt`、`logistics.waybill/lastNode/lastNodeAt`、`spec.*`、`missingFields` |
| 缺字段只拦"本轮真要用到"的 | `FIELD_TRIGGERS × order.missingFields` 求交集 |
| 退货原因代价对比（A 场景） | `policy.return_reasons()` → `seller_cost / counts_return_rate / affects_score` |
| 会话级审计（不持久化） | `app.py:362 log_action()`：采纳建议 / 发送（原样或改写）/ 忽略建议 / 转人工 / 标记已解决 / 重新打开会话 |

### 3.2 不做什么，以及为什么

| 不做 | 为什么这个阶段不做 | 边界与口径 |
| --- | --- | --- |
| 全流程客服机器人 | 目标会变成"每句都答上来"，与"每句都有依据"直接冲突 | "我不追求自动解决率，追求答上来的每句都有出处" |
| 多类目 | 类目规则是硬差异，单人无跨类目验证能力 | "跨类目证据只用于归纳共性问题，未做跨类目验证" |
| 真实系统对接（订单/售后/物流） | 无后端、无数据库；字段形状对齐商家后台，值可造假 | "换真接口时只替换 repository 层，判定逻辑不动" |
| 自动解决率 / 回复率作为目标 | 可以靠"硬答、只答简单的"刷上去 | 见第 8.1 节北极星论证 |
| 让大模型参与判定 | 判定要可复现、可审计、可测试；模型自报 state 在工作台被丢弃 | "模型只把已判定可发的话说得更像人" |
| 权限体系 / 多坐席并发 | 归属人当前是**文案与流程约定**，不是系统强制角色 | 主动说，不要等人问 |
| 持久化埋点 / 看板 / A-B 分流 | 未实现，审计刷新即丢 | "指标口径设计好了，数据一条都还没有" |
| 转人工后的回传与工单流转 | 只做了一半：带原因码与上下文，没做交接后闭环 | 6 种原因码：no_knowledge / conflict / high_risk / out_of_scope / customer_request / other |
| B 场景独立页面（参数缺失） | 只以 C9 订单 + 用例形式存在，`app.py` 无对应页面 | 界面只有"工作台 / 退货原因"两页（`?dev=1` 才加三页） |

提醒：合格的边界要回答三件事——**不做什么、为什么这个阶段不做、什么条件下会做**。只写"不做多类目"是清单；写"因为类目规则是硬差异且我没有跨类目验证能力，等有一个真实类目的工单日志后再扩"才是决策。

## 4. 为什么"答得没依据"比"答得慢"更值得做

### 4.1 两种问题的成本结构不一样

| 维度 | 答得慢 | 答得没依据 |
| --- | --- | --- |
| 可撤销性 | 可道歉、可补偿，客户损失的是时间 | 承诺发出即成为客户预期，**撤回等于失信** |
| 成本承担者 | 客户等待 + 客服加班 | **转移到商家**：运费、品退率、店铺考核、赔付 |
| 是否随规模放大 | 线性（多招人可缓解） | 非线性（错误归类会被复制成习惯，见 P2"这月帮我品退大几十单"） |
| 能否靠更好的生成模型解决 | 能 | **不能**——生成越流畅，无依据的承诺越像真的 |

最后一行是核心判断，也有代码级证据：`policy.decide()` 第①步注释写着"投诉/法律/舆情/健康风险一旦出现，不该再去检索政策——**检索得越准，越可能把承诺说得更像真的**"。

### 4.2 七条会话逐条论证（counterfactual 引用原文，均为【构造】）

| 会话 | 旧做法（原文） | 为什么错 | 实测判定 | 依据 / 缺什么 |
| --- | --- | --- | --- | --- |
| C1 周女士 V3·退款进度 | "旧做法是「退款 1–3 个工作日到账」；但这笔退款单根本没生成，等一周也不会到账。" | K3 的适用前提是"退款审核通过后"，前提不成立时引用它就是无依据 | `need_info`·不可发·客服 | 售后规则-004；缺"退款单号" |
| C2 陈先生 V1·退货（过敏） | "旧做法是「拆封也能退」或「过敏赔您」；健康风险不能由客服口头定性。" | 过敏属健康风险，定性权不在客服；K2 要求医院证明或质检报告 | `blocked`·不可发·客服组长 | 售后规则-012（首条）；命中「过敏」 |
| C3 刘先生 V1·物流停滞 | "旧做法是「已经帮您催了」；没有催件单，客户三天后会再问一次。" | 声称完成了没有记录的动作，是**另一种无依据** | `ready`·**可发**·客服 | 物流规则-003；只说"需要我现在提交登记吗" |
| C4 赵女士 V2·质量+投诉 | "旧做法是解释或承诺赔偿；投诉、法律风险必须由组长承接。" | 客户已提 12315 与投诉，任何解释都可能被当成责任认定 | `blocked`·不可发·客服组长 | 售后规则-005（首条）；命中「12315」「投诉」 |
| C5 孙女士 V3·价保 | "客服已经说「可以补、我帮您提交」；但这单没有活动标记，若是秒杀或券叠加，提交也会被驳回。" | 售后规则-014 明确"秒杀/券叠加不适用"，适用性未核对就承诺 | `need_info`·不可发·客服 | 售后规则-014；缺"价保适用性" |
| C6 吴先生 V1·换货 | "客服已经说「在仓库处理中」；但换货单没落库，这句话 48 小时后无法兑现。" | 没有换货单就没有"仓库收到寄回"这个起点，48 小时无法起算 | `need_info`·不可发·客服 | 售后规则-005；缺"换货单号" |
| C7 郑先生 V1·发票 | "旧做法是「可以开」；但发票流程不在知识库，开不出来就是二次投诉。" | 0 条可引用规则时，任何肯定回答都是编的 | `no_knowledge`·不可发·知识库管理员 | 无依据；登记知识缺口 |

汇总【实测】：**1 可发 / 3 信息不足 / 2 高风险拦截 / 1 知识不足**。C4、C7 **不需要订单事实**：C4 第①步即 blocked，C7 第⑤步 no_knowledge，会话上的 orderId（SO20261101008 / SO20261028031）只是展示字段，已写进 `orders.json.noLookupConversations`。**这不是数据缺失，是这条会话用不到订单。** 被问"为什么这两单查不到"就这么答。

### 4.3 写透 C6：AI 拦住了一句人已经说出口的承诺

时间线（`mock-data.json` messages，【构造】但时间戳自洽）：11-04 16:20 客户"我上周寄回去换的货，什么时候能发出来？"→ 16:22 客服"您好，换货单已在仓库处理中，发出后会同步单号给您。"

订单事实（`SO20261031055`，【实测】）：`afterSale.type = "exchange"`、`appliedAt = 2026-11-02T09:20`、`deliveredAt = 2026-11-01T14:05`、`missingFields = ["换货单号"]`、`policyHooks` = "售后规则-005 可以换货吗 → 需先有换货单才算受理"。政策条文（K4 / 售后规则-005）：**仓库收到寄回后 48 小时内发出**。

推导链（这一步是判定层真正的设计动作）

判定层做了什么【实测】：`need_info`、不可发、归属**客服**（不是组长），追问话术原文：

> "这笔 SO20261031055 的换货单没有落库，无法报出库时间；需核对该换货单是否生成，不能按'在仓库处理中'口头承诺。"

三个设计细节：① **归属客服而非组长**——这是可补齐的事实缺口（need_info），不是风险（blocked）；混成一个"不可发"，客服就不知道该去问客户还是找组长。② **拦的是下一句，不是上一句**——已说出口的撤不回来，系统能做的是不让第二句继续圆谎，这就是"AI 的价值有时是拦住人已经说出口的承诺"。③ **诚实标注**：48 小时后客户会再问/会投诉是**我的推断【未验证】**，我有的只是政策条文与字段状态。

### 4.4 写透 C1：这不是话术问题，是数据问题

客户 11-05 10:36"退款申请提交三天了，怎么还没到账？"，10:42 补一句"好的，麻烦快点，我急着用钱。"订单 `SO20261105001`【实测】：`refund.appliedAt = 2026-11-02T15:10`、`refundNo = null`、`status = "submitted_not_created"`、`channel = "微信支付"`——申请日 11-02 到询问日 11-05 正好三天，**时间戳对得上，这不是随口编的剧本**。

旧做法引用 K3"微信支付 1–3 个工作日到账"，但 K3 原文前提是"**退款审核通过后**"，而这笔连退款单都没生成，前提不成立。**引用一条适用条件不满足的政策，就是无依据发送。** 售后规则-004 的 `cannot_answer` 早写着"无法承诺具体到账时间"——规则画了线，只是没人执行。判定层输出【实测】：`need_info`、缺"退款单号"、依据售后规则-004，追问话术："这笔 SO20261105001 的退款单没有生成，不能按'在途'解释；需核对该笔退款是否落库，或引导客户重新提交。"

**一个真实修过的 bug 值得当故事讲**（出处 `docs/下一步清单.md` 第 1 节）：判定原来只读"最后一句客户消息"，C1 最后一句是"好的，麻烦快点"，于是被判成知识不足；改成**整段客户发言**后才判对。教训：问题的定义会被一个技术细节偷偷改写，PM 必须知道输入是什么。话术层永远看不到 `refundNo`——**"能办事"与"会背政策"的分界就在这里。**

### 4.5 C3 是对照组：没有它，"会停"就无法与"无能"区分

`orders.json` 里 C3 的 `whyThisOrder` 原文："对照组：知识齐全、无风险、条件完整 → ready。没有这条，'会停'就无法证明是判断而非无能。"实测话术：

> "您反馈运单尾号 8873 的包裹在沈阳转运中心已经 4 天没有更新，属于异常。按规则可以为您登记催件并转专员跟进；需要我现在提交登记吗？"

两个不变式由 `test_policy.py` 强制：物流回答**必须引用订单运单号后 4 位**、**不得出现"已为您登记"**。这是把"只说有依据的话"写成可执行验收，而不是写在 PRD 里当口号。

**这一条曾经有个我自己发现的缺口，本轮已修，值得当故事讲**：话术里的天数原来取自客户原话（`policy._days_mentioned`），客户说"五天没动"，系统就写"已经 5 天没有更新"。但按订单 `lastNodeAt = 2026-10-31T22:40` 到会话最后一条消息 11-05T10:35 复算是 **4 天**。即：**ready 态话术在复述一个未经核对的客户自述数字**——系统自己违反了"只说有依据的话"。

修法：`decide()` 新增 `as_of` 参数（界面传该会话最后一条消息的时间，**不用 `datetime.now()`**，否则同一张单在不同日期跑出不同结论、演示无法复现），`compose_answer()` 改用 `_days_between(as_of, lastNodeAt)`。客户口径与字段口径不一致时，往 `Verdict.steps` 记一条「核对客户口径：客户说 5 天，按节点时间算 4 天，话术采用字段口径」，客服在判定过程里看得见。新增**第 15 条验收用例**专门断言这件事。原假设 A15 由此关闭。

### 4.6 什么时候"答得慢"才是主要问题（诚实的反面）

如果一个店铺工单量极高、客户流失主要来自等待、承诺兑现率本来就很高，优先级就该反过来——先做效率再做门禁。**我没有数据判断当前属于哪种情况【未验证】。** 我的处理方式是把 AHT 放进**反向指标**而不是目标，一旦恶化到不可接受就按第 8.4 节退让。这比嘴硬"依据永远比效率重要"专业得多。

| 角色 | 表面上要什么 | 真实动机（KPI / 情绪） | 他最省事的路径 | 这条路径谁付钱 | 判定层给他什么 |
| --- | --- | --- | --- | --- | --- |
| 一线客服（王倩 A1） | "帮我把客户安抚住" | 少挨骂、快点结案、响应时长考核 | 说一句确定的话（"在处理中""可以补""1–3 天到账"）；把退货归成品质退货 | **商家**（运费+品退率+考核）、**客户**（失信） | ready 给带出处话术；need_info 给"该问什么"，不用自己编 |
| 客服组长（李强 A2） | "别出事" | 背投诉指标、背升级工单 | 事后骂人、事后质检 | 商家已付过钱 | blocked / conflict 明确归属到他，附命中规则与上下文 |
| 知识库管理员 | "知识覆盖率高" | 背覆盖，但补规则是额外工作量 | 把缺口拖着不补 | 下次同类问题继续 no_knowledge | no_knowledge 变成一条**有具体问题文本的缺口登记** |
| 商家 / 店主 | "客服别乱承诺" | 背品退率、店铺评分、平台处罚 | 无法直接干预每一句话 | 自己 | A 场景把"多掏多少、是否计品退率"摆在同一屏 |
| 客户（周女士/吴先生等） | "给我个准话" | 要**确定性**，不是要礼貌 | 追问、投诉、12315 | 商家 + 自己的时间 | 追问话术含"缺什么/为什么不能答/下一步"，而不是"正在为您查询" |

### 5.1 四组动机冲突（本文第二个核心）

1. **客服最省事的路径，恰好是商家最贵的路径。** 品质退货：客户不付寄回运费、退款更快、客服少解释一轮 → 客服最优；但 `seller_cost = ASSUMED_SHIPPING * 2`、`customer_pays_return = False`、`counts_return_rate = True`、`affects_score = True` → 商家最贵。**这不是客服素质问题，是激励结构问题**：培训解决不了激励结构，门禁可以改变默认路径。
2. **客服的响应时长 KPI 与"追问"天然冲突。** need_info 意味着多一轮对话，所以我把"门禁绕过率"列为反向指标——普遍绕过说明门禁太紧或建议太差，不是客服不听话。
3. **知识库管理员背覆盖，但登记缺口短期是给自己加活。** no_knowledge 的价值要等"知识缺口闭环周期"才体现；没人补规则，这个状态就变成垃圾抽屉（见 8.3）。
4. **客户要确定性，系统给的是"现在不能确定"。** 这是本产品**最大的体验风险【未验证】**：处理不好，体验比旧做法更差。缓解手段是追问话术三要素，但是否有效只能靠走查与试点回答。

### 5.2 用户、买单人、否决者不是同一个人；以及一个必须主动说的现实

**用户**是一线客服（每天点几百次的人），**买单人**是商家/店主（为品退率与赔付付钱），**否决者**是客服组长（背投诉指标，有权决定能不能上线）。这决定了界面给谁看什么——"退货原因"页是**给商家看的那一屏**，工作台是给客服看的那一屏。作品集最常见的错误是只写用户。

必须主动说的现实：归属人（客服 / 组长 / 知识库管理员）在当前版本是**文案与流程约定，不是系统强制的角色权限**；无登录、无权限体系、无多坐席并发。所以"归属"这一版是**设计主张**，不是控制手段。主动说这句话，比被问出来强十倍。

## 6. 问题的量化尝试与诚实标注

### 6.1 A 场景：同一张单，三条退货路径

订单 `SO20261106012`【实测】：持妆粉底液 30ml，¥269，色号 01 象牙白，`afterSale.opened = false`、`used = false`、`reason = "拍错色号，想换成 02 自然色"`，签收当天申请（`deliveredAt` 与 `appliedAt` 同日）。

| 退货原因 | 允不允许 | 商家多掏 | 客户付寄回运费 | 计入商责退货率 | 影响店铺考核 |
| --- | --- | --- | --- | --- | --- |
| 七天无理由退货 | 允许（未拆封、签收当天） | **¥0** | 是 | 否 | 否 |
| 换货（同款换色号） | 允许（15 天窗口内，诉求是换不是退） | **¥12**【假设】 | 是 | 否 | 否 |
| 品质退货 | **禁用**（订单里没有任何质量证据） | **¥24**【假设】 | 否 | **是** | **是** |

### 6.2 口径声明（这一段不能省，省了就是废稿）

- ¥12 来自 `policy.py:520` 的 `ASSUMED_SHIPPING = 12`，是**假设的单程运费，不是实测**；¥24 = `ASSUMED_SHIPPING * 2`，因为品质退货客户不付运费，来回两程都落在商家账上。
- **相对关系有政策依据**：售后规则-002（质量问题商家承担运费、无理由买家承担）、K4（换货寄回运费买家承担）、K2（质量问题需医院证明或质检报告）。**绝对金额没有依据**：真实运费随快递合约、运费险、重量变化，上线前必须用真实账单替换。
- 品质退货被禁用的理由**来自订单字段与客户原话**，不是模型判断：未拆封、未使用、原话是"拍错色号"。

### 6.3 敏感性检查，以及"真正贵的不是运费"

把 `ASSUMED_SHIPPING` 改成 15，三个数字变成 ¥0 / ¥15 / ¥30（灵敏度检查），**方向不变**：品质退货最贵、且只有它计品退率。提醒：量化第一步不是"找准确的数字"，而是**分离相对关系与绝对数值，再检查结论对假设是否敏感**——不敏感就可以带着假设往下做并显式标注；敏感就必须先拿真实数据，否则整个论证是沙上建塔。

运费是**可量化但小额**的部分，`counts_return_rate` 与 `affects_score` 这两个布尔才是大头：它们指向店铺考核、流量与平台处罚，而**处罚阈值我没有数据【未验证】**。所以这一屏的正确讲法是"**把客户的问题归错类，代价不会消失，只会转移给商家**"（`app.py:767` 原文），而不是"帮商家省了 24 块钱"。

### 6.4 我尝试过但放弃的量化，以及禁止出现的写法

放弃的三项：无依据发送率的**下降幅度**（无基线、无质检标注、无持久化日志）、赔付金额减少（无真实退款/赔付接口）、AHT 变化（从未测量）。现在只写口径不写数字，例如无依据发送率＝质检判定为无依据/超权限的已发送消息数 ÷ 已发送消息总数。

| 禁止 | 应该写成 |
| --- | --- |
| "原来 AHT 5 分钟" | "AHT 未测量，列为反向指标" |
| "投诉率下降 30%" | "投诉率无基线，无法声称下降" |
| "准确率从 40% 提升到 88%" | "40%/66%/88% 是旧引擎三版的**转人工判断**准确率，与五态不是同一系统" |
| "运费 12 元" | "假设单程运费 ¥12（`ASSUMED_SHIPPING`），非实测" |
| "支持多类目" / "已上线 / 有真实用户 / 降低了赔付" | "锁美妆个护，跨类目证据只用于归纳共性问题" / "个人作品集原型，未上线、无真实用户、无业务指标" |

## 7. 候选方案空间与被否决的选项

把"减少无依据承诺"摊开，我至少考虑过 6 条路。**否决理由必须落到这个团队、这个类目、这个阶段**，否则就是抄来的对比表。

| 候选 | 它解决什么 | 结论 | 理由（团队 / 类目 / 阶段） | 它的失败模式 |
| --- | --- | --- | --- | --- |
| A 全自动 AI 回复 | 自动解决率、人力成本 | **否决** | 目标函数错了：奖励"答上来"，不奖励"答得有依据"。单人无标注团队、无真实接口，无法为自动发送兜底 | 把无依据承诺自动化、规模化 |
| B 话术模板库 / SOP 检索 | 客服查得到政策 | **否决（作为主方案）** | 美妆的问题不是"不知道政策"，是"政策适用条件不满足"（C1 的 K3、C5 的秒杀排除）。模板库读不到 `refundNo` | 客服把模板当结论，前提不核对 |
| C 事后质检 + 培训/罚则 | 追责、威慑 | **否决（作为主方案）** | 承诺已发出、预期已形成，质检只能事后罚款；且加剧客服"少说话"的逆激励，与响应时长 KPI 冲突 | 罚了人，钱已经赔了 |
| D **事前判定门禁** | 发送前判定这句话能不能发 | **选中** | 判定可用本地规则实现，单人可完成、可测试（15 条用例）、可审计；不依赖真实接口即可验证机制 | 客服多一步、可能绕过；AHT 上升 |
| E 提升检索与生成质量（语义向量+更强模型+扩规则） | 召回率、答对率 | **降级为后续** | 意图 82% 三版持平说明关键词法到上限；但 V3 的 5 条漏转证明**检索再准也不等于出口对**。23/31 条规则无触发词，扩规则先要补词 | 答得更流畅的无依据承诺 |
| F 字段补齐 / 数据治理看板 | 缺字段本身 | **降级为前提，不是替代** | 治理是长期工程，单人推不动商家后台改造；但判定层能暴露"哪几个字段最常卡住"，反过来给治理排优先级 | 治理做完了，客服照样乱承诺 |

**为什么 D 与 E 是顺序而非互斥**：先做门禁再做召回——门禁的正确性可以用 15 条用例验收，召回的提升需要真实会话日志，我手上只有前者。反过来就会陷入"准确率再涨 2 个点"的竞赛，而那个竞赛与商家付的钱无关。**为什么 D 与 C 是互补而非互斥**：事后质检提供北极星指标的**标注来源**（无依据发送率需人工质检判定），所以 C 不是被永久否决，是被降级为度量手段——不再负责"阻止承诺"，只负责"测量承诺"。

### 7.1 被否决选项的"复活条件"（写清条件才叫决策）

| 候选 | 什么条件下我会改选它 |
| --- | --- |
| A 全自动回复 | 有真实接口 + 持久化审计 + 质检标注，且 ready 态无依据发送率在试点期稳定为 0 |
| B 模板库 | 真实工单显示主要问题是"查不到政策"而非"前提不成立" |
| C 事后质检为主 | 门禁绕过率高到无法收敛，且商家愿意为质检付费 |
| E 语义召回 | 拿到真实会话日志，no_knowledge 中"其实有规则但没召回"的占比显著 |
| F 数据治理 | 判定日志显示 need_info 高度集中在少数几个字段（当前 4 张单声明缺字段：退款单号 / 换货单号 / 价保适用性 / 开封后使用期限） |

### 7.2 选中 D 的代价，我不藏着

客服多一步操作，AHT 可能上升（未测量）；客服可能绕过门禁自行发送（未测量，靠门禁绕过率监控）；`conflict` 态允许发送但必须勾选确认，**这个勾选可能变成橡皮图章**；当前 DeepSeek key 无效（HTTP 401），界面跑本地 `compose_answer` 兜底文案——不影响判定，但意味着"模型改写措辞"这条线**当前没有被真实验证过**。

## 8. 成功长什么样 & 失败长什么样

> 全部指标均为**建议口径，尚未上线验证**。当前原型只有会话级审计（6 类动作，存 `st.session_state`，刷新即丢），无持久化埋点、无看板、无 A/B 分流。所以下面每个指标的**当前值都是"未测量"**。

### 8.1 指标体系

| 层级 | 指标 | 公式 | 数据来源 | 为什么是它 |
| --- | --- | --- | --- | --- |
| 北极星 | **无依据发送率** | 质检判定为"无依据/超权限"的已发送消息数 ÷ 已发送消息总数 | 人工质检标注 + 发送日志 | 直接对应产品主张，越低越好，且**不能靠多答刷上去** |
| 驱动 1 | 追问补齐率 | need_info 会话中补齐字段后继续处理的占比 | 会话状态流转 + 字段变更记录 | 证明"追问"这个动作真的有用 |
| 驱动 2 | 知识缺口闭环周期 | 从登记 no_knowledge 到新规则上线的中位天数 | 知识缺口工单 | 证明"不知道"变成了组织动作 |
| 反向 1 | AHT | 会话接入到解决的中位时长 | 会话时间戳 | 门禁会增加步骤，必须监控有没有把客服拖慢 |
| 反向 2 | 门禁绕过率 | 客服忽略建议后自行发送且被判无依据的占比 | 忽略日志 + 质检 | 普遍绕过 = 门禁太紧或建议太差 |
| 健康 | 判定覆盖率 / 模型失败率 | 有明确状态的会话占比；`llm` 返回 error 的占比 | 判定日志 / 调用日志 | 系统自身可用性 |

**为什么不用回复率 / 准确率 / 自动解决率当北极星**：回复率高可能意味着硬答更多；准确率高可能意味着把难题全转人工；自动解决率高可能意味着把风险会话也自动结了。三个都能被"多答、答简单的"刷上去，与"减少无依据承诺"不对齐。

### 8.2 分阶段的"成功"

| 阶段 | 可验收的成功信号 | 当前状态 |
| --- | --- | --- |
| 原型阶段（现在） | 15 条用例全过；7 条会话卡片"不可发"与按钮禁用 0 例外；物流回答含运单尾号且不含"已为您登记"；conflict 必须勾选才解锁 | **已达成**【实测】 |
| 走查阶段 | 5 个非同行 × 3 分钟，能自己说出"它为什么拦住我" | 未执行【未验证】 |
| 试点阶段 | 无依据发送率有基线、有下降；追问补齐率可算；AHT 变化在可接受范围 | 无试点，全部未测量 |
| 上线阶段 | 知识缺口闭环周期可算；门禁绕过率收敛 | 未上线 |

### 8.3 失败长什么样（写成"如果…就…"）

① 无依据发送率没降、AHT 却涨了 → 产品失败，回滚门禁，回去做效率工具。② 门禁绕过率持续偏高 → 不是客服不听话，是建议没用或门槛太高；先改建议质量，再考虑放宽 low 风险的 need_info 为"提示但可发"。③ 追问补齐率很低 → 追问话术不可执行，回去改 `_ask_text()` 三要素。④ conflict 一律被勾选后发送 → `requires_ack` 变成橡皮图章，必须加"勾选时必填采用哪条规则的理由"。⑤ no_knowledge 登记后长期无人补规则 → 变成垃圾抽屉，知识管理员的动机设计失败。⑥ 客户因为"被追问"而更愤怒 → 第 5.1 节标出的最大体验风险成立，要重新设计**对客户**的措辞（不是对客服的）。

### 8.4 专题：如果上线后 AHT 涨了 30%，怎么办

先说清：**30% 是我设的讨论阈值，不是测量值，也不是行业基准【假设】。** 处理顺序（不要一上来就放宽门禁）：

1. **分解涨在哪一步**：把 AHT 拆成"判定等待 / 追问轮次 / 转人工等待 / 冲突勾选"四段，看增量集中在哪。
2. **按状态分层看**：涨在 need_info 且**补齐率高** → 必要成本，用二次咨询率/投诉率对冲论证（旧做法省下的时间会在三天后还回来）；涨在 need_info 但**补齐率低** → 追问无效，改话术不是放宽门禁；涨在 no_knowledge → 知识库债，先补规则（当前 31 条，23 条无触发词）；涨在 blocked 转人工等待 → 组长承接能力问题，与判定层无关，需要排班/SLA。
3. **同时看门禁绕过率**：AHT 涨 + 绕过率涨 = 门禁太紧，客服在用脚投票，此时优先放宽**低风险**拦截而不是全部。
4. **保留不可协商项**：对话风险词（12315 / 投诉 / 过敏 / 赔偿等）与 `risk_level = high` 的规则（当前 9 条）**任何情况下不放宽**——这是产品主张的底线，放宽它就等于回到旧做法。
5. **以上都做完仍不可接受** → 承认这个类目/这个团队不适合事前门禁，写进复盘，而不是硬撑。

### 8.5 明确的"停下来"条件（kill criteria）

试点期内拿不到无依据发送率的基线（拿不到就无法证明任何事）→ 停；走查中 5 人有 4 人看不懂"它为什么拦住我"→ 停，先改表达再改功能；商家不愿意为品退率/处罚付费（第 1 节的可反驳前提被推翻）→ 停，问题不成立。

提醒：写成功指标时同时写"**这个指标怎么被刷**"和"**什么情况下我承认做错**"。只有前者是 KPI 文档，两者都有才是产品判断。

## 10. 给初学者的方法论小结：问题框定这一步，PM 到底在干什么

下面 5 条可直接迁移到下一个项目

**方法 1：先写"谁付出了什么代价"，再写"我要做什么"。** 本项目不是"做一个 AI 客服"，而是"客服说一句无依据的话，商家被记一次商责退货"。代价必须能指到**一个字段或一条政策**（`counts_return_rate = True`、K2 拆封不支持无理由），否则就是形容词。
填不出名词的那一格，就是还没想清楚的地方

它是唯一能证明我分得清
> 动作：建一张证据表，五列——来源 / 一手还是二手 / 能证明什么 / **不能证明什么** / 怎么补。然后检查每个数字的引用链，链断了（文件打不开、截图找不到）就把数字删掉。

**方法 3：用反事实逼自己说清"不做会怎样"。** 7 条会话各写一句"旧做法是 X，但 Y，所以 Z"。C6 的"客服已说在仓库处理中，但换货单没落库"就是这么逼出来的——**它比任何功能列表都有说服力**。同时诚实标注：反事实是构造的，不是观测的。
> 动作：给最核心的 3 个场景各写一句"旧做法是……但……所以……"，句末标注【观测】或【构造】。写不出"但"的场景，可能不是真问题。

**方法 4：找动机冲突，而不是找痛点。** 客服最省事的路径（品质退货）恰好是商家最贵的路径（¥24 + 计品退率 + 影响考核）。痛点列表谁都会写，**动机冲突才能解释"为什么这个问题一直没被解决"**——因为对说话的人来说它不是问题。
找不到冲突，就要怀疑这只是锦上添花的功能

**方法 5：量化时先分离"相对关系"与"绝对数值"，再做敏感性检查。** ¥0 / ¥12 / ¥24 里 ¥12 是 `ASSUMED_SHIPPING` 假设值：相对关系有政策依据，绝对金额没有；把 12 改成 15 结论方向不变，**所以我可以带着假设继续做并显式标注**。
> 动作：把假设值写成代码里的一个常量（不要散落在文案里），改一次它的值看结论方向是否变化。方向不变 → 标注假设继续走；方向变 → 先停下来找真实数据。

**交付前自检（逐条打勾）**：① 问题陈述里有"谁付代价"，且代价能指到字段或政策；② 每个数字都能说出出处，未测量的一律写"未测量/假设/未验证"；③ 有一节专门写"我没有的证据"并给出最便宜的补法；④ In/Out of scope 都写了"为什么这个阶段不做"；⑤ 至少 4 个候选方案，每个被否决的都写了复活条件；⑥ 有北极星、有反向指标、还有"什么情况下我承认做错"；⑦ 假设清单每条都有"如果错了会怎样"和"怎么最便宜地验证"；⑧ 全文没有"已上线/有真实用户/降低了赔付/支持多类目"这类无据声明。
