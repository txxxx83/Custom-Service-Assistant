## 1. 一句话认识这个项目

**产品主张：把「不确定」变成可执行的动作，并让商家看得见为什么。**

它是一个给电商售后客服用的**建议 + 门禁系统**，不是自动回复机器人。

- 有依据时：给一句带出处的建议，客服采纳/改写后发送。
- 没依据时：**不给话术**，只给动作——追问客户、转人工、禁止发送——并写清这一步该谁接手。

它**不是**什么（面试里主动说清楚，比被追问出来强）：

| 不是 | 为什么不是 |
| --- | --- |
| 不是聊天机器人 | 它不追求「每句都答上来」，追求「答上来的每句都有出处」 |
| 不是大模型应用 | 判定全部由本地规则完成，模型只负责把已判定可发的建议改写措辞 |
| 不是生产系统 | 无真实订单接口、无持久化、无登录权限、无真实客服使用 |
| 不是准确率竞赛 | 评测页的 82%/88% 是**上一代规则引擎**的历史基线，与现在的五态判定不是同一个系统 |

**最值钱的一条洞察**（务必背下来，这是你区别于其他候选人的地方）：

> 这个系统最有价值的时刻，不是「AI 答对了」，而是「AI 拦住了人已经说出口、但兑现不了的承诺」。
> C6：客服上一句已经说了「换货在仓库处理中」，但订单里换货单号是空的——这句话 48 小时后必然失信。
> C5：客服已经说了「可以补差价、我帮您提交」，但订单没有活动标记——如果是秒杀或券叠加，提交也会被驳回。
> 系统在这两句变成事实之前，把它们判成 `need_info`，并告诉客服该去核对什么。

## 2. 你必须掌握的四层知识

面试官的问题会从四个方向来。每一层我都给出「必须能回答的问题」和「达标自测」。

### 第 1 层：业务层（最重要，占面试 60%）

必须能回答：

1. 售后客服为什么会乱承诺？（省事、KPI 是响应时长、知识库查不到就凭印象答）
2. 乱承诺的代价落在谁身上？（商家：运费、赔付、品退率、店铺评分；消费者：二次投诉）
3. 「七天无理由」「换货」「品质退货」三者的区别是什么？为什么客服偏爱品质退货？
4. 美妆个护类目的特殊性有哪些？（拆封后不支持无理由、过敏属健康风险、色号/容量/开封后使用期限是必填参数）
5. 为什么「退款三天没到账」不是话术问题，而是数据问题？（退款单没落库，`refundNo` 为空）
6. 品退率为什么商家在意？（计入商责退货率 → 影响店铺考核与流量）

**达标自测**：不看任何文档，用 60 秒向一个不懂电商的人解释「为什么选错退货原因商家会多掏 24 块钱」。讲不顺就回来读第 7 章。

### 第 2 层：判定层（项目的骨架，占面试 25%）

必须能回答：

1. 五种状态分别是什么、各自允许做什么、归属谁？（第 5 章表）
2. 判定为什么是七步、顺序为什么不能换？（第 4 章）
3. `blocked` 和 `need_info` 有什么区别？（内容不能发 vs 现在还不能发）
4. 为什么冲突态允许发送但要勾选确认？（系统不替人做价值判断，但留痕）
5. 「唯一判定入口」解决了什么具体问题？（卡片说不可发、按钮却能点）
6. 模型为什么不能参与判定？（不可复现、不可审计、无法保证门禁一致）

**达标自测**：在纸上默写七步顺序与每步出口状态，错一步就重读第 4 章。

### 第 3 层：数据层（证明你不是在演剧本，占面试 10%）

必须能回答：

1. 订单里哪些字段参与判定？（`refund.refundNo`、`afterSale.opened/used/reason/appliedAt`、`deliveredAt`、`logistics.waybill/lastNode`、`spec.*`、`missingFields`）
2. `missingFields` 和 `FIELD_TRIGGERS` 是怎么配合的？（订单声明缺什么，触发词决定这次是否真的要用它）
3. 知识规则里哪些字段影响判定？（`category`、`risk_level`、`conflict_group`、`stance`、`conflict_trigger`、`triggers`、`conditions`）
4. 会话、消息、订单、建议是怎么关联的？（`convId` / `orderId`）
5. 为什么 C4、C7 的订单号不在 `orders.json` 里？（它们在查单之前就有结论，订单号只是展示字段）

**达标自测**：随便指一条会话，说出它的状态是由哪个字段/哪条规则决定的。说不出就是还没懂。

### 第 4 层：度量层（PM 的专业性，占面试 5%，但决定你是「做页面的」还是「做产品的」）

必须能回答：

1. 这个产品的北极星指标应该是什么？为什么不是「回复率」或「准确率」？
2. 哪些是反向指标（做了这件事会变差的指标）？
3. 当前原型记录了什么、还缺什么才能算出这些指标？
4. 如果上线，你怎么设计 A/B 才能证明「减少无依据承诺」？

**达标自测**：写出 1 个北极星 + 2 个驱动 + 2 个反向 + 1 个健康指标，每个都给公式和数据来源。见第 9 章。

#### A1 一条知识规则（照着这个模板写）

```json
{
  "id": "售后规则-015",
  "category": "售后咨询",
  "question": "赠品需要一起退回吗？",
  "conditions": "七天无理由退货；订单含赠品",
  "answer": "无理由退货需将赠品一并寄回；赠品已使用或缺失的，按赠品标价扣除。",
  "risk_level": "low",
  "cannot_answer": "赠品是否已使用需仓库验收后判定，不能提前承诺全额退款",
  "triggers": ["赠品", "小样", "送的", "礼品"]
}
```

字段的作用（必须记住）：

| 字段 | 谁在用 | 写错的后果 |
| --- | --- | --- |
| `category` | `_recall` / `_filter_hits` 按意图过滤 | 写错类目 → 这条规则永远召回不到 |
| `risk_level` | `decide()` 第⑥步 | 标 `high` → 一律不自动作答；标 `low` 但内容涉及赔付 → 漏拦 |
| `triggers` | `_trigger_hit`，召回与过滤都靠它 | 不写 → 客户换个说法就召回不到（C8 曾经就是这么坏的） |
| `conflict_group` + `stance` | `engine.find_conflict` | 同组两条结论相反 → `conflict`；组名写错 → 冲突永远不触发 |
| `conflict_trigger` | 同上 | 决定「客户说到什么词才算踩进这个冲突」 |
| `conditions` | `_relevance` 只比 `question` + `conditions` | 写得太泛 → 到处命中；太窄 → 命中不了 |
| `cannot_answer` | 目前只展示，不参与判定 | 这是给客服看的边界，也是你未来做「越权拦截」的原料 |

**练习**：加上面这条赠品规则，然后在界面「试一句」输入「退货赠品要一起退吗」，确认它命中 `售后规则-015` 且状态是 `ready`。

#### A2 一条测试用例（元组顺序不能错）

```python
("赠品未寄回（新规则必须被召回）", "退货的话赠品要一起寄回吗",
 "SO20261106012", "退货的话赠品要一起寄回吗",
```

不需要检查的位置写 `None`。跑法：`python test_policy.py`，看到 `15 通过 / 0 失败` 才算完成。

#### A3 字段触发词

```python
FIELD_TRIGGERS = {
    "退款单号": ["到账", "退款", "退钱"],
    "换货单号": ["换货", "寄回", "什么时候能发", "什么时间能发", "发出", "寄出"],
    "价保适用性": ["价保", "补差价", "降价", "差价"],
    # 新增：赠品是否寄回
    "赠品状态": ["赠品", "小样", "送的"],
}
```

**产品含义**：订单缺一个字段，不代表每次都要拦。客户问物流时，订单缺「色号」不该拦。
触发词就是「这次真的要用到它」的判断依据。写宽了 → 到处误拦（客服烦）；写窄了 → 该拦没拦（商家赔钱）。

**练习**：把 `"退款"` 从退款单号触发词里删掉，跑测试，看 C1 是否从 `need_info` 变成别的状态。改回来。这一步让你亲手体会「一个词决定一次赔付」。

#### A4 门禁派生属性

```python
@property
def can_send(self) -> bool:
    """能不能点发送。只有 ready 与 conflict（需确认）可以。"""
    return self.state in {"ready", "conflict"}

@property
def requires_ack(self) -> bool:
    """conflict 允许发，但必须客服先确认「两条规则我都看过」。"""
    return self.state == "conflict"
```

**为什么必须写成属性而不是在界面里判断**：界面里再写一遍 `if state == "ready"`，就有了第二套规则，迟早不一致。
这是本项目最核心的工程—产品原则：**判定只有一处定义，其他地方只读结果。**

#### A5 七步判定骨架（能默写这个就够了）

```python
def decide(question, order_no="", kb=None, orders_doc=None, dialog="") -> Verdict:
    intent = detect_intent(question)                 # 识别意图
    hits = _filter_hits(_recall(question, kb, intent), question, intent)  # 检索规则

    if _risk_hits(dialog):        return blocked     # ① 对话风险词
    if find_conflict(hits, question): return conflict # ② 规则互斥
    if _needs_order(intent, question):               # ③ 查订单
        status, order = lookup_order(order_no, orders_doc)
        if status != "found":     return need_info   #    查无此单 / 没单号
    if _missing_for(order, question): return need_info # ④ 缺本次要用的字段
    if not hits:                  return no_knowledge # ⑤ 无可引用规则
    if any(i["risk_level"] == "high" for _, i in hits): return blocked # ⑥ 规则高风险
    return ready                                     # ⑦ 出口
```

真实代码比这个多做的事：每一步都 `v.step("做了什么", "结果")`，界面渲染的就是这些步骤，**不是另写的模板**。

#### A6 退货原因的代价

```python
ReasonOption(
    code="quality_return",
    label="品质退货",
    allowed=has_quality_evidence,      # 订单/原话里有没有质量证据
    why="订单里没有任何质量证据……",
    seller_cost=ASSUMED_SHIPPING * 2,  # 来回运费 ¥24（假设值）
    customer_pays_return=False,        # 客户不付寄回运费
    counts_return_rate=True,           # 计入商责退货率
    affects_score=True,                # 影响店铺考核
)
```

**产品含义**：`allowed` 是门禁，`seller_cost / counts_return_rate / affects_score` 是**后果量化**。
PM 的价值就在后三个字段——把「这样选不好」变成「这样选多掏 24 块、被记一次商责」。

#### A7 追问话术

```python
if name == "换货单号":
    return (f"这笔 {order.get('orderId')} 的换货单没有落库，无法报出库时间；"
            "需核对该换货单是否生成，不能按“在仓库处理中”口头承诺。")
```

**写法要求**：① 指出缺哪个字段 ② 说明为什么不能答 ③ 给出下一步动作。

### B 级：必须会读、会改参数（不要求从零写）

| 函数 | 位置 | 你要看懂什么 |
| --- | --- | --- |
| `detect_intent` | `engine.py:36` | 按**命中关键词个数**选类目，不是按字典顺序。C5 曾被「签收」误判成物流，就是这里改的 |
| `_recall` | `policy.py:229` | 召回=字符重合 + 触发短语两条通道；类目不符在召回阶段就丢 |
| `_filter_hits` | `policy.py:249` | 过滤三条件：类目一致、触发命中或实词二元组≥2、同分按原始重合度排 |

| `lookup_order` | `policy.py:173` | 三出口 `found / not_found / no_number`，为什么不能合并 |
| `_missing_for` | `policy.py:277` | `missingFields` × `FIELD_TRIGGERS` 的交集逻辑 |
| `compose_answer` | `policy.py:465` | 物流回答用订单运单尾号 + **按 `as_of − lastNodeAt` 算出的停留天数**（不抄客户原话），且只说「可以为您登记」不说「已登记」 |
| `get_suggestion` | `app.py:418` | 只有 `ready` 才请模型改写；失败静默回退本地话术 |
| `cb_send` | `app.py:581` | 发送后追加消息、状态转 `waiting_customer`、清空草稿、写审计 |
| 发送门禁组合条件 | `app.py` 搜 `can_send = (` | 草稿非空 + 未锁定 + 判定可发 + 状态不在 `handed_off/waiting_customer` + 冲突已勾选 |

**读法建议**：不要逐行读。带着问题读——「C6 为什么是 need_info？」然后从 `decide()` 第④步跳到 `_missing_for` 跳到 `FIELD_TRIGGERS["换货单号"]` 跳到订单的 `missingFields`。这条链走通一次，胜过通读十遍。

### C 级：看懂概念即可（不用会写）

- Streamlit 的 rerun 机制：每次交互整个脚本重跑，所以状态要放 `st.session_state`。
- `@st.cache_data`：JSON 改了但页面没变，多半是缓存——**重启服务**，不是代码错了。
- 回调（`on_click=cb_send`）在 rerun 之前执行，所以能在回调里改状态。
- `trace_html` / `log_action`：把 `Verdict.steps` 和审计记录渲染出来，纯展示。
- 三栏布局、CSS、chip 颜色：知道信息层级即可（主区=对话与动作，辅区=依据与订单）。

### D 级：不用碰

- `engine.py` 的 `judge()` 与 `data/evaluation_results.csv`：上一代规则引擎与历史评测，只用于「为什么不再只追准确率」的论证。
- `llm.py` 的 HTTP/JSON 解析细节：知道它只改写措辞、失败返回 `state="error"` 就够。
- `_archive/`：过时材料。

## 4. 七步判定逐步精讲

顺序本身就是产品主张。每一步我都给「为什么在这个位置」和「面试追问」。

| 步 | 做什么 | 出口 | 代码 | 为什么在这个位置 |
| --- | --- | --- | --- | --- |
| ① | 对话风险词（`engine.HANDOFF_KEYWORDS`，**16 个**：11 high / 5 medium） | `blocked` | `policy.py:351` | 不依赖订单，且**不可协商**。检索得越准，越可能把承诺说得更像真的 |
| ② | 规则互斥组冲突 | `conflict` | `policy.py:365` | 只依赖规则。若放在查单之后，「冲突但订单号打错」会先报信息不足，把冲突藏起来 |
| ③ | 查订单（三出口） | `need_info` | `policy.py:378` | 只有「这个问题需要订单事实」时才查（`_needs_order`） |
| ④ | 缺本次要用到的字段 | `need_info` | `policy.py:401` | 缺字段≠每次都要拦，靠触发词判断相关性 |
| ⑤ | 知识匹配 0 条 | `no_knowledge` | `policy.py:416` | 宁可说不知道，也不拿隔壁场景的规则凑答案 |
| ⑥ | 命中规则 `risk_level=high` | `blocked` | `policy.py:427` | 第二道闸：即使检索命中，规则本身标了高风险也不自动作答 |
| ⑦ | 全通过 | `ready` | `policy.py:441` | 每句都要有出处 |

**面试追问 1：为什么①在③前面？**
答：风险判断不需要订单事实。如果先查单，一个提到 12315 的客户因为订单号打错，会先得到「请提供订单号」——这既延误了风险处置，也把高风险会话伪装成普通信息缺失。

**面试追问 2：为什么②在③前面？**
答：藏起来的冲突就是下一次赔付。两条规则结论相反时，无论订单查不查得到，都必须让人看见两条原文。

**面试追问 3：⑥和①有什么区别？**
答：①看**客户说了什么**（对话风险词），⑥看**我们自己的规则怎么说**（规则标注的风险等级）。例如「显示签收但我没收到」客户语气平静，但 `物流规则-008` 标了 `high`，因为涉及赔付责任认定，必须人工。

**面试追问 4：为什么不用大模型做判定？**
答：判定要可复现、可审计、可测试。模型输出不稳定，同一个问题两次可能给不同状态，门禁就会时松时紧。所以模型只负责措辞，状态一律以 `decide()` 为准。

**面试追问 5：`_needs_order` 会不会漏查？**
答：会，这是已知取舍。它靠意图（物流/售后）+ 字段触发词判断。冷门问法可能不触发查单，从而跳过缺字段检查。当前用 15 条用例覆盖已知问法，上线前需要真实会话日志来补。

## 5. 五态与门禁

| 状态 | 中文 | 系统做什么 | 归属 | 可发 | 需勾选 | 转人工原因码 |
| --- | --- | --- | --- | --- | --- | --- |
| `ready` | 可发建议 | 给带出处的建议 | 客服 | ✅ | — | — |
| `need_info` | 信息不足 | 不给结论，列出该问什么 | 客服 | ❌ | — | — |
| `conflict` | 规则冲突 | 并列两条原文 | 客服（判断不了升级组长） | ✅ | ✅ | `conflict` |
| `no_knowledge` | 知识不足 | 登记知识缺口 | 知识库管理员 | ❌ | — | `no_knowledge` |
| `blocked` | 高风险拦截 | 禁止生成可发送内容 | 客服组长 | ❌ | — | `high_risk` |
| `error` | 查询失败 | 显式报错，保留人工入口 | 客服 | ❌ | — | `other` |

**两个必须知道的实现现状**（2026-11-12 核对）：

1. **标签只有一份**。`ready` 的中文标签是「可发建议」。早期 `app.py` 另写了一套（"可审核"），和 `policy.py` 不一致——客服会问"可审核到底能不能发"。已改成 `STATE_LABEL = {**policy.STATE_LABEL, "missing": "暂无建议"}`。`missing`（暂无建议）是界面独有态，表示还没产出建议，**不是判定结果**。
2. **`error` 态当前不可达**。标签、归属、转人工原因三处映射都定义了它，但 `decide()` 里**没有任何分支产出** `state="error"`；`orders.json.lookupRules` 声明的第三出口"查询失败"也没实现。所以它是"已定义、未接线"的兜底，不是正在工作的兜底。真接订单接口后，超时会渲染出空标签——这是一条真实的待办，面试可以主动说。

**两种「不可发」必须分开讲**：

- `blocked` = **内容不能发**。换个人也不能直接发，必须走人工处置流程。
- `need_info` = **现在还不能发**。补齐事实（客户给单号、仓库补参数）后可以继续。

把这两者混成一个「不可发」，客服就不知道该去问客户还是该去找组长。

**发送门禁的完整条件**（`app.py` 搜 `can_send = (`）：

```
草稿非空 且 会话未锁定 且 Verdict.can_send 且 状态不在 {handed_off, waiting_customer} 且 (非冲突 或 已勾选确认)
```

五个条件缺一不可。其中「状态不在 waiting_customer」是为了防止**重复发送**——这是上一版的真实 bug。

**会话状态机**（与判定状态是两回事，别混）：

```
processing ──发送──> waiting_customer ──客户回复──> processing
processing ──转人工──> handed_off ──重新打开──> processing
processing ──标记解决──> resolved ──重新打开──> processing
```

### 6.4 一个我自己抓出来的 Bug：系统说了没依据的话（**面试重点讲这个**）

这是全项目最值得讲的一段，因为它不是"我做了个功能"，而是"我发现自己的产品违反了自己的主张"。

**项目的立身之本是一句话：只说有依据的话。** 但 C3 的物流话术曾经长这样：

> 您反馈运单尾号 8873 的包裹在沈阳转运中心已经 **5 天**没有更新……

这个「5 天」是从哪来的？从**客户自己嘴里**来的。客户说"我的快递五天没动了"，代码里的 `policy._days_mentioned()` 把「五」抠出来，直接填进话术。

而按订单字段复算：`lastNodeAt = 2026-10-31T22:40` → 会话最后一条消息 `2026-11-05T10:35`，实际是 **4 天**。

**也就是说：一个号称"每句话都要有依据"的系统，正在复述一个未经核对的客户自述数字。** 客户记错了、或者故意夸大，系统就替他把这个夸大后的数字写进了商家要负责的正式答复里。这跟它要拦的那些"无依据承诺"是同一类错误，只不过发生在自己身上。

**怎么修的（三步，都是产品决策，不是技术炫技）：**

| 步 | 做了什么 | 产品上的理由 |
| --- | --- | --- |
| 1 | 给 `decide()` 加显式入参 `as_of`，值取**会话最后一条消息的时间** | 天数必须有计算基准。不用 `datetime.now()`——那会让同一张单在不同日期跑出不同结论，演示无法复现 |
| 2 | 话术天数改为 `_days_between(as_of, lastNodeAt)`；`_days_mentioned()` 降级为**只用于对账** | 依据只能来自订单字段，客户原话是"诉求"不是"事实" |
| 3 | 两个口径不一致时，`Verdict.steps` 追加一步 **「核对客户口径」**，写明"客户说 5 天，按节点时间算 4 天，话术采用字段口径" | 差异不能悄悄吞掉。坐席要看得见系统改了客户哪个数字，否则他不敢发 |

修完的话术：

> 您反馈运单尾号 8873 的包裹在沈阳转运中心已经 **4 天**没有更新，属于异常。按规则可以为您登记催件并转专员跟进；需要我现在提交登记吗？

注意结尾是**问句**。原来写的是"已为您登记催件"——但登记动作根本没实现，那又是一句没依据的话。现在只承诺界面上真有的东西。

还加了**第 15 条验收用例**专门守这条，断言四件事：话术含「已经 4 天没有更新」、话术**不含**「5 天」、`steps` 里有「核对客户口径」、话术不含「已为您登记」。**改回去测试就红。**

**面试怎么讲（60 秒）：**

> "我这个项目的主张是'只说有依据的话'。做完之后我自己走查，发现物流话术里的停滞天数是抄客户原话的——客户说五天，系统就写五天，但按订单物流节点算其实是四天。等于系统自己在复述一个没核对过的数字。我做了三件事：把参考时刻做成显式入参而不是读系统时间，保证可复现；天数只从订单字段算；两个口径不一致时在判定步骤里明写差异，让坐席看得见。最后补了一条回归用例锁住它。这件事让我理解到，AI 产品的'可信'不是模型能力问题，是**数据来源纪律**问题——每一句对外话术都要能指回一个字段。"

**这一段能同时证明四件事**：你会自己走查而不是等别人挑错；你分得清"客户说的"和"系统知道的"；你懂可复现性对 demo 的意义；你会用测试把产品纪律固化下来。

## 7. A 场景：钱是怎么算出来的

同一笔订单（`SO20261106012`，持妆粉底液，拍错色号想换 02 自然色，未拆封、签收当天）：

| 退货原因 | 允不允许 | 商家多掏 | 客户付寄回运费 | 计入商责退货率 | 影响店铺考核 |
| --- | --- | --- | --- | --- | --- |
| 七天无理由 | ✅ | ¥0 | 是 | 否 | 否 |
| 换货（同款换色号） | ✅ | ¥12 | 是 | 否 | 否 |
| 品质退货 | ❌（无质量证据） | ¥24 | 否 | **是** | **是** |

- ¥12 来自 `ASSUMED_SHIPPING = 12`（`policy.py:520`），是**假设的单程运费**，不是实测。讲的时候必须说「假设」。
- ¥24 = 来回两程。品质退货客户不付运费，所以两程都落在商家账上。
- 品质退货被禁用的理由**来自订单字段**：未拆封、未使用、客户原话是「拍错色号」——没有任何质量证据。
- 机制来源：商家评论「这月帮我品退大几十单」。客服选品质退货最省事（客户不用付运费、退款更快），代价是商家的品退率与考核。

**这一屏的产品意义**：它不讲「AI 会不会说话」，只讲「选错原因谁付钱」。这是整个项目里最容易被非技术面试官理解的价值。

**面试追问：为什么换货也算 ¥12？**
答：换货商家要承担发出新货的运费（假设值），客户承担寄回运费。这是假设口径，真实运费按快递合约与运费险变化，上线前要用真实账单替换。

## 9. 度量与埋点（PM 的专业性所在）

### 9.1 你手上唯一的实测数据（面试先讲这个）

`data/evaluation_results.csv`：**50 条评测用例 × 3 个版本**，规则引擎离线跑出来的，不是估算。
跑的是 `engine.py`（上一代规则基线），**不是** `policy.py` 的五态判定层——这一点必须说清。

| 版本 | 用例数 | 意图识别 | 转人工判定 | 风险判定 | 要点命中 | **无依据回答** |
| --- | --- | --- | --- | --- | --- | --- |
| V1 | 50 | 41/50 = 82% | 20/50 = 40% | 20/50 = 40% | 15/50 = 30% | **50/50 = 100%** |
| V2 | 50 | 41/50 = 82% | 33/50 = 66% | 33/50 = 66% | 24/50 = 48% | **0/50 = 0%** |
| V3 | 50 | 41/50 = 82% | 44/50 = **88%** | 44/50 = 88% | 25/50 = 50% | **0/50 = 0%** |

「无依据回答」的口径就写在 `app.py` 评测页里：`answer` 非空 **且** `refs` 为空 **且** 未判转人工。
这正是北极星指标的离线代理指标——**你不用等上线，就能证明这个指标是可算的**。

**这张表最值钱的不是 88%，是「意图识别三版都是 82%」。**

为什么？因为它排除了一个替代解释。如果你只报「转人工判定从 40% 涨到 88%」，面试官会问：
「是不是你的意图识别变准了，所以后面都跟着变准？」而你可以直接回答：

> 「意图层三版都是 82%，一行没改。变的是加了依据要求和发送门禁。
> 所以收益来自判定，不是来自更强的识别或生成。」

这是一个**能被追问、且经得起追问**的因果论证。初学者报数字，进阶者排除替代解释。

口径纪律（背下来）：

- 82% = **意图识别准确率**（三版相同）
- 88% = **V3 的转人工判定准确率**（44/50），不是「AI 准确率」，不是「上线后提升」
- 这 50 条 ≠ 那 15 条。50 条是 `engine.py` 的离线评测集；15 条是 `policy.py` 的判定验收用例。两套东西。
- 150 行 = 50 × 3，不是 150 条用例。

**练习**：把这张表讲给一个不懂技术的人听，限时 60 秒，且必须主动说出「我没有上线数据」。

### 9.2 指标体系（建议口径，尚未上线验证）

| 层级 | 指标 | 公式 | 数据来源 | 为什么是它 |
| --- | --- | --- | --- | --- |
| 北极星 | 无依据发送率 | 质检判定为「无依据/超权限」的已发送消息数 ÷ 已发送消息总数 | 人工质检标注 + 发送日志 | 直接对应产品主张，且越低越好 |
| 驱动 1 | 追问补齐率 | `need_info` 会话中补齐字段后继续处理的占比 | 会话状态流转 + 字段变更记录 | 证明「追问」这个动作真的有用 |
| 驱动 2 | 知识缺口闭环周期 | 从登记 `no_knowledge` 到新规则上线的中位天数 | 知识缺口工单 | 证明「不知道」变成了组织动作 |
| 反向 1 | 平均处理时长 AHT | 会话从接入到解决的中位时长 | 会话时间戳 | 门禁会增加步骤，必须监控它有没有把客服拖慢 |
| 反向 2 | 门禁绕过率 | 客服忽略建议后自行发送且被判无依据的占比 | 忽略日志 + 质检 | 如果客服普遍绕过，说明门禁太紧或建议太差 |
| 健康 | 判定覆盖率 / 模型失败率 | 有明确状态的会话占比；`llm` 返回 error 的占比 | 判定日志 / 调用日志 | 系统自身可用性 |

**为什么不用「回复率」或「准确率」当北极星**：回复率高可能意味着硬答更多；准确率高可能意味着把难问题都转人工了。两者都能被「多答、答简单的」刷上去，与「减少无依据承诺」不对齐。

### 9.3 当前原型已经记录什么

`app.py:362` `log_action()` 写入会话级审计：采纳、改写、发送、忽略、转人工（带原因码）、标记解决、重新打开。
建议生命周期：`pending → adopted / edited → sent / ignored / handed_off`。

**还缺什么才能算出上面的指标**：

1. 持久化（现在只在 `st.session_state`，刷新即丢）。
2. 时间戳差值（AHT、闭环周期需要起止时间）。
3. 质检标注入口（无依据发送率需要人工判定）。
4. 客户侧结果（二次咨询、投诉、退款金额）——需要真实接口。
5. 字段补齐事件（追问补齐率需要知道「什么时候补上了」）。

## 12. 面试讲法

### 12.1 九十秒版（背下来）

> 我做的是一个电商售后客服的**建议与门禁系统**，主张是「只说有依据的话」。
> 售后客服真正让商家亏钱的不是答得慢，而是乱承诺：客服为了省事把「拍错色号」引导成品质退货，商家多掏来回运费还被计入商责退货率；或者随口说「换货在仓库处理中」，但换货单根本没落库。
> 所以我把判定收成一条线：一个 `decide()` 函数返回一个结果对象，界面、发送按钮、转人工、审计日志全部只读它。判定分七步，先看对话风险词，再看规则冲突，然后查订单、查这次真要用到的字段、查知识匹配、查规则风险等级，全通过才给建议。
> 五种状态里，只有「可发」和「规则冲突（需勾选确认）」能点发送。信息不足时它不给话术，而是告诉客服缺哪个字段、该去核对什么；知识不足时登记缺口给知识库管理员；高风险时禁止生成内容并转组长。
> 我做了 7 个会话、31 条规则、15 条判定用例，全过。另外有一份 50 条用例 × 3 个版本的离线评测：意图识别三版都是 82%、一行没改，但「无依据回答」从 100% 降到 0，转人工判定从 40% 升到 88%。这说明收益来自门禁，不是来自更强的识别或生成。
> 最有价值的一条不是 AI 会答，而是它拦住了人已经说出口但兑现不了的承诺。
> 边界我说清楚：数据全模拟，没有真实接口，没有真实客服用过，评测是上一代规则基线的离线结果，所以没有数据证明它降低了赔付。

### 12.2 三分钟版

在九十秒版之后补三段：

1. **一个具体案例走完整链路**（推荐 C6）：客户问「换货什么时候发出」→ 意图售后 → 召回售后规则-005 → 无风险词 → 无冲突 → 查到订单 → `missingFields` 含「换货单号」且触发词命中「什么时候能发」→ `need_info` → 发送禁用 → 追问话术「换货单没落库，不能按在仓库处理中口头承诺」→ 归属客服。
2. **一个量化后果的案例**（A 场景）：同一单三个原因，¥0/¥12/¥24，只有品质退货计品退率，无质量证据时禁用，理由来自订单字段。运费是假设值。
3. **一个取舍**：为什么模型不参与判定（可复现、可审计、门禁一致），以及为什么风险与冲突放在查单之前（藏起来的冲突就是下一次赔付）。

> 如果面试官偏产品/偏细节，第 3 段换成 **§6.4 的 C3 口径 Bug**——自己走查发现系统抄客户数字、三步修好、补回归用例。这段比讲取舍更能证明你有产品纪律。

### 12.3 被追问时的标准答法

| 追问 | 怎么答 |
| --- | --- |
| 这不就是写死的规则吗？ | 规则是写死的，**判定不是**。同一句话换一张订单，状态就变；顶部「试一句」跑的是同一个 `decide()`，可以现场输入任意问题验证 |
| 准确率多少？ | 我没有线上准确率。15 条用例全过是**验收通过率**，不是准确率。有一份 50 条 × 3 版的离线评测（上一代规则基线，与五态不是同一系统）：意图识别一直 82%，转人工判定 40%→66%→88%，无依据回答 100%→0%。**意图层没动，所以收益来自门禁** |
| 有真实用户吗？ | 没有。走查与访谈方案已写好但还没执行，所以我不能声称它降低了赔付 |
| 为什么不用大模型？ | 用了，但只用来改写措辞。判定要可复现可审计，模型输出不稳定会让门禁时松时紧 |
| 规则冲突是真实的吗？ | 不是。两条互斥规则是我手工构造的演示样本，真实样本 0 条。我把它做出来是为了验证「冲突时不替人选择」这个机制 |
| 上线要多久？ | 判定层可以直接复用；需要补的是订单/售后接口、持久化、权限、质检标注、真实规则库。我不会给一个拍脑袋的天数 |
| 你怎么知道客服会用？ | 我不知道。这正是反向指标「门禁绕过率」和「AHT」要监控的，也是走查要回答的第一个问题 |
| 你怎么保证系统自己不胡说？ | 我抓到过一次：物流话术的停滞天数原来抄客户原话，客户说 5 天系统就写 5 天，按订单节点算其实是 4 天。现在天数只能由 `as_of − lastNodeAt` 算，两个口径不一致时在判定步骤里明写差异，并有一条回归用例锁住（详见 §6.4） |
| 为什么不用系统当前时间？ | 那会让同一张单在不同日期跑出不同结论，演示无法复现。我把参考时刻做成显式入参 `as_of`，取会话最后一条消息的时间 |
| 「试一句」输入换货问题却是信息不足？ | 因为没选订单。查单是三出口，缺订单号就 `need_info`，不会硬猜。选中 SO20261106012 再输入同一句就是可发。这正好演示「同一句话换一张单，结论就变」 |

### 12.4 六句不要说的话

1. ❌「准确率从 40% 提升到 88%」——口径混了。正确说法是「**转人工判定**准确率从 40% 到 88%，**意图识别一直 82% 没变**，这是上一代规则基线的离线评测」。少了限定词就会被追死。
2. ❌「降低了赔付/提升了效率」——没有数据。
3. ❌「已实现完整 AI 客服系统」——无接口、无持久化、无权限。
4. ❌「运费 12 元」不加「假设」——会被问数据来源。
5. ❌「支持多类目」——只锁美妆个护，跨类目证据只用于归纳共性问题。
6. ❌「系统会自动登记催件 / 提交知识缺口 / 五种状态都在跑」——登记与缺口登记都没实现，`error` 态当前不可达。凡是要说「已实现」，先能指到代码行；指不到就进 §13.1 缺口表。

## 13. 已知边界，以及旧手册哪些说法已失效

### 13.1 当前真实边界（面试主动说）

- 无真实订单/售后/物流接口；订单是本地 JSON。
- 无持久化：会话状态、草稿、审计都在 `st.session_state`，刷新即丢。
- 无登录与权限：归属人（客服/组长/知识管理员）是**文案与流程约定**，不是系统强制的角色权限。
- 无真实客服使用，无赔付下降数据，走查与访谈未执行。
- 规则冲突是手工构造的演示样本。
- 转人工只做了一半：带原因码与上下文，没做交接后的回传与工单流转。
- 情绪识别是关键词，不是模型；`riskFlags` 是预置标签，实时风险来自 `_risk_hits`。
- 模型 key 当前失效（401），系统静默回退本地话术。
- C4/C7 的订单号是展示字段，未落进 `orders.json`——因为它们在查单之前就有结论。

**另有六处「已定位、本轮故意没修」的缺口。这些要主动说，不能说成已实现：**

| 缺口 | 事实 | 你该怎么说 |
| --- | --- | --- |
| `error` 态不可达 | `decide()` 没有任何分支产出 `state="error"`，只有标签/归属/原因三处映射 | 「已定义但当前不可达的兜底态」 |
| `Verdict.actions` 未渲染 | 字段有值（ready 是「采纳或改写后发送」等），传进界面后从未画出来 | 「判定层已产出建议动作，界面还没接」 |
| `cannot_answer` 未参与判定 | 31 条规则都写了这个字段，`decide()` 不读它 | 「字段备好了，还没接进判定」 |
| A 场景话术硬编码 | 退货原因页 `REASON_SCRIPT` 是写死文案，不走 `compose_answer` | 「代价是算的，话术是写死的」 |
| `SUGGESTION_BY_CONV` 死代码 | `app.py` 里定义后从未被引用，历史快照残留 | 待清理，不影响判定 |
| 知识缺口登记未实现 | no_knowledge 卡片已改为「知识缺口登记尚未实现」 | 只承诺界面上真有的「转人工」 |

**为什么留着不修**：这一版已定稿，再开一轮重构会把演示脚本、测试、文档全部拖进新一轮对账。把缺口写清楚，比补半个功能更有价值——面试官问「哪里还不完善」时，你能逐条指到代码，这本身就是专业度。

### 13.2 旧版《产品经理必答问题手册》失效对照

旧手册写于判定层重构之前，以下说法**已经不对**，新版已重写：

| 旧手册说法 | 现在的事实 |
| --- | --- |
| AI 建议与风险是「预置模拟数据」 | 由 `policy.decide()` 实时计算，`Verdict` 是唯一来源 |
| 四种状态 ready/conflict/no_knowledge/blocked | 五态，新增 `need_info`（另有 `error` 兜底） |
| 风险 = `riskFlags` + `suggestion.risks` 合并 | 统一读判定结果，`riskFlags` 只作展示标签 |
| 置信度 0.91/0.42 是预置模拟值 | 现在展示的是**相关度**（实词二元组重合数），不是置信度，更不是准确率 |
| 没有操作审计日志 | 有，`log_action()` 记录采纳/改写/发送/忽略/转人工/解决/重新打开 |
| 没有真实大模型 | 接了 DeepSeek，但只改写 ready 措辞；当前 key 失效 |
| 发送条件 = ready + 未转人工 + 未解决 + 草稿非空 | 还要求状态不在 `waiting_customer`，冲突态需勾选确认 |
| C2 冲突例子是「七天无理由 vs 类目规则」 | 冲突演示是「拆封用过的美妆还能退吗」，售后规则-001 vs 008 |
| 代码技能围绕 `selected_id` / `next()` / 列表推导式 | 现在围绕 `Verdict` / `decide()` 七步 / `FIELD_TRIGGERS` / 用例 |
| 订单信息是「对话里的一句旁白」 | 订单是可查询数据，缺字段直接决定状态 |

- 它教你**讲清楚已经做出来的东西**，不替你补上缺失的验证。走查、访谈、真实接口都还没做。
- 指标与埋点是**设计建议**，不是已上线口径，没有任何真实数据支撑。
- 代码行号以 2026-11-12 的版本为准，后续改动后请用函数名搜索定位，不要背行号。
- 竞品对比结论以 `docs/竞品与行业调研.md` 的证据清单为准，本手册不重复引用未核验的说法。
