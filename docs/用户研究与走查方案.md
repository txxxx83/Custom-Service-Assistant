### B.1 研究目标与 5 个可证伪的研究问题

总目标：验证核心主张的前提——"售后客服真正的成本不在答得慢，而在答得没依据"——在真实工作里是否成立。

| 编号 | 研究问题 | 什么证据算证实 | 什么证据算证伪 | 对应原型 |
| --- | --- | --- | --- | --- |
| RQ1 | 客服在什么情况下会**明知没依据仍然承诺**？ | 3 人以上能讲出具体一次：当时说了什么、为什么敢说、后来怎么收场 | 5–8 人都说"从不承诺没依据的话"，且能指出店里已有的拦截机制（质检/话术库/权限） | C5「可以补」、C6「在仓库处理中」 |
| RQ2 | "答得没依据"的代价由谁承担，是否真的比"答得慢"更贵？ | 有人能说出一次因口头承诺导致的赔付/品退率/考核后果 | 代价几乎全落在"客户等太久投诉"，与承诺内容无关 | A 场景 ¥0 / ¥12 / ¥24 与品退率 |
| RQ3 | 客服现在**有没有"查单据是否落库"这个动作**？还是只背政策时效？ | 有人演示过查退款单/换货单状态的路径，或明确说"查不到就先安抚" | 所有人都能一键看到单据状态，不存在"没落库"这种情况 | C1 退款单号、C6 换货单号 |
| RQ4 | 被系统拦住不能发时，客服会**补齐、绕过、还是升级**？ | 有人承认会换个说法自己发、或截图问组长 | 所有人都愿意停下来补事实，且认为多花的时间可接受 | 门禁绕过率（反向指标） |
| RQ5 | 知识库缺一条规则时，现在**谁补、多久补**？ | 能说出具体角色与周期，或承认"没人补，靠老员工记忆" | 有成熟的知识运营流程与 SLA，缺口不是问题 | C7 `no_knowledge` 与知识缺口闭环周期 |

写研究问题的纪律：**问行为与动机，不问愿望**。"你希望有什么功能"是废问题，"上一次你怎么做的"才是问题。每个 RQ 必须能被判死——判不死的问题不是研究问题，是自我安慰。

### B.2 方法选择与理由

- **选半结构化深访 + 轻量现场回溯**（请对方打开自己的工作台讲最近一条会话）。理由：RQ1/RQ3/RQ4 都是"人在压力下怎么决策"，只有追问才挖得到；问卷拿不到"当时我在想什么"。
- **不选问卷**：问卷要 100+ 有效样本才有统计意义，你一个人拿不到；且态度不等于行为，"我会遵守门禁"这种答案毫无价值。
- **样本量 5–8 人**：Nielsen 的经典结论是 5 人能发现约 85% 的可用性问题；深访的收敛判据是**同一主题在 3 人以上独立出现，且最近 2 场不再冒新主题**。低于 5 人只能叫"早期信号"，不能叫"洞察"。
- **不做日记研究 / 大样本卡片分类**：成本超出单人项目。卡片分类只作为**访谈内的探针**用（B.5 P2），不作为独立研究。
- **Probe 与 Signal 的关系**：理想是深访挖根因 + 工单大样本验频次。你**没有工单权限**，所以 Signal 这条腿现在是断的——诚实写"频次结论待大样本验证"，不要拿 8 人样本说"X% 的客服"。

**激励与邀约**：30–45 分钟，50–100 元红包或等值礼品（**自定预算，非行业标准**）；给对方的回报是一份脱敏的《售后判定自查清单》。时间段避开大促与晚高峰，选 10:00–11:30 或 14:00–16:00（客服排班空档）。

私信话术（三句，可直接发）：
> "您好，我是做产品研究的个人，不是商家也不是推销。我在研究售后客服'哪些话敢发、哪些话不敢发'，想请您聊 30–45 分钟，有 50 元感谢费。全程不碰您的客户信息，也不问店铺经营数据，只聊您怎么处理售后。方便的话我按您的排班约时间。"

**诚实降级路径**：0 人 → 只做 Part E，作品集写"专家走查 + 工程验证"；1–2 人 → 标"早期信号"；3–4 人 → 标"假设，待扩样"；5–8 人 → 才能写"访谈样本中 N/M 人提到"。

### B.4 访谈大纲（五段式，可直接照着念）

**第 1 段 暖场（5 分钟）**
1. 感谢您抽时间。今天大概 45 分钟，聊您平时怎么处理售后，**没有对错答案**，我不是来考核您的。
2. 先问一句：我可以录音吗？只用于我自己整理，客户信息一律不记，30 天内删除。（授权话术见 B.7）
3. 您做售后多久了？现在这家店主要卖什么类目？
4. 您一天大概接多少条会话？高峰在什么时候？
5. 您平时用哪个后台？电脑还是手机？
- 追问句："能具体说说吗？" / "还有呢？"
- 错误示范："您是不是觉得售后特别难做？" → 正确示范："您做售后这段时间，最花精力的是哪一块？"

**第 2 段 真实场景回溯（15 分钟）——本段是全场重心**
1. 请您想**最近一次**让您觉得棘手的售后，不用挑最典型的，就最近那次。客户说了什么？
2. 您当时第一句回的是什么？为什么先说这句？
3. 您当时查了哪些东西？在哪个页面查的？查到了什么、没查到什么？
4. 这件事最后怎么收的？客户满意吗？您有没有被组长或质检说过？
5. 如果重来一次，您会在哪一步做不一样的动作？
- 追问句："您说'查了一下'，具体是点开哪个页面？" / "那句话您发出去之前，犹豫过吗？犹豫的是什么？" / "后来发生了什么？"
- 错误示范："一般来说你们怎么处理退款？"（问概括，得到的是官方话术）→ 正确示范："上一次退款没到账，您具体做了什么？"
- 错误示范："您会不会因为怕投诉就先答应客户？"（把答案递给对方）→ 正确示范："您当时决定这么回，考虑的是什么？"

**第 3 段 具体行为深挖（20 分钟）**
1. 您有没有过"其实不太确定，但先答应下来"的时候？最近一次是什么情况？（RQ1）
2. 客户问"退款怎么还没到账"，您怎么判断是慢还是根本没生成？您会去查退款单号吗？（RQ3）
3. 客户问"换货什么时候发出"，您上一句已经说了"在处理中"，后来发现单没建，您怎么办？（RQ3/C6）
4. 什么情况下您必须转给组长？转的时候您会带哪些信息过去？（RQ4）
5. 店里有没有话术库或知识库？您遇到库里没有的问题怎么办？谁去补？（RQ5）
6. 您被考核什么指标？回复时长、满意度、还是品退率？哪个最让您紧张？（RQ2）
- 追问句："为什么那时候敢答应？" / "如果不答应，您担心发生什么？" / "您刚才说'按规定'，规定写在哪？"
- 错误示范："如果有个系统能在发送前拦住您，您会用吗？"（让人预测自己行为，答案不可靠）→ 正确示范："上一次您被质检拦下来，您当时怎么处理的？"
- 错误示范："您希望 AI 帮您做什么？"（追逐解决方案）→ 正确示范："您刚才说那一步很烦，烦在哪？"

**第 4 段 概念反馈（10 分钟）——必须放在最后，先看会污染前面所有回答**
1. （先不给看原型）"如果有个东西在您点发送之前拦一下，您觉得它**最该拦什么**？"
2. （给看 C1 一屏）"您看这张卡片，您觉得它想让您做什么？您会照着做吗？哪一步您不会做？"
3. （给看 C6 一屏，指出上一句客服已说"在仓库处理中"）"系统在这里拦住了，您觉得这是帮了您还是给您添麻烦？"
4. "卡片上这段话，您能直接发给客户吗？如果不能，您会怎么改？"（验证 `_ask_text` 是内部说明还是客户话术）
5. "如果它拦错了，您会怎么办？"（RQ4，绕过路径）
- 追问句："您说'没用'，是哪一部分没用？" / "您期望这里出现什么？"
- 错误示范："您觉得这个设计好不好？"（社会赞许偏差，对方一定说好）→ 正确示范："您刚才看了 5 秒没说话，那 5 秒您在找什么？"
- 错误示范："这个拦截是不是很有价值？" → 正确示范："这一屏对您明天的工作有什么用？没有的话也直说。"

**第 5 段 收尾（5 分钟）**
1. 有什么我没问到、但您觉得我该知道的？
2. 您身边有没有做售后的同行愿意聊？（滚雪球，但标注来源）
3. 我整理完能不能再找您 15 分钟核对一下我理解得对不对？
4. 感谢费怎么给您方便？录音我 30 天内删，整理稿里您只会出现代号。

### B.5 探针（Probes）：4 个具体工具

| 编号 | 怎么做 | 记录什么 | 映射到原型哪里 |
| --- | --- | --- | --- |
| P1 逐句回溯 | "请打开您昨天最后一条会话，遮住客户信息，逐句讲您当时在想什么。" | 每一句客服回复前的**决策依据**：查了什么、没查什么、怕什么 | `Verdict.steps` 是否覆盖了客服真实的决策步骤；缺哪一步 |
| P2 卡片分类 | 20 条客户问题（12 条取自 31 条规则的 `question`，8 条是我自造的同义改写，**标注为研究材料**），请对方分三堆：敢直接答 / 要先查 / 必须转人工 | 分类结果与 `risk_level`、`FIELD_TRIGGERS` 不一致的条目；对方犹豫超过 5 秒的条目 | 不一致项 → 改 `risk_level` 或补触发词；犹豫项 → 说明判定边界模糊 |
| P3 两条回复二选一 | 给 C1 的两条回复：A「退款 1–3 个工作日到账」B「这笔退款单没有生成，需核实是否落库或重新提交」。问："**哪条您敢发出去？为什么？**" | 选 A 的理由（时效压力/客户情绪/考核）；选 B 但要求改写的措辞 | C1 的 `counterfactual` 是否成立；`_ask_text` 的客户可见话术 |
| P4 代价排序 | 给三张卡：七天无理由 ¥0 / 换货 ¥12 / 品质退货 ¥24（计品退率）。先问"您平时会选哪个"，再问"如果考核按品退率扣分，排序会变吗" | 两次排序的差异；对方是否知道品质退货计商责 | A 场景的代价模型是否讲对了人；¥12 假设值要不要换成真实运费口径 |

探针纪律：**P3 不要问"哪条更好"，要问"哪条您敢发"**。"好"是态度，"敢发"是行为。

### B.6 反偏见提示（访谈者必须警惕的 7 条）

1. **社会赞许偏差**：对方会说"我们从不乱承诺"。对策：不问规范问实例——"最近一次例外是什么？"；强调不是考核、不告诉店长。
2. **引导性提问**：把答案藏在问题里（"您是不是觉得查退款单很麻烦？"）。对策：问题里不出现形容词与结论，只出现动作。
3. **把假设当事实**：你的主张是"成本在答得没依据"，这是**待验证假设**。对策：每场访谈前把 RQ1–RQ5 的证伪条件读一遍，主动找反例。
4. **只听极端用户**：被赔付过的客服会给你最生动的故事，但那是尾部。对策：配额里必须有"没出过事的普通客服"，结论按 N/M 写，不按音量写。
5. **把自己的方案当需求**：对方说"要是有个拦截就好了"，不要立刻问"拦截应该长什么样"。对策：先问"你为什么想要它/上一次没有它发生了什么"。
6. **救场与沉默**：对方卡住时不要替他说完。对策：默数 5 秒，再问"您现在在想什么？"
7. **附和与同情**：不要说"对呀这太烦了"。对策：只回"嗯""然后呢"，保持中立，否则后续回答会向你倾斜。

## Part C｜归纳方法

### C.1 亲和图法：具体七步（不是概念）

1. **拆观察点**：把每场记录拆成"一句话一个点"，一张便签一个点。原话与行为分开写。5 场访谈通常拆出 120–200 个点（**这是操作预期，不是本项目数据**）。
2. **摊开**：用在线表格或桌面便签，全部可见，不要按参与者分栏——按参与者分栏会让你只看到"某个人说了什么"，看不到"多少人说了同一件事"。
3. **静默分组**：不预设标签，只按相似性移动便签。单人做法：先自己分一轮，**隔一天再分第二轮**，两轮差异大的地方就是你主观投射的地方；有条件请一个朋友盲分第三轮。
4. **命名主题**：用"谁 + 在什么场景 + 遇到什么"命名，例如"一线客服在退款未落库时缺少可查入口"。禁止用"体验不好""效率低"这种空名字。
5. **量化频次**：每个主题写 **N/M**（M 个参与者中 N 个提到），不写百分比。
6. **标情绪强度**：low / medium / high，依据原话用词与语气。排序用 **频次 × 情绪强度**。
7. **饱和度判读**：同一主题 3 人以上独立出现、且最近 2 场无新主题 = 基本饱和；否则标"未饱和，早期信号"，并写明还差几人。**未饱和也允许出报告，但标题必须带"早期信号"。**

### C.2 从访谈到"高频体验问题 + 受影响流程"的归纳路径

路径：**观察点 → 主题（N/M + 情绪）→ 痛点（blocker/major/minor）→ 定位到流程环节 → 落到判定层的具体改动**。

本项目的流程环节清单（归纳时往这 9 个格子里放，不要自创）：
会话接入 → 意图识别 → 风险词判定 → 规则冲突 → 查订单 → 本轮缺字段 → 知识匹配 → 发送门禁 → 转人工与知识缺口闭环。

### C.3 JTBD 提炼模板 + 两个示例

模板：**当【context 场景】，我想【job 要完成的任务】，让我能【outcome 期望结果】。**
每条 JTBD 必须挂：支持主题编号、对应字段、**证伪条件**、证据状态。

**示例一（C1 退款进度）——假设示例，待访谈验证，不是访谈结论**
> 当客户说"退款申请提交三天了还没到账、急着用钱"时，我想先确认这笔退款单到底有没有生成，让我能给出一个不会在一周后被打脸的答复，而不是先安抚再被二次投诉。
- 对应字段：`refund.refundNo` 为空 + `refund.status = submitted_not_created`；`FIELD_TRIGGERS["退款单号"]`
- 证伪条件：若访谈发现客服后台能一眼看到退款单状态、"未落库"根本不构成困惑，则这条 JTBD 不成立，C1 的价值要重述。

**示例二（C6 换货）——假设示例，待访谈验证，不是访谈结论**
> 当客户问"换货什么时候发出"、而我上一句已经说了"在仓库处理中"时，我想在承诺兑现不了之前知道换货单没落库，让我能主动改口，而不是 48 小时后被追着问。
- 对应字段：`afterSale.type = exchange`；`missingFields = ["换货单号"]`
- 证伪条件：若访谈发现客服说"在处理中"是店里公认的安抚话术、客户与组长都不当真，则"拦住已说出口的承诺"这个主张需要降级为"减少误解"，不能再讲"避免赔付"。

### C.4 怎么把归纳结果回填到判定层（四个具体例子）

以下"访谈里可能听到什么"全部是**假设句式，不是真实引言**，用来演示回填路径。

| 改动类型 | 假设听到什么（待验证） | 具体改哪里 | 怎么验 |
| --- | --- | --- | --- |
| **新增规则** | "运费险怎么理赔"问得很多，但 31 条里没有 | 在 `data/knowledge_base.json` 续一条 `售后规则-015`（现有编号只到 014），填全 `conditions / answer / risk_level / triggers` | 在 `test_policy.py` 加一条用例，期望 **16 通过 / 0 失败**（原有 15 条 + 新增 1 条，与手册练习 1 同口径） |
| **改 FIELD_TRIGGERS** | 客户说"钱怎么还没回来"，系统答非所问 | `FIELD_TRIGGERS["退款单号"]` 现为 `["到账","退款","退钱"]`，补真实语料里的说法（如"钱没回来"）。**词必须来自访谈/工单，不能自己编了当证据** | 现场复算：该句 + C1 订单应回到 `need_info`（退款单号），而不是现在的 `no_knowledge`（见 E7-1） |
| **改风险词** | 客户说"我要去黑猫投诉"，系统没拦 | 风险词表实际在 `engine.py` 的 `HANDOFF_KEYWORDS`（**16 个词**：消协/12315/律师/赔钱/赔偿/补偿/投诉/曝光/仅退款/过敏/烂脸/起痘/刺痛/骗子/垃圾/差评）。FACTS 第四节以 RISK_WORDS 列了 8 个代表词，讲的时候用代码口径 | 加一条用例：整段对话含新词 → `blocked` 且 `handoff_reason = high_risk` |
| **改追问话术** | "卡片这段我没法直接发客户，它是写给我看的" | `policy._ask_text()` 的"换货单号"分支现在输出"这笔 X 的换货单没有落库…不能按'在仓库处理中'口头承诺"——这是内部说明。改为**双段**：给客服的动作说明 + 可直接发客户的追问句（含字段名 + 不能答的原因 + 下一步） | 加断言：`need_info` 的 ask 文本含"请您提供/确认"类客户可见句；并跑 Part D 的 T2/T3 复测 |

### C.5 归纳纪律

- 不下"X% 的客服"这种量化结论，只写"8 人中 6 人提到"。
- 1–2 人提到的极端体验（如一次大额赔付）**也要记**，不能因为频次低就埋掉；标注"低频高危"。
- 每条洞察必须挂：原话 + 频次 + 情绪强度。没有原话的洞察是你的想象。
- 与假设矛盾的证据**优先写**，它比支持证据值钱；所有未验证项一律标"待验证"，包括本文的 JTBD 示例与回填例子。

## Part D｜可用性测试方案（Test：验证原型好不好用）

### D.0 前提与诚实边界

- **尚未执行**。以下是剧本，不是结果。任何成功率、时长、卡点数字都必须实测后才填。
- 参与者 5 人（一线客服 3 / 组长 1 / 店主或知识维护 1），moderated 远程（腾讯会议或飞书共享屏幕），单场 45 分钟，**正式测前必跑 1 场 pilot** 调剧本。

### D.1 任务剧本 T1–T5

**T1｜C3 物流停滞（正常发送）· must · 预计 6 分钟**
- 念给用户的话："这位客户说快递五天没动，他等着用。请您按平时的习惯处理这条会话，处理到您觉得可以告一段落为止。"
- 起点：工作台默认选中 C1，需自己在左栏找到 C3（刘先生 V1 / 物流 / 优先级高）。
- 成功标准：① 找到 C3；② 说出回答里引用的运单尾号 **8873** 与"沈阳转运中心 4 天没更新"（**注意是 4 天不是 5 天**：客户原话说五天，系统按 `lastNodeAt` 算出 4 天，话术采用字段口径——参与者若说"客户明明说五天"，这正是 T2 要观察的心智模型冲突，记原话不要纠正）；③ 点"发送回复"；④ 发送后能说出"现在等客户回复，不能连发第二条"。
- 预期路径：左栏选 C3 → 读右侧卡片（可发）→ 展开"它是怎么判出来的" → 草稿已预填 → 直接发送或先点"采纳并填入" → 状态转等待客户。
- 已知易错点：草稿**已预填**，不点"采纳并填入"直接发也算采纳（`cb_send` 逻辑），用户可能纠结要不要先点采纳；发送后按钮禁用可能被误认为故障；话术结尾"需要我现在提交登记吗"是**征询**不是已完成，用户可能误读为系统已登记。

**T2｜C1 退款单没生成（发现根因）· must · 预计 8 分钟**
- 念给用户的话："客户说退款申请提交三天了还没到账，急着用钱。请您处理这条会话，并告诉我您下一步准备做什么。"
- 起点：工作台默认选中 C1（周女士 V3 / 老客 / 高客单）。
- 成功标准：① 说出根因是"退款单没生成"而不是"到账慢"；② 指出缺的字段名（退款单号）；③ 不发送（按钮禁用）；④ 说出下一步是核实落库或引导客户重新提交。
- 预期路径：读卡片"信息不足" → 读缺失字段说明 → 展开判定步骤看到"退款单号为空" → 看"如果没有这道判定" → 尝试发送发现禁用 → 口述下一步。
- 已知易错点：卡片文案是**内部说明口吻**（"需核对该笔退款是否落库"），用户可能找不到"能直接发客户的话"；用户可能手打一句"1–3 个工作日到账"试图绕过——**重点观察他是否知道这样也发不出去**（`can_send` 还要求 `verdict_can_send`）；这是 RQ4 的行为证据。

**T3｜C6 换货单未落库（识别已说出口的承诺）· must · 预计 8 分钟**
- 念给用户的话："这条会话里，您的同事已经回复过客户一句话了，客户还在等。请您接着处理。"
- 起点：左栏选 C6（吴先生 V1 / 换货 / 优先级低）。
- 成功标准：① 注意到上一句客服说了"在仓库处理中"；② 说出换货单没落库、不能报出库时间；③ 不发送；④ 说出要不要改口、怎么改口。
- 预期路径：读对话气泡里的客服上一句 → 读卡片"信息不足 · 缺换货单号" → 对照"如果没有这道判定" → 判断前一句承诺不可兑现。
- 已知易错点：用户可能认为"系统和同事说的矛盾"是 bug 而不是拦截；C6 的首条依据是 **售后规则-005（可以换货吗）**，与"换货单未落库"不同题，用户可能觉得依据不对——这是真实可观察的困惑点，不要替他解释。

**T4｜C4 高风险（转人工）· should · 预计 6 分钟**
- 念给用户的话："这位客户情绪比较激动。请您处理这条会话。"
- 起点：左栏选 C4（赵女士 V2 / 老客 / 投诉历史 / 优先级紧急）。
- 成功标准：① 判断不能由一线回复；② 找到"转人工处理"；③ 原因选"高风险：投诉/法律/舆情"（默认已预选 `high_risk`）；④ 说出归属是客服组长；⑤ 知道转人工后本会话不再由 AI 建议驱动。
- 预期路径：读对话（含"退一赔三""12315""发微博"）→ 卡片高风险拦截、发送禁用 → 看风险提示 → 转人工原因下拉 → 点转人工。
- 已知易错点：转人工后状态变 `handed_off`，"转人工处理"按钮随即禁用，用户可能重复点击以为没生效；**风险提示条数来自实时命中词，与 `mock-data.json` 里 C4 的 3 条 `riskFlags` 不一定相等**（`riskFlags` 是旧版遗留，不参与界面判断），不要拿它当期望值。

**T5｜C7 知识不足（登记缺口）· should · 预计 7 分钟**
- 念给用户的话："客户问能不能开发票，他要报销。请您处理这条会话，并且想办法让这个问题以后不再重复出现。"
- 起点：左栏选 C7（郑先生 V1 / 发票 / 状态已转人工）。
- 成功标准：① 说出知识库没有发票规则；② 说出归属是知识库管理员；③ 对"怎么让以后不再重复"给出动作或明确指出当前做不到。
- 预期路径：卡片知识不足 → 归属知识库管理员 → 找登记入口 → （很可能找不到）→ 口述替代方案。
- 已知易错点（**代码已确认的设计缺口，不是用户能力问题**）：C7 初始状态就是 `handed_off`，"转人工处理"按钮**已禁用**，用户可能无路可走；卡片文案本轮已改为"可转人工；知识缺口登记尚未实现"（不再承诺不存在的按钮），但 `Verdict.actions` 里的"登记知识缺口"**仍未渲染**，所以"该找谁"只是一行归属文字，不是可点的动作。若用户卡在这里，记为 finding，**不要提示他"其实没有这个功能"**，先问"您期望这里有什么？"

### D.2 主持人脚本

**开场（逐字稿）**
> "今天我们测的是这个产品，不是您。您卡住、觉得难、觉得没用，都是产品的问题，不是您的问题。我是做这个原型的人，所以您骂它我完全不会介意，反而最有用。接下来 45 分钟，5 个任务。请您**边操作边把心里想的说出来**，包括'我不知道下一步该干嘛'——这句话对我特别值钱。我先演示一下：我现在想找这条会话，我会点这里，因为它写着物流……明白了吗？另外这个原型是本地跑的，刷新页面记录会清空，这是它的限制，不是您操作错了。"

**任务介绍模板**
> "我现在给您一个场景：【念任务描述】。您看到屏幕上这些，接下来您会怎么做？请假装我不在您旁边，不要问我'该点哪里'，按您自己的想法来。"

**卡住了怎么办（三级提示，每级都要记 assist）**
1. 先**沉默 30 秒**，只观察，不出声。
2. 中立追问："您现在在想什么？" / "您期望接下来发生什么？" / "您看到什么让您这么做？"
3. 仍卡住 → 给**最小提示**（只指方向不给答案："右边那一栏您可以再看看"），并在记录里标 `assists=1`，该任务成功度降为 partial。

**什么时候闭嘴**：用户问"这个是干嘛的" → 不解释，反问"您觉得它是干嘛的？"；用户走错路径 → 不纠正，让他走下去看会发生什么；用户骂设计 → 不附和、不辩护，只回"嗯"；用户沉默 → 不救场。

**收尾 debrief（4 问）**：整体哪里最难、哪里最顺？如果只能改一处您改哪？和您平时用的后台比有什么不同？有什么我没问到但您想说的？

**主持人反偏见 6 条**：救场偏见 / 引导偏见 / 解释设计 / 附和偏见 / 任务介入 / 替用户总结。逐条对照 B.6 执行。

### D.3 观察记录表字段与成功度分级

| 字段 | 取值 / 说明 |
| --- | --- |
| participant_id / segment / date / duration_min | P1 / 一线客服 / 日期 / 实际分钟 |
| task_id | T1–T5 |
| success | success / partial / fail / skipped |
| time_to_complete_sec | 从念完任务到达成成功标准 |
| errors | 走错路径次数（点错会话、找错按钮） |

| verbatim_quotes | **逐字原话**，禁止改写 |

成功度四档：**success** 无帮助一次走通全部标准；**partial** 绕路/用了提示/只完成部分标准；**fail** 放弃或主持人叫停；**skipped** 技术故障或用户拒绝。
量化口径：按任务聚合成功率、均时、平均错误、求助率。**成功率 < 70% 或求助率 > 30% 的任务，必出 3 级以上 finding**。样本 < 5 人时只写"早期可用性信号"，不写百分比结论。

### D.4 严重度评级（Nielsen 0–4 级，例子均为**预判，待实测确认**）

| 级 | 名称 | 定义 | 本项目预判示例 |
| --- | --- | --- | --- |
| 4 | catastrophic 灾难性 | 核心任务无法完成 / 数据丢失 / 无依据内容被发出 | `need_info` 或 `blocked` 态下"发送回复"仍可点（15 条用例覆盖了 `can_send` 不变式，但界面还叠加了草稿非空与会话状态条件，**必须人工点**） |
| 3 | critical 严重 | 能完成但需大量帮助 / 严重挫败 | T5 知识缺口无登记入口，且 C7 转人工按钮已禁用（F-A3，代码已确认） |
| 2 | major 主要 | 反复出现、影响效率，用户能自己绕过 | 五态标签三处不一致（F-A1）；同义说法归因错误把客服引向错误接手人（E7-1） |
| 1 | minor 轻微 | 偶发，不影响完成 | 知识依据全部显示"适用 …"而非更新时间——31 条规则**都没有 `updated_at` 字段**，客服无法判断规则是否过期 |
| 0 | cosmetic 外观 | 视觉细节，无功能影响 | chip 颜色与间距、卡片留白 |

判定纪律：**严重度不只看频次**。1 人遇到的 4 级也必须修；6 人遇到的 0 级仍是 0 级。建议两人独立打分后讨论（单人项目就隔一天再打一次，对比差异）。

### D.5 修复优先级排序方法

1. **频次 × 严重度矩阵**：3–4 级 + 频次 ≥ 50% → P0 立即修；3–4 级 + 低频 → P1 上线前修；2 级 + 高频 → P1；2 级 + 低频 → P2；0–1 级 → P2/P3 批量修。
2. **按 vertical slice 四层排修复顺序**，映射到本项目文件：
   - foundation（地基）：`policy.py` 的单一事实源、状态标签字典统一 → F-A1 / F-A2
   - core-ui（主路径组件）：`app.py` 建议卡与门禁按钮 → F-A3 的入口缺失
   - interactions-states（状态与异常）：空态、`error` 兜底、审计持久化 → F-A2
   - polish（文案与视觉）：退货原因页说明文案 → F-A4
3. 每条修复标 **reuse / modify / create** 与 **depends_on**：F-A1 是 foundation，不依赖别的；F-A3 的按钮依赖 `Verdict.actions` 已存在（reuse 即可，成本最低）；F-A5 要把 A 场景接回 `Verdict`（modify，依赖 foundation 先稳）。
4. **P0 ≥ 5 条时先试制 1–2 条**，找 2–3 位新参与者快跑一轮 RITE 复测，确认方向再批量改。
5. 每次改完必须跑 `python test_policy.py`（不改用例数时期望 **15 通过 / 0 失败**；每新增一条用例，期望通过数就 +1，加 1 条 = **16 通过 / 0 失败**）+ `python -m py_compile app.py policy.py engine.py llm.py test_policy.py`，改了 JSON 重启 Streamlit。

### D.6 访谈与测试的先后取舍（单人项目必须想清楚）

同一批人先访谈后测试会**互相污染**：访谈第 4 段已经看过 C1/C6，测试时他就不是"第一次见"了。三种可选：
- 最优：两批人，访谈 5–8 人、测试另招 5 人。
- 次优：同一批人，**先测后访**（T1–T5 做完再进访谈大纲），并把访谈第 4 段改为"回顾刚才哪一屏您最不确定"。
- 兜底：只能约到 3 人 → 先测后访，全部结论标"早期信号（3 人）"。

## Part F｜给初学者的方法论小结

1. **给证据分等级，别把工程验证当用户价值。** 用例证明自洽，模拟数据证明形状，访谈证明动机，可用性测试证明好用，上线数据证明收益。五级不能互相冒充。
   - 今天就能做：在 README 第 5 节加一行"当前证据等级：工程验证 + 代码走查；用户证据缺口：访谈 / 工单 / 可用性测试"。
2. **没有用户资源时，诚实本身就是加分项。** 不要假造访谈。把"我知道缺什么证据、我知道怎么补、我已经补了不依赖用户的那一部分"写成一页，这比编三段用户引言强十倍——编的引言经不起一个追问："这位客服叫什么、在哪家店、哪天聊的？"
   - 今天就能做：把 A.5 那段 60 秒答法背下来，对着手机录一遍，回听删掉所有没有证据支撑的形容词。
3. **先做不依赖用户的走查，再花钱约人。** 专家走查能发现三到五成问题，成本是零。把明显矛盾清掉再让真人测，才不会浪费宝贵的 5 个参与者。
   - 今天就能做：勾完 E1 与 E2 两组（共 7 项），每项留一张截图，把 F-A1 的三处标签统一成一个词，然后跑 `python test_policy.py` 确认仍是 15 通过 / 0 失败。
4. **问行为，不问意愿。** "您会用吗"得到的是礼貌，"上一次您怎么做的"得到的是事实。所有探针都要落在具体一次事件上。
   - 今天就能做：把 B.4 大纲里所有含"会不会/想不想/觉得好不好"的句子改成"上一次…您具体做了什么"。
5. **每条洞察挂证据链，未验证的一律标"待验证"。** 原话 + 频次 N/M + 情绪强度，三样缺一就不叫洞察。小样本不下百分比结论。
   - 今天就能做：把 C.2 那张空归纳表建好，**只写表头不填数据**，并在文件名里写上"待访谈后填写"。

**四件不要做的事**：不要假造访谈记录与用户引言；不要把 88% 说成"AI 准确率"或"上线提升"；不要声称已上线、有真实用户、有业务收益；不要把模型说成决策者（它只改写 `ready` 态的措辞，自报 state 被丢弃，当前 key 无效、实际跑本地兜底）。
