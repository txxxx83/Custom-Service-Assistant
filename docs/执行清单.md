# 执行清单（最终版）

> 产品主张：**把"不确定"变成可交付的动作**——追问、转人工、禁发，并让商家看得见为什么。
> 卖的是**状态模型与产品判断**，不是"我做了一个系统"。
> 版本：2026-11-12。上一版差异见文末。

---

## 零、三条不动摇的判断

| 判断 | 依据 |
|---|---|
| 5 条证据 → **3 类痛点**（说错话商家付钱 / 办错事商家被罚 / 不敢用等于没有） | 证据是现象，痛点是由现象归纳出的损失；并列的痛点没有主次 |
| **只做穿 2 个场景**，且 A 是主、B 是 A 的分支 | 10 天做 2 个能穿；做 5 个就是 5 个半成品 |
| 卖的是"什么时候该闭嘴"的**判定**，不是界面 | 判定可回归测试，界面谁都能做 |

## 一、数据与判定（第 1–3 天，地基，不做完下面全是空的）

- [ ] **`data/orders.json`**：7 张订单
  字段：订单号、SKU、规格（尺码）、支付时间、发货时间、物流状态+节点时间、退款申请时间、**退款单号（故意 1–2 张为空）**、支付渠道、是否拆封、客户申请原因
  *为什么*：现在订单只是对话里的一句旁白，程序取不到字段。没有字段，"退款三天没到账"只能背政策；有了字段才能判断"退款单根本没生成"。

- [ ] **`data/policies.json`**：把 30 条知识里可判定的部分抽成结构化规则
  例：退货窗口 7 天、品质退货需证明、拍错码属无理由、赔付类表述禁止、时效按渠道（微信 1–3 / 银行卡 3–7）
  *为什么*：知识库是给人读的散文，判定要的是字段。混在一起，"匹配"就退化成字符重合——82% 的来源就是这个。

- [ ] **冻结 `data/knowledge_base_v3.json`**
  *为什么*：50 条评测要可复现；改库会让附录里的 88% 自相矛盾。

- [ ] **补齐或删除 C5/C7 的悬空数据**
  *为什么*：演示时点到没内容的会话最露馅。

- [ ] **`policy.py` 五态**：`ready / need_info / conflict / no_knowledge / blocked`
  *为什么*：四态里"缺条件"没有位置，而售后最高频就是缺条件。缺条件时给建议＝猜，直接转人工＝浪费一次追问。

- [ ] **固定判定顺序**：查单 → 查政策 → 查冲突 → 查风险 → 出口
  *为什么*：顺序一变结论就变，必须写死，才能被回归测试、被复述。

- [ ] **结构化输出**：`state / reason_code / missing_fields / cited_kb_ids / draft`
  *为什么*：界面、审计、评测三处消费同一份结果，才不会"卡片说能发、门禁说不能发"。

- [ ] **LLM 只做措辞，不做判定**；无 key 用模板兜底
  *为什么*：模型不能保证可回归。"为什么不用 LLM 判定"是必被追问的问题，这个答案有分量。

## 二、两条场景（第 4–5 天）

### 场景 A（主案例，占一页纸 80%）：拍错货 ≠ 品质退货

- [ ] 客户："我买错码了，想换 39 的"
- [ ] 系统必须同时用三样：订单事实（买的是 38）+ 政策（拍错码走 7 天无理由换货）+ 取舍（选品退最省事，但商家被罚）
- [ ] 若客户坚持退货且已拆封 → `conflict` 或 `no_knowledge`，不猜

*为什么*：这是 5 条证据里唯一有数字的痛点（一月几十单品退、运费上千），也是唯一"话术审核拦不住、必须读订单"的场景。

### 场景 B（A 里的一个分支按钮，三行带过）：参数缺失就不报数

- [ ] 客户："一斤大概多少个？" → 该商品 `spec` 字段为空 → 不回数字，回 `need_info`，同时把缺口写进知识缺口清单
*为什么*：直接复现图 01；证明"不知道就说不知道"是可执行机制，不是口号。**不单独立场景**，否则稀释 A。

## 三、演示装置（第 6 天）

- [ ] **查询结果显式列出**：查了哪张单、取了哪几个字段、算出几天、退款单号有无
  *为什么*：这是"能办事"的唯一证据，也让面试官能当场验证。
- [ ] **发送门禁读同一判定**
  *为什么*：单一真相源。
- [ ] **DemoConsole**：4–5 个按钮强制切五态
  *为什么*：90 秒演示不能靠碰巧点到；让面试官自己按，他才信。
- [ ] **转人工带上下文与原因**（对应证据 05）
  *为什么*：现在转人工是假动作；"转接断链"正是商家宁可关客服的原因之一。
- [ ] **实时问答降到 `?dev=1`**
  *为什么*：开发工具不是产品，摆在外面稀释主张。

## 四、叙事（第 7–8 天）

- [ ] **一页纸案例 PDF**，顺序固定：
  1. **为什么非得是个产品**（先发制人：SOP+提示词能解决一半，产品不可替代的是"字段在订单里、政策会变、出事要留痕、判定可回归、责任有归属"）
  2. 问题与证据（5 条 → 3 类痛点 + 对账表：已解决/未解决/为什么）
  3. 场景 A 走一遍（含一次拦截与一次追问）
  4. 五态与判定顺序（状态机图）
  5. 基线表与验证结果
  6. 边界：不接真接口、数据是造的、样本局限
  *为什么*：HR 和面试官只看这一页，其余都是附录。

- [ ] **基线表**（一页）
  | 指标 | 估算 | 来源 / 假设 | 置信度 |
  |---|---|---|---|
  | 单店月品退单量 | 20–50 单 | 评论"这月帮我品退大几十单" | 中 |
  | 单次赔付 | 15–30 元 | "赔付运费快上千了" ÷ 20–50 | 中 |
  | 单店月直接损失 | 400–1,500 元 | 上两行相乘 | 中 |
  | 该类咨询占比 | 10–20% | **无来源，标为假设** | 低 |
  | 人工处理一单 | 3–8 分钟 | 需 1 位客服确认 | 低 |
  | 现有处理方式 | 关闭智能客服 / 全人工 / 事后申诉 | 评论 03/04 | 高 |
  *为什么*：没有基线，"商家被罚"就还是形容词。**每一行写来源与置信度**，标"低"的自己先说出来，比编精确数字可信十倍。

- [ ] **README 重写**：怎么跑、数据是造的但结构真、接不了接口、评测是附录
  *为什么*：第一屏决定他信不信。
- [ ] **90 秒视频**
  *为什么*：投递时不可能让人装环境。
- [ ] **状态机一页图**
  *为什么*：五态迁移最容易被追问，也最能显示严谨。

## 五、验证与收尾（第 9–10 天）

- [ ] **价值验证（替代原"实现验收"）**：10 条真实问法 × 裸模型 / 有闸门各跑一遍，人工判错误类型
  *为什么*：准确率可能不变甚至下降，但**致命错误（越权承诺、引导错因）归零**——这才是价值。原验收只证明"按设计工作"。
- [ ] **5 人可理解性走查**，只问一句："你能说出它为什么停吗？"
  *为什么*：直接测核心主张（可解释）。**标注：不是用户验证。**
- [ ] **1 位真客服 + 2 位商家访谈**（有就放附录，没有就口头讲）
  *为什么*：硬凑 3 位客服＝编造；诚实标注样本局限反而是方法论成熟。
- [ ] **轮换已泄露的 DeepSeek key**，`secrets.toml` 不进仓库
  *为什么*：key 已在聊天记录出现。
- [ ] **统一术语**（品退 / 品质退货 / 无理由退货）
  *为什么*：术语混用被认为不懂业务，最廉价的失分。
- [ ] **清掉"剧本演示数据"这类自曝标签**
  *为什么*：要么在 README 一次说清，要么别在界面上反复提醒。

## 六、明确不做

| 不做 | 理由 |
|---|---|
| 接真实商家/物流接口 | 谁都做不到，作品集也不证明这个 |
| 登录、多客服、权限 | 与"该不该闭嘴"无关 |
| 数据大屏、动效 | 零信息量，吃两天 |
| Vue 重写 | 为显得专业而重写，是负分 |
| B 路线全量重构 | 现在缺的是数据和判定，不是架构 |
| 把场景 B 当独立案例 | 会稀释 A；A 有真实代价与激励错配 |

## 七、验收（已按 2026-11-12 拍板修订，原稿有 3 条错误）

**原稿的错误**：「我帮您重新提交」是越权承诺（系统无提交能力）；「买错码」与「一斤多少个」属服饰/生鲜，已锁美妆；「致命错误为 0」是统计过度（0/10 的 95% 上限约 26%）。

修订后的验收：

1. 挑「退款单号为空」的单：系统**不说**"我帮您重新提交"，说"未查到退款单，建议人工核实或引导您重新提交"（停在事实层）
2. 说「我买错色号了，想换 02」：走**无理由换货**流程，**不**引导品质退货；若客户改口要退且已拆封 → `need_info` 追问是否质量问题
3. 问「这瓶开封后能用多久」：该字段为空 → 不回数字，回追问并登记知识缺口
4. 问「敏感肌能用吗」：进 `blocked`（健康风险），**不**进 `need_info`
5. 卡片写的与发送按钮状态永远一致（同一判定源）
6. 10 条 smoke test 措辞：「本轮未出现致命错误，n=10，仅用于发现失败模式」
7. 一页纸里 5 条证据每条都标「已解决 / 未解决 / 为什么」+ 来源、类目

## 八、定稿拍板（2026-11-12，与上文冲突时以本节为准）

### 8.1 品类
- **锁美妆个护**。A＝买错色号想换；B＝开封后使用期限/容量缺失。
- 「敏感肌能用吗」**不进 B**：属健康风险，归 `blocked`，否则与 blocked 撞车，演示时必被问"这到底是缺信息还是高风险"。
- 跨类目证据（无花果=生鲜、保温杯=百货、评论=美妆）→ 标注：「仅用于归纳共性问题，**未做跨类目验证**」；每张截图标来源、类目、日期。

### 8.2 主张
- 「商家关掉 AI 不是因为不会用，是因为赔过钱」→ 改为**「是算过账：赔付与纠纷的成本，高于它省下的人力」**（证据证明成本，不证明关停原因）。
- 补一句范围说明：「一次判定不能证明商家会重开 AI，但它是重开的必要条件；我先证明闸门有效。」

### 8.3 冲突立场（推翻我原来的"站商家"）
- **不站边**。站**可举证的事实与平台规则**：规则内帮商家省，规则外不硬拦，规则不明转人工。
- 理由：① 帮商家拒赔，最后被罚的是商家；② "站商家"＝不确定就选一边，与"不确定就停"自相矛盾；③ 客服一旦觉得工具是甩锅工具，就不会用。
- 上下文包**两侧证据都写**；文案叫「判定依据」，不叫「免责理由」。

### 8.4 conflict
- 叫**机制演示态**，不叫"降级"；状态模型里保留。
- **4 真 + 1 演**：ready / need_info / blocked / no_knowledge 真实跑通；只有 conflict 演示。
- `no_knowledge` **不脚本化**——问「能开发票吗」即可真实触发。
- 附录原话：「知识库中真实冲突样本为 0，conflict 仅用于演示机制。」

### 8.5 验证与范围
- **10 条对照进必做**（×2 组 ×6 类错误，2–3 小时）；20–30 条是加分。至少 5 条刻意选难例。
- 措辞只能写「本轮未出现致命错误，n=10，仅用于发现失败模式」。
- **第 5 天 checkpoint**：若 policy.py + 数据层未跑通 → 砍 B、砍第五态，只留 A + ready/need_info/blocked，一页纸标「演示范围」。
- 固定砍单顺序：视频 → 5 人走查 → B → 第五态 → 第二场景。**永远保留**：A、一页纸、1 场访谈、10 条 smoke test。

### 8.6 数据
- 5 张核心订单：A / B / 退款未生成 / 已拆封 / 正常。已落地 `data/orders.json`（另加 1 张价保辅助单，理由见文件内 `whyThisOrder`）。
- 「查无此单」是**测试输入**，不是订单，放在 `demoTestInputs`，由 DemoConsole 注入。
- 查询三出口：查到 / 查无此单（need_info）/ 查询失败（显式报错，不进状态机）。

### 8.7 基线表补注
- 「单店自述，不是行业均值」
- 「这是运费赔付，不含货值；总损失更高但不估」

### 8.8 一页纸最终目录（8 节）
1. 一句话 + 场景
2. 证据与洞察（5 条 → 3 类痛点 + 对账；每条标来源和类目）
3. 为什么不是 SOP（**只留两条**：字段在订单里、出事要留痕；其余三点进附录）
4. 场景 A 走一遍（含「退货原因后果」那一屏：谁承担运费 / 是否计入品退率 / 是否触发处罚）
5. 状态模型（4 真 + 1 演；判定顺序；动作矩阵）
6. 基线与验证（标「单店自述」；10 条 smoke test）
7. 边界与反思（转人工只做一半、跨类目未验证、冲突样本 0）
8. 如果重做 / 什么会让我改变判断（各 3 行）

## 九、与上一版的差异

| 上一版 | 这一版 |
|---|---|
| 验收＝5 条"系统会不会做"（实现验证） | 验收＝10 条问法 × 2 组比**错误类型分布** + 5 人走查（价值验证） |
| 无基线 | 一页基线表（估算＋来源＋置信度） |
| 一页纸从"问题"开始 | 第一屏先答"**为什么非得是个产品**" |
| 场景 A、B 并列 | A 主、B 降为 A 的一个分支按钮 |
