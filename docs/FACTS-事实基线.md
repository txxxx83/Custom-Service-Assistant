# 项目事实基线（所有文档必须与此一致，不得编造）

核对时间：2026-11-12。核对方式：读代码 + 跑 `python test_policy.py` + 用 app.py 的同一条调用路径复算 7 条会话。

## 一、项目定位

- 路径：`D:\Desktop\产品\demo`
- 名称：电商售后 AI 客服 · **判定层**原型（不是"AI 客服机器人"）
- 技术：Streamlit + Python 标准库；无数据库、无后端服务、无真实接口
- 数据：**全部模拟**。类目锁定 **美妆个护**（单一类目，未做跨类目验证）
- 交付性质：**个人作品集 / 学习项目**，未上线、无真实用户、无真实业务指标
- 作者身份：产品经理初学者，一人完成（无研发/测试/运营团队）

## 二、核心主张（一句话）

> 售后客服真正的成本不在"答得慢"，而在"答得没依据"。
> 这个原型不做"更快地生成回答"，做的是**在回答发出前判定这句话能不能发**——
> 该追问就追问，该说不知道就说不知道，该转人工就转人工。

关键洞察（面试可讲）：**AI 的价值有时是拦住人已经说出口的承诺。**
例：C6 客服已说"在仓库处理中"，但换货单没落库，48 小时后无法兑现；判定层把它拦成 need_info。

## 三、五态（state）与门禁

| state | 中文标签（唯一来源 policy.STATE_LABEL） | can_send | requires_ack | 归属人 | 转人工原因 |
|---|---|---|---|---|---|
| ready | **可发建议** | True | False | 客服 | 无 |
| need_info | 信息不足 | False | False | 客服 | 无 |
| conflict | 规则冲突 | True（需勾选确认后才可发） | True | **客服（判断不了升级组长）** | conflict |
| no_knowledge | 知识不足 | False | False | 知识库管理员 | no_knowledge |
| blocked | 高风险拦截 | False | False | 客服组长 | high_risk |
| error | 查询失败 | False | False | 客服（保留人工入口） | other |

注意（归属人一列必须逐字照抄 `policy.OWNER_LABEL`，不要按直觉简写）：
- `ready` / `need_info` → 客服；`blocked` → 客服组长；`no_knowledge` → 知识库管理员；`error` → 客服（保留人工入口）；`conflict` → **客服（判断不了升级组长）**，不是"客服组长"。
- `conflict` 的 `can_send=True` 但界面必须先勾选"我已确认采用哪条规则"才解锁发送；`requires_ack=True` 是门禁条件之一。
- **ready 的标签是「可发建议」**，不是"可发送"也不是"可审核"。2026-11-12 已把 app.py 的 STATE_LABEL 改为 `{**policy.STATE_LABEL, "missing": "暂无建议"}`，标签只有一份。
- **error 态当前不可达**：policy.py 里只有标签/归属/原因三处映射提到它，`decide()` 没有任何分支产出 `state="error"`。文档应写"已定义但当前不可达的兜底态"，不要声称它在工作。
- `missing`（暂无建议）是**界面独有**的态，表示还没产出建议，不是判定结果。

## 四、七步判定顺序（policy.decide，顺序不可调换）

1. **识别意图**（detect_intent，按关键词命中数打分，不是字典顺序）
2. **对话风险词**（扫**整段客户发言**，命中即 blocked）
   - 唯一来源：`engine.HANDOFF_KEYWORDS`，**16 个词**
   - high（11 个）：消协 / 12315 / 律师 / 赔钱 / 赔偿 / 投诉 / 曝光 / 过敏 / 烂脸 / 起痘 / 刺痛
   - medium（5 个）：补偿 / 仅退款 / 骗子 / 垃圾 / 差评
   - 分级逻辑在 `policy._risk_hits()`
   - **注意**：`app.py` 里曾有一个 8 词的死列表 `RISK_WORDS`（含"退一赔三"），早已无人使用，2026-11-12 已改为 `RISK_WORDS = policy.HANDOFF_KEYWORDS` 别名。**不要再引用那个 8 词口径**。"退一赔三"本身不在词表里，那句测试用例是靠"12315"和"投诉"命中的。
3. **规则互斥冲突**（同一 conflict_group 命中多条 → conflict；high 风险规则必须在此之前或同层被拦住）
4. **查订单**（三个出口：查到 / 查无此单 / 查询失败）
5. **本轮真正需要的缺失字段**（FIELD_TRIGGERS × order.missingFields 求交集；无关缺字段不拦本轮）
6. **知识匹配**（无可引用规则 → no_knowledge）
7. **规则风险等级**（命中规则 risk_level=high → 不自动作答）
8. 出口 ready

> 代码里 `Verdict.steps` 第一步固定是"识别意图"，共 7 个判定步骤 + 出口。文档统一表述为"七步判定"。

## 五、单一事实源

`policy.decide(question, order_no="", kb=None, orders_doc=None, dialog="", as_of="") -> Verdict`

- 建议卡、发送门禁、转人工原因、审计日志**全部只读这一份 Verdict**
- `Verdict` 派生属性：`can_send` / `requires_ack` / `handoff_reason` / `badge` / `as_dict()`
- `Verdict.steps` 记录真实执行步骤，界面**渲染它**，不另写模板
- 历史缺陷：以前两处各写一套 if，导致"卡片说不可发、按钮却能点"
- **参数名坑（写脚本必踩）**：没有 `order=` 这个参数；`orders_doc["orders"]` 是**列表不是字典**，主键字段叫 **`orderId`**（不是 orderNo）；依据字典里的规则 ID 键叫 **`kbId`**（不是 ruleId / id）。

### 5.1 `as_of` 参考时刻（2026-11-12 新增，是本轮最重要的设计决策）

模拟数据没有真实时钟，所以判定需要一个"现在是几点"的锚点：

- `app.conv_as_of(cid)` = 该会话**最后一条消息的 `at`**
- `app.order_as_of(order_no)` = 该单所属会话的时刻；没选订单就用全局最后一条消息
- 两者传给 `decide(..., as_of=...)`，落到 `Verdict.as_of`

**为什么不用 `datetime.now()`**：那会让同一张单在不同日期跑出不同结论（七天窗口过期、停滞天数变化），演示就无法复现。面试可直接讲这句："判定必须可复现，所以我把参考时刻做成显式入参，而不是偷偷读系统时间。"

### 5.2 客户口径 vs 字段口径对账（第 15 条用例守的就是这条）

- 物流停滞天数**只能**由 `_days_between(v.as_of, order.logistics.lastNodeAt)` 算出
- `policy._days_mentioned()` 仍保留，但**只用于对账，不作为话术依据**
- 客户说的天数与算出来的不一致时，`Verdict.steps` 追加一步 **"核对客户口径"**，话术采用字段口径
- C3 实例：客户说"五天没动"，`lastNodeAt=2026-10-31T22:40` → 会话末条 `2026-11-05T10:35`，复算 **4 天**。现话术："您反馈运单尾号 8873 的包裹在沈阳转运中心已经 **4 天**没有更新，属于异常。按规则可以为您登记催件并转专员跟进；需要我现在提交登记吗？"
- 若 `lastNodeAt` 缺失 → 不编天数，写"节点更新时间缺失，算不出停滞天数，先按异常登记催件"
- **禁止**：话术出现"已为您登记"（登记动作未实现，只能问"需要我现在提交登记吗"）

## 八、订单即数据（这是"不是剧本"的证据）

关键字段 → 判定用途：
- `refund.refundNo` 为 null 且 `refund.status = submitted_not_created` → C1 不能按"在途"解释
- `afterSale.opened / used` → 是否拆封用过，决定七天无理由适用性

- `missingFields` → 与 FIELD_TRIGGERS 求交集，决定本轮是否 need_info
- `policyHooks` → 该单适用的店铺政策原文（K1–K6）

## 十、大模型边界（最容易被面试官戳穿的地方）

- 模型：DeepSeek（`llm.py`，HTTP 调用）
- **模型只改写 ready 态的措辞**，它自报的 state 在工作台里被**丢弃**
- 调用失败 → **静默回退**到本地 `compose_answer` 文案，判定结果不变
- `?dev=1` 的"实时问答（引擎）"页签是**另一条对照线**，展示模型自报 state，用于人机对比，不参与工作台门禁
- **当前 key 状态：已配置但无效**。真实调用返回 `HTTP 401 Authentication Fails, Your api key: ****25b5 is invalid`。所以现在界面跑的是本地文案兜底。
- 安全纪律：key 视为已泄露，必须轮换；`secrets.toml` 留在 `.gitignore`；不进仓库、不进作品集压缩包；上线走 Streamlit Cloud secrets

三句话讲法：
1. "判定不交给模型，模型只负责把已经判定为可发的话说得更像人。"
2. "模型挂了不影响判定，因为判定是规则做的。"
3. "我留了一条对照线，能看到模型自己判会判成什么，用来评估要不要放权。"

## 十一、评测数据（这是全项目唯一的真实测量结果，务必用准）

来源：`data/evaluation_results.csv`，**50 条评测用例 × 3 个版本（V1/V2/V3）**，规则引擎离线跑出来的结果，**非估算**。
运行主体是 `engine.py`（历史规则基线），**不是** `policy.py` 的五态判定层。README 第 103 行明确写着"评测里的 82%/88% 是规则基线的历史数字，与现在的五态不是同一个系统，不要混着讲"。

复算结果（字段：version / user_query / pred_intent / expected_intent / pred_handoff / expected_handoff / pred_risk / expected_risk / key_hit / answer / refs）：

| 版本 | 用例数 | 意图识别 | 转人工判定 | 风险判定 | 要点命中 | **无依据回答** |
|---|---|---|---|---|---|---|
| V1 | 50 | 41/50 = 82% | 20/50 = 40% | 20/50 = 40% | 15/50 = 30% | **50/50 = 100%** |
| V2 | 50 | 41/50 = 82% | 33/50 = 66% | 33/50 = 66% | 24/50 = 48% | **0/50 = 0%** |
| V3 | 50 | 41/50 = 82% | 44/50 = **88%** | 44/50 = 88% | 25/50 = 50% | **0/50 = 0%** |

- **82% = 意图识别准确率**（三版相同，说明意图层没改过）
- **88% = V3 的转人工判定准确率**（44/50），不是"AI 准确率"，不是"上线提升"
- **无依据回答**定义（app.py 评测页真实口径）：`answer` 非空 **且** `refs` 为空 **且** 未判转人工。这正是北极星指标的离线代理指标
- 最有说服力的一条：**无依据回答从 V1 的 50/50（100%）降到 V2/V3 的 0/50（0%）**，而意图识别始终 82% 没动——说明改善来自"加了依据与门禁"，不是"模型变聪明了"

正确讲法：
> "50 条评测用例离线跑三个版本。意图识别一直是 82%，没变；但无依据回答从 100% 降到 0，转人工判定从 40% 升到 88%。这说明收益来自判定门禁，不是来自更强的生成。这是规则基线的离线数据，我没有上线数据。"

**禁止**：把 88% 说成 AI 准确率 / 上线后提升；把 50 条评测和 15 条验收用例混为一谈（**两套不同的东西**：50 条是 engine.py 的离线评测集，15 条是 policy.py 的判定验收用例）。
**禁止**编造任何历史基线（如"原来 AHT 5 分钟""原来投诉率 3%"）。没有测量过的数字一律标注"假设/未验证"。

## 十五、写作纪律（所有文档共同遵守）

1. 数字只能来自本文件，或现场跑代码得到；不得凭印象写
2. 规则 ID 必须真实存在（售后规则-001…014 / 商品规则-001…009 / 物流规则-001…008）
3. 状态名只用五态英文 + 固定中文标签
4. 任何未测量的数字必须显式标注"假设"或"未验证"
5. 不得声称已上线、有真实用户、有业务收益
6. 不得把模型说成决策者
7. 面向初学者的文档要给出"怎么做"和"怎么自测"，不能只有概念
8. **函数签名、参数名、JSON 字段名必须现场读代码核对**，不许凭印象写（本轮已因此纠正：`decide` 无 `order=` 参数、`orders` 是 list、主键 `orderId`、依据键 `kbId`、KB 无 `scope`/`updatedAt`）
9. 文档里出现的每个"已实现"都要能指到具体代码行；指不到的一律进 §13.1 缺口表
