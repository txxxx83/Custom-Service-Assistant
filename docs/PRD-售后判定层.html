先读这一段：这份 PRD 的性质

这是一个个人作品集项目的需求文档，产品、开发、测试三个角色都由我承担，没有真实用户、没有上线、没有真实业务指标。为了不把它写成一份假装有大团队的文档，本文做了三件事：

  • 功能清单里每一条都标注真实实现状态（已实现 / 部分实现 / 未实现），可以逐条对着代码核；
  • 所有数字要么是跑代码得到的（50 条评测、15 条验收用例、31 条规则），要么显式标注为假设（如 ¥12 运费）；
  • 排期是个人可执行计划（每周 14 小时），不是虚构的团队工时。

被问到"这个 PRD 是真做过的吗"——功能清单的状态列和验收标准就是答案。

1. 需求背景

一句话定位：查得到、可逆的（物流、发票、地址）自动答；涉钱涉责的（退款、赔付、质量认定）必须先过人一遍——答错的代价不可转移。

1.1 问题描述

电商售后客服的成本，通常被归因为"答得慢"。但在这个项目调研的场景里，真正贵的不是慢，而是答得没依据——客服说出一句听起来专业、实际上系统里根本没有对应事实的话。

三个真实存在于本项目会话数据里的例子（mock-data.json 的 counterfactual 字段）：

会话客服会说出口的话系统里的事实代价
C1"退款 1–3 个工作日到账，请您耐心等待。"refund.refundNo = null，status = submitted_not_created——退款单根本没生成等一周也不会到账，客户二次进线 + 投诉
C6"您的换货已经在仓库处理中了。"missingFields = ["换货单号"]——换货单没落库48 小时后无法兑现，承诺变谎言
C5"可以补差价，我帮您提交。"该单没有活动标记，若是秒杀或券叠加则价保不适用提交后被驳回，客户认为被耍
核心洞察：这三个例子里，客服都不是"不会答"，而是"答得太顺"。 所以本产品的价值主张不是生成更快的回答，而是在回答发出之前判定这句话能不能发。 换句话说——AI 的价值有时是拦住人已经说出口的承诺。

1.2 为什么不选"提高自动解决率"

自动解决率是行业最常见的北极星，但它在本场景下会激励错误的行为：把不该自动答的问题也自动答了，短期指标好看，长期品退率与纠纷率上升。本项目明确不追求自动解决率，宁可让 7 条会话里只有 1 条可发。

1.5 约束条件

  • 时间约束：个人项目，每周可投入约 14 小时；作品集需在投递季前定稿。
  • 资源约束：一人承担产品/开发/测试；无真实客服可访谈（当前最大缺口，见 §7 风险 1）；无研发、测试、运营团队。
  • 技术约束：Streamlit + Python 标准库；无数据库、无后端服务、无真实接口；订单与知识全部为本地 JSON；审计日志存 session_state，刷新即丢。
  • 数据约束：全部模拟数据。类目锁定美妆个护单一类目；跨类目证据仅用于归纳共性问题，未做跨类目验证。
  • 合规约束：过敏等健康风险不得由客服口头定性，必须转人工；投诉/法律/舆情词命中即拦截；API key 不得进仓库、不得进作品集压缩包。
  • 模型约束：DeepSeek 只改写 ready 态措辞，不参与判定；当前 key 无效（HTTP 401），实际跑本地文案兜底。

2. 策略矩阵

本产品的"用户分群"不是按人口属性分，而是按会话的可判定状态分——因为决定体验差异的不是客户是谁，而是系统此刻掌握多少事实。这是本项目策略设计的关键取舍。

2.3 A 场景策略：把动机冲突显式标价

「买错色号想换」这一句，客服可以引导成三条不同的路径。三条路径对客服的省事程度和对商家的代价方向相反。本产品的策略是：不替客服选，而是把代价摆出来。

路径额外运费成本计品退率影响店铺评分对客服对商家
无理由退货¥0（买家承担）否否需解释运费，稍费口舌最便宜
换货¥12 假设值否否流程略长中等，且符合客户真实诉求
品质退货¥24 假设值是是最省事最贵，可能触发平台处罚
必须声明的假设：ASSUMED_SHIPPING = 12 是假设单价，不是实测运费。 三条路径的相对关系有政策依据（订单 policyHooks K1/K2/K4）；绝对金额没有依据。 面试时主动说这句话，比被追问出来强得多。

2.4 明确不做的策略（Won't）

不做为什么
全自动发送（无人工确认）与"发送前判定"的主张直接冲突；本产品的价值在于人仍在环内
追求自动解决率会激励"把不该自动答的也自动答"，长期推高纠纷率
多类目扩展跨类目证据只够归纳共性问题，不够支撑规则；先把单一类目做穿

真实工单系统对接无接口权限；repository 层已隔离，换真接口只替换该层
让 LLM 参与判定判定必须可复现、可测试、可追责；模型自报 state 在工作台被丢弃

3. 判定规格（本 PRD 的核心，研发按此实现）

3.1 单一事实源

policy.decide(question, order_no="", kb=None, orders_doc=None, dialog="", as_of="") -> Verdict

建议卡、发送门禁、转人工原因、操作审计全部只读这一份 Verdict，任何一处不得自己再写一套 if。

这条规格来自一个真实缺陷：早期版本两处各判一次，导致"卡片显示不可发、发送按钮却能点"。 界面矛盾不是 UI bug，是判定不唯一。修法是收敛到一个函数，而不是同步两处逻辑。

3.1.1 参考时刻 as_of（可复现性规格）

模拟数据没有真实时钟，凡是要算"过了几天"的判定都必须有一个显式基准：

项规格为什么
取值app.conv_as_of(cid) = 该会话最后一条消息的 at；「试一句」用 app.order_as_of(order_no)，未选单则取全局最后一条消息基准必须来自数据本身，不来自运行环境
禁止不得使用 datetime.now()否则同一张单在不同日期跑出不同结论（七天窗口过期、停滞天数变化），演示无法复现，验收用例也会随日期变红
落地写入 Verdict.as_of，随判定一起可审计坐席/复盘时能看到"这个结论是按哪个时刻算的"

这条是产品决策而非技术细节：判定必须可复现，才谈得上可审计。面试被问"为什么不用系统时间"时按此回答。

两处必须说清的实现现状：
  • 标签只有一份：ready 的中文标签是「可发建议」。早期 app.py 另写了一套（"可审核"），与 policy.py 不一致，已于 2026-11-12 改为 {**policy.STATE_LABEL, "missing": "暂无建议"}。missing（暂无建议）是界面独有态，表示还没产出建议，不是判定结果。
  • error 态当前不可达：标签、归属、转人工原因三处映射都定义了它，但 decide() 里没有任何分支产出 state="error"；orders.json.lookupRules 声明的第三出口"查询失败"也未实现。真接订单接口后超时会渲染出空标签——这是已知未实现项，不是已工作的兜底。

3.4 发送门禁（界面唯一判据）

can_send = (
    bool(draft.strip())                                    # 有内容
    and not locked                                         # 会话未结案
    and verdict_can_send                                   # 只读 Verdict
    and st_["status"] not in {"handed_off","waiting_customer"}
    and ack                                                # conflict 态需勾选确认
)

五个条件全部成立才解锁发送按钮。ack 在非 conflict 态默认 True。

3.5 可解释性规格

  • Verdict.steps 记录真实执行步骤，第一步固定为"识别意图"；界面渲染它，不得另写模板。
  • 每条依据必须可点开看到规则原文（31 条规则的 question / conditions / answer / cannot_answer）。
  • need_info 必须说清缺哪个字段、为什么需要，并给出可直接发出的追问话术。
  • 物流类 ready 回复必须引用订单真实运单号；不得声称已执行没有记录的动作（如"已为您登记催件"）。
  • 客户口径 vs 字段口径必须对账：话术里的一切数字只能由订单字段算出（停滞天数 = as_of − logistics.lastNodeAt），不得抄客户原话。客户自述与字段口径不一致时，Verdict.steps 必须追加一步「核对客户口径」，写明两个数字并说明采用字段口径。节点时间缺失时不得编造天数，改为"算不出停滞天数，先按异常登记催件"。
  • 依据本身也要对齐政策：规则的 conditions 必须与店铺政策原文（K1–K6）同口径。命中了一条与政策矛盾的规则，即使状态是 ready，这句话依然没有依据。
这两条规格来自本轮走查抓到的两个真实缺陷（都已修，并有用例守住）：
  • 系统抄了客户的数字：C3 客户说"五天没动"，compose_answer 原来用 _days_mentioned() 把"五"抠出来直接写进话术；按 lastNodeAt=2026-10-31T22:40 到会话末条 2026-11-05T10:35 复算实为 4 天。一个号称"只说有依据的话"的系统在复述未经核对的客户自述。修法见 §3.1.1 + 本节后两条，第 15 条验收用例断言话术含"已经 4 天没有更新"、不含"5 天"、steps 含"核对客户口径"、不含"已为您登记"。
  • 依据与政策不一致：物流规则-003 原写"超过 3 天无更新"，店铺政策 K6 第一档写"超过 48 小时"。已把规则改为"物流超过 48 小时无更新（与店铺政策 K6 第一档同口径）"；K6 第二档"超 72 小时且客户要求可补发或退款"涉及金额，写入 risk_note，不由该条自动作答。
